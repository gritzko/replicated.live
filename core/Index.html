Beagle SCM

Indices

For search, display and handling git object can be indexed. git per se only index their location in the store for fast retrieval. be and bee index a lot of things: commit graph, file paths, trigrams, etc. Both git and be-native store keep the objects, and all the multitude of functions above that is very index-dependant. In a sense, beendexes turn git into a true database.

Technology

All indexes are built lazily; if some recent commits are not indexed yet, that happens on the first query. Beendexes are stored as LSM-like sorted runs of wh128 entries ("whiffs"). Periodically, runs get merged and deduplicated.

Field types

There is a bunch of entry types containing the same bit field types in different combinations. There are no full-text indexes or vector-anything indexes. Mainly, it is hashlets:

  • hashlet60 — the TOP 60 bits of a 20-byte sha, big-endian (dog/WHIFF.h whiff_hashlet(s, 15)); blob, commit and ref hashlets are ALWAYS the full 60.
  • path_hl — 40 bits: the TOP 40 of the sha1 hashlet of the repo-relative path text, no leading slash (hlOfText(path) >> 20).
  • rev — a 20-bit per-path arrival counter, minted oldest-first as the walk seals commits; rev = 2^20-1 is the EMPTY slot spelling, never a real rev.
  • vnib — the low nibble of a value, RESERVED (0) wherever the record does not name a field for it.
  • seg_hl — the top 40/20/10 bits of ONE path segment's text hashlet (filename / parent dir / ancestor dir); 0 spells "absent", so a genuine 0 hash bumps to 1 (the filename slot names nothing absent and never bumps).

Entry types

Eight kinds, the nibble in key & 0xf. Rows are never deleted and re-puts are idempotent.

  • REV-BLOB (1) — key path_hl:40|rev:20|1, val blob_hl:60|vnib:4: which blob this path carries at this rev.
  • REV-CMMT (2) — key path_hl:40|rev:20|2, val commit_hl:60|vnib:4: the commit that introduced this rev of the path. A DIRECTORY path gets these and ONLY these (LITE-044): one row per commit that changed anything under it, which is what lite list attributes a dir row from.
  • REV-PARS (3) — key path_hl:40|rev:20|3, val par1:20|par2:20|par3:20|4: this rev's parent REVS; a 4th+ parent rides a second row.
  • CPAR (4) — key commit_hl:60|4, val parent_hl:60|ord:4: one row per parent, first parent ord 0; a ROOT commit gets one row with an EMPTY parent.
  • B2P (5) — key blob_hl:60|5, val path_hl:40|rev:20|vnib:4: the reverse map, which path/rev a blob is the content of.
  • FSEG (6) — key fn_hl:40|prnt_hl:20|6, val seg0..seg5:10 ROOT-FIRST| depth:4: the partial-path record (LITE-011), the last segment's hash plus the ancestor dir segment hashes; a pure function of the path TEXT, minted once at the path's rev 0, never invalidated (it names, not states).
  • LINK (7) — key dst_hl:40|0:20|7, val src path_hl:40|0:20|vnib:4: the backlink SUSPECT record (LITE-033), one row per (dst, src) pair. dst_hl is minted from the target TEXT — the repo-relative path text for a file link, the bare ticket code (LITE-029) for a ticket link, so a ticket's backlinks survive the thin↔fat layout move. Anchors are dropped: a row names files, not places.
  • MARK (F) — key ref_hl:60|F, val tip commit_hl:60|vnib:4: the per-ref watermark, the LAST write of a run (DOG-027). lindex keeps its own under the RESERVED ref hlOfText("lindex"), which is no ref and so never collides.

What the records buy

Each query is a scan of ONE key prefix; no ODB ancestry walk happens at query time.

  • A file's whole history is ONE prefix scan of its path_hl: the rows come back rev-ordered, each rev naming its blob, its commit and its parent revs.
  • The commit DAG is the CPAR rows alone, which is what lite log walks (LITE-007 ancestry), newest-first over a reverse Kahn.
  • CPAR doubles as the INDEXED flag: a commit with any CPAR row is in the lane, which is why a root commit still gets an empty-parent row.
  • A commit hashlet IS an object name — git.getHex takes any 6..40 hexlet — so a row's 15-hex hashlet60 reads date, author and subject off the ODB.
  • lite list's last-commit fuse (LITE-017) reads both halves off the entry's OWN rows, exact at any depth and walk-free: a FILE folds its path_hl chain, a DIR takes the NEWEST of its REV-CMMT rows (LITE-044). A hot dir changes in most commits, so its chain is as long as the history and is never read whole: revs are dense, so the newest is found by galloping exact-key probes, O(log) seeks for the indexer and for the fuse alike.
  • A PARTIAL path (abc/TCP.c, bare TCP.c) resolves via one FSEG scan plus a pruned descent of a commit's tree (index/resolve.js): the tree entries carry the real names, so the answer is TEXT and ambiguity is a list.
  • "Who links to this?" is ONE prefix scan of the target's LINK key: the vals are the carriers' path_hl, named back to text by the same tree descent.
