MARK-001 MED: a list entry's continuation line renders as a separate <p> inside the <li>

StrictMark list entries soft-wrap: a following line indented to the SAME depth continues the entry's text (StrictMark; the wiki line budget — bullet 2 lines — makes such continuations normative across /wiki and /todo). mark instead flushes the continuation as a nested <p> inside the still-open <li>, so one logical entry renders as bare inline text PLUS a paragraph block (wrong structure, wrong spacing). Reported by gritzko 2026-07-07; reproduced with ~/bin/mark same day. Scope: beagle/mark (C + ragel). Method Issues.

Input

Context

  • Repro (2026-07-07): - first entry line + next line continuation indented to the same depth renders <li>first entry line<p>\ncontinuation…\n</p>\n</li> — entry text bare, continuation wrapped in <p>.
  • Mechanism leads: MARK.c:38 buffers soft-wrapped PARAGRAPH text (joined into one line at flush), but a list entry's own text is emitted bare while its <li> is held open for nesting (MARK.c:396-405 frame model, mark_para_flush MARK.c:412); the continuation line then enters the paragraph buffer and flushes as <p> INSIDE the li.
  • A deeper-indented paragraph inside an entry legitimately nests as <p> (the deferred-</li> design) — only the SAME-depth continuation is misclassified.

Goals

  • A same-depth continuation joins the entry's inline text with a space (the same soft-wrap join the paragraph buffer does): <li>first entry line continuation…</li>.
  • Deeper-indented blocks inside an entry keep nesting as they do today; sibling and shallower lines still close the entry.

Constraints

  • Fix in beagle/mark (MARK.c / MARKE.c.rl) — line classification is ragel's job, no manual byte scanning (CLAUDE no manual parsing).
  • Repro-first in mark/test (strict-dir harness); wiki/blog pages render via make, so re-render must stay byte-stable except the fixed lists.

WIP

Design decisions

  • Entry text rides the EXISTING paragraph buffer with a para_li mode (para_del for wontfix <del>): the para continuation path does the same-depth join, mark_para_flush emits li-text bare (no <p>), budget-checks the JOINED entry as "bullet"; sub-4-space leftover indent trimmed at the join (spec ruling StrictMark.mkd:65 "a block continues on later lines via a 4-space indent").
  • Bullet budget now checks the joined entry at flush (2×64 total), not per source line — truer to the 2-line budget; a maxed 64+64 join could newly breach --strict (none in the wiki today).
