MARK-017: no API to read a .md file's YAML front matter — the preamble lexes as prose

Nothing in the tree knows what a .md front matter block is: grep -i 'front.\?matter\|preamble' over ~/src/quickjab hits only unrelated code. A file that opens with ---, a run of key: value lines and a closing --- is read by MDTLexer (dog/tok/MDT.c:207) as plain document body — the opening delimiter matches MDTThematicBreak (MDT.c:139:y0) and paints as a ruler, and every YAML line then goes through the inline machine one line at a time, so title: x comes out word+punct+word, a bare [tag] in the body fuses as a wiki shortcut link (DOG-042) and a # line inside the block is lexed as an ATX heading. Two things are missing and they are separable: the LEXER must stop treating the preamble as prose, and there must be a reading API — a caller (site rendering, an index, the OG meta of MARK-011) has no way to ask a .md file for its title, date or tags. The .mkd side has had its answer since DOG-026: the meta pair Key: value is block grammar, matched by MKDTB.c.rl:74 and exposed as a region; .md needs the equivalent for the dialect it actually uses.

Input

Context

.md is a first-class ext in the dispatch table (dog/tok/TOK.c:226), and front matter is how every generator on the planet carries .md page metadata; the renderer side already wants it (MARK-011 needs title/description for link cards, MARK-006 rules on .md first-classness).

  • Repro today: feed ---\ntitle: Hi\ntags: [a, b]\n---\n\n# Body\n to MDTLexer; the delimiters come out R, title comes out S, [a, b] comes out a G/F/G wiki link, and nothing reports a title at all.
  • YMLTLexer (dog/tok/YMLT.h) already exists, same {data, cb, ctx} shape, already registered for yml/yaml at TOK.c:166 — the highlighting half needs no new grammar, only a delegation.
  • There is no .md metadata consumer to break: this is new API, not a behaviour change to an existing one.

Goals

A .md preamble is recognized as its own block, painted as YAML, and readable through a documented API.

  • Extraction: given the file bytes, hand back the front matter body slice and the offset where the document proper starts; NONE when the file has no preamble. Recognized ONLY at byte 0, opener exactly --- + blank tail, closed by a --- or ... line or by EOF.
  • Reading: iterate or look up the flat key: value pairs of that body — scalars (plain, '/" quoted), inline [a, b] and block - item sequences, # comments skipped. A nested map is REFUSED with a code, never half-parsed.
  • Lexing: MDTLexer emits the two delimiter lines as markup and routes the body through YMLTLexer; # inside the preamble is a YAML comment, [a, b] is not a wiki link, and a .md file WITHOUT front matter lexes byte-identically to today.
  • --- anywhere below line 1 stays a thematic break, per CommonMark; the preamble is a head-of-file extension and nothing else.

WIP

Design decisions

  • BOTH, settled: MDFMEach(body, cb, ctx) is the primitive (one cb(key, value) per pair) and MDFMGet(body, key, val) is a nine-line lookup over it — a caller after title should not write a callback, an indexer after every pair should not probe by name.
  • Its own module, tok/MDFM.h: the readers (MARK-011 OG meta, a site index) want the pairs with no lexing at all, while MDT.h is the lexer's {data, cb, ctx} state. MDT.c:6:y0 includes MDFM, never the reverse.
  • A sequence is FLAT — one cb(key, elem) per element, inline [a, b] and block - item alike — so the two YAML spellings are indistinguishable downstream, as .mkd's repeated meta keys are (DOG-026).
  • Regions, not copies: mdfm{open, body, close, rest} and mdfmline{kind, key, val, seq} mirror mkdtblock's shape (MKDT.h:40:R6); quotes and brackets fall off at the machine's own region ends, nothing is unescaped or allocated.
  • Delimiters paint 'H', one token per line — the preamble is a fenced region and takes the code fence's tag (MDT.c:220:y0); the RRRR of a thematic break stays the ruler's alone, so the two never read alike.
  • A --- that is the WHOLE file stays a CommonMark ruler: lacking a closer, a preamble needs a body (MDFM.c:41). TOK01.c:1112:bb pins "---\n" as RRRR and that pin is right — an empty EOF-closed preamble carries nothing.
  • Two ragel machines, one twin: mdfml classifies ONE preamble line into kind + key + value regions (the MKDTB.c.rl idiom — finishing actions record the ends, C only reads them back), mdfme drains one element off an inline sequence.

Blockers and bummers

  • An inline # comment after a PLAIN scalar is not stripped: title: Hi # note reads Hi # note, the scalar rule and the comment rule being ambiguous over the same bytes. After a quoted or [..] value the comment IS stripped.
  • A nested map refuses the WHOLE body — one nested key and MDFMEach yields no pairs at all. MDFMNEST is the caller's cue to fall back, never a partial read; that is the ticket's own rule.
  • MDTLexer sees bytes, not files, so a diff hunk that happens to open with --- plus a key: value run would lex as front matter. Nothing re-lexes a .md hunk from a non-zero offset today.
