GRAF-003: graf pair cache never persists — flush on consumer exit

Now
DONE

The GRAF-001 ahead/behind pair cache computes and then DROPS its results every run: no caller ever invokes graf.flush(), and the auto-flush threshold (MEM_FLUSH = 4096 pairs) is far above what one work render produces (~200 pairs). So every jab work re-walks the DAGs the cache was built to spare.

Input

Context

Profiled jab work 2026-07-24 (warm cache, ~3.6k syscalls): the ahbeh walks open+mmap nearly EVERY pack, EVERY run — the pair cache is cold each time.

  • 341 .keeper opens per run: 80/87 packs of ~/.be/beagle-ext, 64/67 of ~/.be/beagle-ext-tests (154 unique packs total).
  • shared/graf.js seekPair always misses on disk: the shard's *.graf.idx runs are NATIVE (types 1..5, newest Jun 30) — zero 0xA/0xB pair rows ever landed.
  • flush() fires only at memPairs >= MEM_FLUSH (4096); a 93-wt forest caches ~200 pairs, exits, loses them. grep -rn 'flush' jsrc/views/work/ — no caller.
  • GRAF-001 already specifies "persist as a fresh small run via idxmaint"; the machinery exists and is tested, it is just never reached.

Goals

Persist the memtable at end of run so run N+1 seeks what run N walked; the steady state is near-zero pack IO (tip metas only).

  • work.js registry keeps its per-shard graf handles; after emitForest (all hunks fed) call flush() on each opened graf.
  • First run seeds the shard runs; a repeat jab work with unchanged tips must do 0 paint walks (verifiable via graf.stats).
  • Any future consumer (status/relate) inherits the same rule: flush what you opened, once, at exit.

Constraints

  • Flush stays best-effort under the native .lock.graf flock; a read-only store degrades silently (the idxmaint norm, already in graf.js).
  • An empty memtable must not land an empty run (flush() already guards; keep it).
  • No flush mid-render — one run land per (shard, run), at the end.

WIP

Design decisions

  • (proposed) registry() grows flushAll() iterating its grafs map; emitForest calls it in a finally-style tail so a throw mid-render still lands what was computed.
