JSQUE-020: drop the job queue, dispatch by plain recursion

Now
DONE

Retire the .be/queue ULOG dispatch (core/job.js + core/loop.js + core/barrier.js) in favour of the in-process recursion the read views already use (core/recurse.js). The queue was JSQUE-001/002/003/006; this reverses that where recursion is strictly simpler.

Input

Context

  • Read views (status, diff, ls, …) already dispatch WITHOUT the queue via core/recurse.js — a synchronous depth-first walk (JAB-004/014). Only get + post touch the queue's barrier.
  • Only two verbs require("core/barrier.js"): verbs/post/post.js and verbs/get/get.js. Every other "barrier" mention (delete preflight, status "no barrier") is unrelated; the .fold( in get/patch/weave is weave.fold, a different primitive.
  • post's barrier is a SINGLE-PASS ceremony, no fan-out: it already holds the whole decision set in memory (dres.decisions) and builds the tree from it (commitM.buildTree(dres.decisions)); the barrier.fold callback is just acc.count++ and its ONLY consumer is a cross-check (POSTFOLD: range mismatch) — tautological once in memory (post.js:569-600).
  • get's delSweep fold is REPORT-ONLY: it back-scans the queue to tally delete leaves into ctx._get.delSwept, and the code notes JS has no rmdir leaf so the empty-dir collapse is a no-op; the per-path del rows are already the durable effect (get.js:867-888).
  • What the queue genuinely earns elsewhere: breadth-first order, durable back-scan fold, crash-resume via the .done offset. None of the three is load-bearing for the two folds above.

Goals

  • Delete core/barrier.js and both call sites: post's commit fold → an in-memory count assert (or drop, since leaves derives from dres.decisions); get's delSweep → an in-memory tally over the fan-out descriptors (or drop if delSwept is never rendered).
  • Prove FULL parity: the existing test/ golden-snapshot suite stays green with no test edits.
  • End-goal (LATER phases, not this worker): replace the loop.js queue dispatch itself with recursion, then retire core/job.js.

Constraints

  • No test edits (meta/work.mkd §4). Start with a characterization run of the current suite as the repro baseline.
  • Never touch the C beagle/; JS be/ only. Run via jab, never native be.
  • test/ is a submodule — stage new/changed source with jab put so a jab get recursion cannot sweep it.
  • Scope THIS worker to the barrier removal only (get + post + core/barrier.js). Queue/loop dispatch removal is a follow-up.

WIP

Design decisions

  • Barrier folds carry no data the handler lacks in memory, so removal is a substitution, not a re-architecture: replace durable re-read with the already-held array.
  • Phase the work so each phase lands green independently: (1) barrier, (2) loop dispatch → recursion, (3) delete core/job.js.
