Two processes opening one Pup lane read-write race on the ONE memtable file: dog_pup_mem_open (dog/DOG.c:1106) goes through FILEMapCreate (abc/FILE.c:821), which is FILECreate + FILEResize + map, so the second opener truncates the file the first has live pages of, and each seals a run under the same max + 1 seqno. What follows is a SIGBUS in the first writer or "cannot commit the index" in both — bee/test/coldfan leg 5 pins the case and fails about one run in ten under load on a pristine tree (2026-09-18). Every read view of bee opens its lane rw (the bring-up is on every use, BEE-065), so two bee log in two shells race the same way. Ruled 2026-09-18 (gritzko): an rw lock on the lane. The forked scan of BEE-072 is NOT the racer — a child writes a dir of its own — but it shares the hazard whenever two independent bee processes bring one repo up at once.

Input

Context

  • dog_pup_mem_open: the memtable is <dir>/<ext> — one file per lane, every rw opener's — created or re-created at open, sized pages whole pages, mapped rw; its fd rides the dict under DOG_PUP_MEM_KEY. A ro open never touches it.
  • DOGPupCreate (DOG.c:798) picks max + 1 over the dir's runs and the stack; DOGPupCreateAt refuses a taken key with DOGPUPFAIL. The seal is tmp + rename, atomic per file, and blind to a sibling writer.
  • abc/FILE.c has no flock/fcntl lock anywhere; FILECreate is O_CREAT | O_TRUNC.
  • Readers are safe by construction (DOG-046): runs are immutable, a ro open maps whatever <seqno><ext> files it finds.
  • quickjab pup.c _pup_<lane>_open(dir, ext, mode, mem) is the only caller; bee's openIndex/openKv/openTri (index/index.js:340:Wt) and the BEE-065 ladder in upForeign (:1071) are the callers of that: rw with a fall-back to ro when rw refuses.

Goals

  • dog_pup_mem_open takes an EXCLUSIVE flock(2) on the memtable file BEFORE any truncation: open <dir>/<ext> with O_RDWR | O_CREAT and no O_TRUNC, lock, and only then resize and map. The lock lives as long as the fd, so it dies with the process — a crashed writer leaves no stale lock.
  • Two modes on the rw open, a flag through DOGPupPutMem/the open path: WAIT (LOCK_EX, block until the holder closes) and TRY (LOCK_EX | LOCK_NB, refuse at once with a NEW code DOGPUPBUSY, distinct from DOGPUPFAIL). A ro open takes no lock.
  • A waiter that gets the lock re-reads the dir (dog_pup_refresh) before it writes, so the runs the holder sealed are in its stack and its next seqno is past them.
  • FILEMapCreate stays as it is for its other callers; the no-truncate open + lock is a new FILEMapLockRW(buf, path, size, wait) or an equivalent in abc/FILE.c, with FILELock/FILEUnlock beside it if a bare pair reads better.
  • Test, dog/test/PUP*.c: two processes (fork) opening one lane rw in WAIT mode both commit, in order, and the dir holds both runs with distinct seqnos; in TRY mode the second answers DOGPUPBUSY and writes nothing; a ro open beside a locked rw open reads the runs; the lock is gone after the holder's DOGPupClose and after its _exit.
  • quickjab: _pup_<lane>_open grows an opts.wait (default WAIT) and abc.index throws "index busy" on DOGPUPBUSY; a leg in test/index.js over io.fork() (QJAB-014).
  • bee: upForeign and bee index open in WAIT mode, so the coldfan leg has BOTH processes answer — the loser waits, finds the mark and no-ops; the read views (log, list, diff, door) open in TRY mode and fall to the ro rung on busy, so a bee log never stalls behind a nine-minute linux index; test/coldfan leg 5 pins the stronger claim ($R1 = 0 && $R2 = 0, both answers equal).

Constraints

  • flock, not fcntl record locks: the lock must survive fork() in the child that inherits the fd (BEE-072's children never close it) and must not be dropped by an unrelated close of another fd on the same file, which fcntl locks are.
  • No lock file of its own: a <ext>.lock name ends in no live ext and bee's sweep would unlink it; the memtable file is already the one every writer shares.
  • macOS and Linux alike (flock is in both); a filesystem without flock (some network mounts) answers the error and the open FAILS rather than proceeding unlocked.
  • The ro path and the run format are untouched; the dir layout is untouched.

WIP

Design decisions

  • Lock the memtable file itself: it exists exactly when a writer is at work, every writer already opens it, and it is the file the race destroys.
  • WAIT as the default at the C level, TRY the caller's choice: a bring-up that waits answers with the winner's rows, a view that must not stall reads what is there.
