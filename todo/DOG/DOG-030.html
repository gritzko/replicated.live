Context

The lite first index of a >1M-commit repo (~/src/linux) runs ~an hour. Profiled on git.git (81,726 commits, local bare clone): first index 344s, of which descend (JS tree diff, lite/index/index.js) is 292s — 89%. Inside that, readTree is 164s over 373k calls: every touched tree, commit-side AND parent-side, is drained entry-by-entry into a JS Map (name string + 40-hex sha string + object literal per entry), then descend scans the FULL width of every changed dir (git.git root = 559 entries, linux dirs 1000s) with three .map() allocations per entry to find the 1-3 entries that differ. C leaves are cheap by comparison: getHex 17.5s/246k calls, tree cursor 0.15s, LSM seals 35s.

  • Probe scripts + numbers: ~/tmp/prof/probe{,2,3}.js (phase-timed bringUp copy, wrapped native leaves).
  • linux read-only probe: BFS 40us/commit (fine), descend-like tree traffic ~8ms/commit → the hour.
  • INDEXES.mkd already rules the prune: a subtree whose sha equals ANY parent's is pruned whole — so JS only ever NEEDS the differing entries; today it materializes everything and prunes after.

Goals

One C leaf that returns ONLY the changed entries, so JS work per commit is O(changed), not O(dir width).

  • RULED API: git.getTreeDiff(h, sha40A, sha40B) -> a git-tree-FORMATTED buf ({mode} {name}\0{sha20} entries, existing git.tree(bytes) cursor reads it, no new JS record shape).
  • Each changed path rides as an adjacent PAIR of entries, same name: new side (A) first, old side (B) second; the all-zero sha1 spells "absent on this side" (add = zero old, delete = zero new).
  • A changed-subdir pair carries the two shas the next getTreeDiff(h, subA, subB) call needs; a changed-blob pair carries exactly the (blob, pblob) emit needs. Recursion stays in JS; merges are pairwise calls per parent, intersected in JS.
  • lite/index/index.js descend cuts over; readTree's Map leaves the index hot path.
  • Target: git.git first index from 344s to well under a minute; identical index rows (byte-identical run contents vs the old walk on a fixture and on git.git).

Constraints

  • The API above is ruled — no reshaping. C side: one dog/git function over raw tree bytes (sorted N=2 merge scan, memcmp on 20-byte shas), binding in quickjab git.c stays marshalling-only (git.c waist rule: no format logic in the binding).
  • Both trees are read INSIDE the leaf off the odb handle (one ODBHex waist) — DOG-031's object cache then serves it for free.
  • Gitlinks (0o160000) dropped, as readTree does today.
  • No manual parsing in C outside the existing tree-entry drain (dog/git GIT.h machinery); repro + perf numbers first, tests green (lite/test/index/run.sh, rows.js), no other tests edited.

WIP

Design decisions

  • Output is a VALID tree-format byte stream but non-canonical (duplicate names, zero shas) — it is a DIFF encoding, never to be hashed or stored as an object.
  • Entry order: A's sort order (git tree order), pairs adjacent, new-then-old.
