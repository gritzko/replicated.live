A pup lane (DOGPupPut/DOGPupCommit, the DOG-027 LSM) has no write lock: two processes writing one lane race the seal/ladder and one dies with cannot commit the index. Field evidence 2026-08-13, ~/src/git/.git/be: a lite log (lazy LITE-006 bring-up) ran while another process was reindexing the same lane after an rm -rf — repeatable Error: cannot commit the index from _pup_wh128_commit, twice, two independent process pairs. Single-writer runs are clean (fresh 81726-commit index verified same day).

Input

Context

Every lite verb may WRITE (log brings the index up to date itself), so two concurrent invocations in one repo are an ordinary user action, not an edge case.

  • Seal names come from max(RONNow, max(DATA)+1) (DOG.c, DOG-027) — that de-collides run NAMES, not the ladder: concurrent compactions merge/unlink runs under each other.
  • Readers need no lock today (runs are immutable, the memtable is per-process); only the seal+ladder in DOGPupCommit mutates the dir.

Goals

Two writers on one lane serialize or one fails EARLY in plain words ("the index is busy, another process is writing") — never a mid-run cannot commit after work is lost.

  • Lock scope: the lane dir; taken by writers only, readers stay lock-free.
  • A dead writer must not wedge the lane (stale-lock recovery, e.g. flock semantics rather than a lock file's existence).
  • Behaviour on contention (block vs fail-fast) is a ruling to request before implementing.

Constraints

  • Belongs in libdog (dog/DOG.c pup layer), not in each binding; jab/quickjab inherit it.
  • ABC house rules (meta/abc.mkd); errors in plain words, not bare C codes.
