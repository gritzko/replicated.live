The tok32 stream bee paints and parses (render/html.js, mark/strict.js) comes from HUNKu32bTokenize, a thin wrapper over TOKLexer and the ragel machines: pure functions over a byte slice with a callback, no stdio, no mmap, no threads. A browser editor (a StrictMark page under contentEditable) wants that stream per keystroke with no round trip, so libdog gets one more build target: a wasm32 module exporting the lexer under quickjab's _tok_parse_into contract, and nothing else of libdog in it.

Input

Context

  • quickjab/tok.c:38 _tok_parse_into(srcBytes, lang, outU8) -> n is the JS face today: packed tok32 written straight into a caller-owned region, (srcn+1)*4 bytes worst case, source capped at 16 MiB (TOK_OFF_MASK).
  • HUNK.c:1558 HUNKu32bTokenize is 20 lines over TOKLexer (tok/TOK.c:325:ne), but HUNK.c drags in FILE, TTY, ANSI, ULOG, THEME and zlib; the wasm entry re-spells those 20 lines instead of linking HUNK.
  • tok/TOK.c resolves an ext through TOK_TABLE, which names every lexer, so the module links all tok/*T.c + tok/*.rl.c plus KEYW.c, BRCT.c, DEF.c, FREE.rl.c, MKDTB.rl.c; all are pure C.
  • abc surface the lexers touch: abc/PRO.h, abc/Bx.h, abc/INT.h, abc/PATH.h (TOK.c), abc/UTF8.h; abc-core as a whole is out — FSW, FILE, MMAP, BASS.c mmap and thread_local ABC_BASS.
  • abc/PRO.h:34 BASS is a 1 GiB lazy mmap; the lexers carve nothing from it, so the wasm build owns a small static arena.
  • Toolchain: clang here already targets wasm32; apk offers wasi-sdk, wasi-libc, wasi-compiler-rt, binaryen; quickjs-ng's CMake (quickjab/qjs/CMakeLists.txt:170) has the WASI/Emscripten branches as a pattern.
  • Consumer: bee serves the module beside the page and render/wrap.js's tok32 accessors read the result unchanged; that landing is a BEE ticket, not this one.

Goals

  • A wasm32-wasi module dogtok.wasm built by a separate cmake invocation under the wasi toolchain file; the top-level CMakeLists.txt takes an if (CMAKE_SYSTEM_NAME STREQUAL "WASI") branch that builds only the tok sources, the abc files they need and the entry.
  • Entry tok/TOK.wasm.c: exports tok_parse(src, srcn, ext, extn, out, outcap) -> n (n tok32 written, negative on refusal), plus tok_alloc(n) / tok_free(p) so JS can place its bytes; same guards as quickjab/tok.c:47 (16 MiB cap, 4-aligned out, room for (srcn+1)*4).
  • ABC_BASS defined in the entry over a static few-MiB arena, ABC_INSANE set, trace silent: no stderr, no clock, no fd reaches the import list beyond what wasi-libc needs.
  • A test/wasm/run.sh that builds the module and, under whatever wasi runtime is present (wasmtime, wasmer, node --experimental-wasi, else skip with a message), lexes the existing test/ fixtures and diffs the tok32 stream against native dogtok's tags and ends.
  • Module size and the import list recorded in test/wasm/run.sh's output; expect well under 1 MiB.

Constraints

  • No edits to any lexer .c.rl / .rl.c, and no #ifdef __wasm__ sprawl in TOK.c; the port is the entry file plus CMake. If a lexer will not compile for wasm32, that is a finding to report, not a fix to make here.
  • Entry file under 100 lines, comment budgets per /meta/comment, no manual parsing (the ext string is passed as bytes to TOKResolve, never split by hand).
  • The native dog library, dogtok and every existing test stay byte-identical in behaviour; ninja test green.
  • No commits, no be post; report and stop.

WIP

Design decisions

  • wasi-sdk over Emscripten: a plain .wasm with a wasi import list is loadable from one WebAssembly.instantiate and a 30-line shim; Emscripten's JS glue buys nothing for a callback-free API.
  • TXTT stays the fallback for an unknown ext, as in TOKLexer, so a .mkd page and a .c block get the same tags as the pager.
  • (open) whether the entry should also export tok_known_ext, so the client can decide server-side-only languages; cheap, gritzko rules.

Blockers and bummers

  • wasi-sdk and lld were absent at first; the CMake branch and run.sh each stop with one line naming the package. Installed 2026-09-07 (wasi-sdk 27, lld21).
  • The sysroot is per-target (include/wasm32-wasi/), so the three probes accept that layout beside the flat one.
  • abc/Bx.h bMap is header-inline, so every object names mmap; the branch takes wasi-libc's _WASI_EMULATED_MMAN / -lwasi-emulated-mman (and the getpid twin for PRO.h's trace helper), no source edit. The six imports are libc's stdio and exit, none reached on a good run.
  • No node, wasmtime or wasmer here; chromium is, so chrome.py bakes fixtures and native dumps into one page and --dump-dom prints the verdict. run.js is untested.
  • The abc subset came out of a link, not a guess: the tok objects' only non-libc externals are PATHu8sBase/PATHu8sExt -> _utf8sDrain32 -> d2s_buffered_n. find_package(ZLIB)/add_subdirectory(abc) skip under WASI but stay in place, or abc/test/PACK.c finds git/PACK.h.

Outcome

  • dogtok.wasm: 298580 bytes, 6 wasi imports, 3 exports; the tok32 stream is byte-identical to native dogtok on all 13 test/data fixtures and on three .mkd/.md pages (4626 tokens for wiki/StrictMark.mkd) in headless chromium; guards answer -1/-2/-3.
  • The changes live in quickjab/dog (git, main, uncommitted): CMakeLists.txt, tok/TOK.wasm.c, test/wasm/, one line in INDEX.md and README.md. That tree's TOKExtAt needs abc/RON.c too, so the abc subset is four files; the module is 448181 bytes there.
  • ~/src/libdog also carries the first cut of the same change, by gritzko's leave, not to be reverted by an agent.
