A Pup stack's memtable is the fixed file <dir>/<ext>, and dog_pup_mem_open opens it O_TRUNC (dog/DOG.c:1048, abc/FILE.c:357). Two rw handles on one dir — two processes, or two handles in one — therefore write ONE inode: the second open zeroes the first writer's rows, the first seals and renames the inode as a run, the second's seal finds no memtable and fails. Rows written before the clash vanish while rows written after it survive, which is exactly the MARK-without-CPAR poison BEE-061 found on 2026-08-23. A handle's run list is also read ONCE at open (DOGPupOpenAll), so a run another process sealed later is invisible to it until reopen.

Input

Context

two.js is the four-line repro over abc.index: handle A puts rows 1..5, handle B opens the same dir and puts 100..105, A puts 6 and commits, B commits.

  • On disk: [6, 100..104] — A's 1..5 gone, B's 105 gone, B.commit throws "cannot commit the index".
  • Live shape: bee's BEE-048 lane cache holds one rw handle per resident server; three bee http of three revisions were up at once, plus the hook's CLI process, all over quickjab/.git/be.
  • The 1584-byte run in BEE-061's snapshot holds 6 commits' rows plus the tip's MARK and zero tip rows — the second writer's memtable open zeroed the tip's rows between the last CPAR put and the MARK put.
  • dog_pup_key_taken (DOG.c:596) already probes the disk for a run name, so run NAMES never collide; only the memtable name does.

Goals

  • The memtable is PER PROCESS: name it <ext> with the pid (or a RON64 nonce) in it, e.g. <pid>.<ext> or <ext>.<pid>, so two writers never share an inode; DOGPupOpenAll keeps skipping every non-run name.
  • A writer notices runs other writers sealed concurrently: before a seal and a ladder, re-scan dir for <10-RON64><ext> names the dict does not hold and map them in (oldest-first order kept), so a ladder collapses the real stack and a reader after a commit sees every run.
  • A run unlinked by another process's ladder is tolerated: a dict entry whose file is gone keeps its mapping until close; the ladder never unlinks what it did not merge.
  • Tests in dog/test/DOG.c: two handles on one dir interleaved — every row survives, both commits succeed; a run sealed by a second handle is seen by the first after its next commit.
  • quickjab's test/pupmem.js / test/index.js legs for the same through abc.index.

Constraints

  • abc.index JS surface unchanged (cont.c:588): dir/ext ride the handle, no new JS state.
  • The 1/8 ladder policy (HIT.h) untouched; DOGPupCreateAt still refuses a taken key.
  • A crashed process's orphan memtable <pid>.<ext> is derived state: skip it on open (never read, never unlinked by dog; the owner sweeps, as bee's sweep does).

WIP

Design decisions

  • The pid form is enough for bee: one handle per process writes at a time. Two handles in ONE process still share the name — the in-process case is bee's BEE-048 lane cache, sequential today; a RON64 nonce per handle closes it for good and costs nothing more.
