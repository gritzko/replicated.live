DOG-041: a JS regex literal has a CHARACTER CLASS — an unescaped / in it

dog/tok/JST.c.rl lexes a regex literal as "/" ( [\\] any8 | any8 - [/\\\n] )+ "/" [dgimsuyv]* — a body that knows escapes and nothing else. A character class is where that breaks: /[,./]/g is legal JS and the / inside [...] needs no escape, but the rule ENDS the literal there. What follows is lexed as code, and if the rest of the class carries a quote (', ", a backtick — a punctuation class carries all three) it opens a string that never closes, the machine ends in a non-final state and the whole file comes back JSTBAD. A file that fails to lex has NO tokens at all, so bee paints it as one plain span: /bee/mark/html.js serves with no highlighting whatever.

Input

Context

Found 2026-08-16 by a reader on /bee/mark/html.js; dogtok mark/html.js answers Error: JSTBAD and prefix-bisection puts the first failure at line 65, const PUNCT = /["#$%&'()*+,./:;<=>?@[\\\]^{|}~!]/g;`.

  • The mis-lex is visible on its own: dogtok on const P = /[a/b]/g; emits G /[a/ then S b, P ], P /, S g — the literal stopped at the class's slash.
  • That alone only MIS-COLOURS; the error needs a quote in the tail: /[/x]/g lexes (wrongly) and returns OK, while /[/']/g, /[/"]/g and `/[/]/g` all return JSTBAD`.
  • JSTBAD costs everything, not one token: no token stream, so the painter falls through to its untokenised-tail path and the file is one tok-S span.
  • The rule is JST's ALONE — grep dgimsuyv dog/tok/*.c.rl matches JST.c.rl:102 and nothing else; CLJT, PRLT and RBT carry regex literals of their own shape and are not this bug.
  • Sweeping every tracked .js in ///bee, mark/html.js is the only file that fails today — the bug is rare, not harmless: one punctuation class kills a whole page.
  • test/TOK01.c JSTBasicTest already pins five regex cases and JSTFileTest a whole-file repro, so the shape of the fix's test is fixed too.

Goals

A regex literal's character class is part of the literal, so a / inside it ends nothing.

  • /[,./]/g, /["#$%&'()*+,./:;<=>?@[\\\]^{|}~!]/g and friends lex as ONE G` token.
  • dogtok ~/src/bee/mark/html.js returns OK and the page paints highlighted.
  • An escaped \] inside a class does not end it, and an escaped \/ outside one goes on working.
  • The five JSTBasicTest regex cases and JSTFileTest keep their answers — a division and a // comment must not become a regex.
  • The other three regex-carrying grammars are LOOKED AT and either cleared or ticketed, not silently assumed well.

Constraints

  • ///quickjab, dog/tok/JST.c.rl — the grammar is the source; JST.rl.c is regenerated with ragel -C JST.c.rl -o JST.rl.c -L and both are committed.
  • Repro first, as a case in dog/test/TOK01.c; no other test edited.
  • Ragel scanners take the LONGEST match, so the class branch must not let a regex swallow a // comment or an unterminated line.
  • No JS parser state: the rule stays the approximation its own comment admits ("true regex detection needs parser state") — this widens the BODY, nothing else.

WIP

Design decisions

  1. The body gains a CLASS BRANCH and nothing else: rxcls consumes [...] whole (escapes inside it included), rxbody alternates it with an escape and a plain byte. No parser state, so the rule stays the approximation its own comment admits.
  2. RULED not to widen this to Perl and Ruby in the same change: RBT HAS the same bug (measured), PRLT does not trip on the same input, and neither has a repro in a tree we serve — they get their own ticket, or none.

Blockers and bummers

  • RBT (Ruby) carries the same rule shape and the same bug: dogtok on a file holding x = /[/"]/ answers RBTBAD. Left alone here — no repro in a served tree, and Ruby's literal has quirks of its own.
  • PRLT (Perl) has the same shape (m/.../, s/.../.../) but did NOT trip on the equivalent input; unproven either way, not claimed fixed.
  • CLJT is CLEARED, not fixed: a Clojure regex is #"...", delimited by quotes, so a / inside it was never a terminator.
