RULING (gritzko, 2026-08-04): status never restamps (membership only, STATUS-011 stands); the restamp belongs to the verbs that already paid for the content test — unknown timestamp → test (maybe write) → stamp. POST-029 made post stamp every file it UNDIRTIES; this ticket is the remaining class: files post's pre-commit classify content-HASHED (mtime off the stamp-set → wtEqBase read+sha, shared/classify.js:546) and confirmed CLEAN. They were never dirty, so the BE-011 loop (verbs/post/post.js:961-974) never touches them — the verdict is discarded and EVERY later be status re-hashes them. Measured: be status in be/ opens ~780 tracked files per run. Their content is in the committed tree exactly like the posted paths', so stamping them to the same assigned post row ts makes the identical truth claim BE-011 already makes. Siblings: POST-029, GET-059 (get's half of the same ruling).

Input

Context

  • The knowledge exists and is dropped: classify's ok bucket is count-only (classify.js:10-12 — "clean tracked files would flood the output"), so post never learns WHICH paths were content-confirmed vs stamp-confirmed.
  • Two sub-classes inside ok, only ONE gets stamped: 1. content-confirmed ok (the hash ran because the mtime was off the stamp-set) → STAMP to the assigned post row ts. 2. stamp-set-confirmed ok (wtlogReader.has(mtime) hit, no read) → LEAVE — it already carries a truthful stamp; restamping shifts provenance for no gain (the PUT.mkd:27 principle).
  • The BE-011 loop is the pattern to extend, not replace: post row appended first, ulog.append returns the ASSIGNED ts, mtimes set to that (POST-029's row-before-stamp discipline, same ts across parent + folded subs via ctx.now).

Goals

After any post, every tracked file whose cleanliness was content-confirmed during that run carries a stamp-set mtime; the next status does zero content reads on the whole committed tree.

  • Repro-first: tree with clean tracked files at randomized (off-stamp-set) mtimes → post (commit-all and selective both) → assert those files' mtimes ∈ the wtlog stamp-set AND next status does zero content reads (test/post/restamp/run.sh + .stampchk.js is the pattern; extend or sibling it).
  • Sub posts (fold-decide): the folded sub's content-confirmed-clean files covered the same way, one ctx.now.

Constraints

  • A still-dirty file must NEVER be stamped (POST-029 constraint stands).
  • An already-stamped file must NOT be restamped — content-confirmed paths only.
  • classify surfaces the content-confirmed-ok path list behind an opt (the JAB-018 opts.listing precedent) — status byte-parity stays intact, status itself remains a strict reader (never a writer; the DIS-023 ban binds STATUS, not post).
  • Row-before-stamp ordering; mtime == an assigned wtlog row ts, never a resampled now.
  • Minimal diff: verbs/post/post.js + shared/classify.js (the opt) + shared/stage.js only if the helper moves there; no other verbs.

WIP

Design decisions

  • The opt is classifyMerge({ wantConfirmed: true }) → an extra confirmed: [path,…] on the result, next to the existing wantClean (the JAB-018 listing precedent). It is a pure ADD: rows/counts are untouched and the field is undefined when the opt is off, so status (which never asks) is byte-identical and stays a strict reader.
  • confirmed is fed from EXACTLY the two sites where the hash actually ran and came back equal: the unpatched leg !stamped && wtEqBase(...) (classify.js:546) and the patched leg wSha === b.sha (classify.js:521). The stamp-set leg (wtlogReader.has(mtime) hit) is deliberately NOT listed — it already carries a truthful stamp and a restamp would only shift provenance (PUT.mkd:27). Nothing dirty can ever enter the list: it is built inside the ok branch only.
  • The conduit is verbs/post/fold-decide.js (post's OWN decide module, not another verb): it turns the opt on and passes m.confirmed out as dres.confirmed. post.js then has a 3-line sibling loop right after the BE-011 add loop, using the SAME rowTs — the ts ulog.append ASSIGNED to the post row, never a resampled now.
  • Truth claim: a content-confirmed clean file is emitted as a keep decision, i.e. its baseline blob rides into the new commit verbatim — identical to an add's bytes-in-the-tree claim BE-011 already stamps on. So the same row ts is the correct stamp for both.
  • Sub posts need no threading: postOne runs per repo and each repo's own classify → own confirmed → own assigned row ts, all off the ONE ctx.now POST-029 established. The G class of the test pins it (the sub's get-materialised helper.c is clean-and-unstamped by construction — get stamps nothing, GET-049).
  • Not touched: shared/stage.js (no helper moved), verbs/put/put.js (its bare-put restamp is its own PUT-004 ground), and the pre-post quad snapshot's second classify (same wt state, so dres.confirmed already covers its paths).
