POST-030: bare jab post on a worktree track throws "no changes since base" instead of advancing the track

HIGH

Incident 2026-07-17, work/PUT-010 (clean wt, 93 ok, ahead 2 on its ///be/ track): bare jab post dies with JS exception: no changes since base. Per POST §Summary item 1, a bare post NEVER commits — it advances the TRACK; for a worktree track row (//X////X) that means a get-style merge of cur's tip into the target's files, then FF the target's base. The error is the COMMIT path's no-changes refusal, so bare post mis-dispatches to commit mode (or the wt-track advance leg is unimplemented in JS) exactly when there is nothing to commit and everything to push.

Design decisions

  • patchTheirs consumed-filter: skip a theirs reachable from cur.
  • Reachability = dag.isAncestor — the divergence view's own walk.
  • Explicit post //B was already correct; bare dispatch was not.
  • Conflict keeps get's GETCONF refusal; target base never moves.

Root cause and fix (2026-07-17, work/BRO-030 working tree)

The ` ? refuse never came from the parent's ///be/ advance: bare post fans into MOUNTED SUBS first (postSubs pre-order), and a clean sub's message-less postOne hit advanceTrack on its SELF-referential submount track (//WT/sub#…, DIS-072) → selfWorktree=true → the POST-026 fall-through bare-advanced the sub's empty-named trunk, which diverges → advanceBranch:326 threw and aborted the (FF-able) parent advance. The _sub` guard for exactly this was set (post.js:726) but never read.

  • Fix 1: a _sub message-less non-narrow postOne returns instead of bare-advancing its self-ref track; the gitlink bump still rides postSubs' own tip compare.
  • Fix 2 (the just-ff ruling): advanceWorktree gains a bareTrack arg — bare-track: dirty target REFUSES ("uncommitted changes"), clean target FFs via a clean checkout; explicit post //X unchanged.
