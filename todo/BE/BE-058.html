Now

Three view-side spots hide failure from the user, found in the 2026-07-24 house-cleaning sweep. The pager launch discards bad-arg errors into an empty viewport, spot's historic search treats an unresolvable ?ref as zero matches, and type/size/tree throw bare C-style codes with no plain-words line — all contradicting the errors-in-plain-words ruling (DIS-079 tracks the same disease for wt-less read verbs; this ticket is the in-view arm).

Input

Context

  • be/views/bro/bro.js:166 broRun pager branch: catch (e) { /* a bad spell just contributes nothing */ } — a typo'd path at jab bro <arg> yields a silent empty viewport, while the same spell typed at the : bar reports err: ... via _runSpell.
  • be/views/spot/search.js:197 walkRef: try { sha = r.resolveHex(...) } catch (e) {} then if (!sha) return; — bad ?ref/?branch emits nothing, exit 0, indistinguishable from no matches; every other bad input there logs a hint and throws (SPOTNOBODY/SPOTNOEXT/SPOTBADPAT).
  • be/views/type/type.js:95,100 throw "TYPENONE"; size.js:144,149 "SIZENONE"; tree.js:130,141-147,194 "TREENONE"/"TREEFAIL" — bare codes, no io.log line. Siblings todo.js:404 and work.js:795 do it right: one plain line, then throw.

Goals

  • Every bad CLI arg produces one plain-words line naming the arg; empty viewport / empty output no longer doubles as an error channel.
  • spot's bad-?ref path joins its siblings: hint + throw.

Constraints

  • Repro per site first (/meta/work §3); pager site needs the pty-click path, not a unit probe.
  • In-pager launch errors go to this.message, not stderr noise.
