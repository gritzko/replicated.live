Method: a /tmp COPY of the quickjab tree (`/tmp/BE066/quickjab-instr, cmake+ninja Release, -DQJPROF), engine patched in TWO places — js_clone_shape arms a flag and forces ctx->interrupt_counter = 1 so the JS stack is captured at the very next safe point, and add_property's clone branch logs <prop_count of the cloned shape>:<key being added>. THE FINDING: the two metrics disagree, and only one of them is what the profile pays. A clone memcpys the shape and dups ONE ATOM PER PROPERTY, so a clone of a 2,000-key dict costs 1,000x a clone of a 2-key row. Weighted by that work (245.6 M property copies per run) the churn has ONE site:

| site (work-weighted, % of the 245.6 M property copies) | % | |-----------------------------------------------------------------------|-------| | shared/cache.js armDir:155 <- arm:233/224 <- rev <- todo/status | 99.59 | | shared/metaidx.js sweep:456 <- find <- snapshot | 0.16 | | shared/store.js walk/readTree/readRecord + classify push (all rows) | 0.24 |

WHY: S.spot / S.wdOf / S.armed / S.seen are four plain objects taking the SAME 20.8 k absolute dir keys in the SAME order. A shape is cloned only when it is SHARED (ref_count != 1) and the next key is not yet a known transition — four dicts in lockstep hit exactly that on EVERY insert, so each insert copies the whole k-property shape: O(n^2), 245 M property copies and 1.0 M minor faults per frame. Nothing to do with key-set variation.

By CLONE CALLS (the naive metric, 519,992 — each one nearly free, but they carry a malloc + gc-list + shape-hash link):

| site (call-weighted) | % | |-------------------------------------------------------------------------|------| | shared/store.js locate/readRecord/getObject rows (3 x 24.9 k) | 14.4 | | shared/store.js readTree {mode,name,sha} | 13.1 | | git.tree C leaf {mode,nameStart,nameEnd,sha,nextOff} (quickjab/pack.c)| 13.1 | | io.lstat/readdir C row {size,mode,kind,mtime,atime} (quickjab/io.c) | 9.8 | | shared/classify.js wtScan {ts,kind,full} | 9.4 | | shared/classify.js push rows (ok/mod) | 9.0 | | shared/classify.js base/theirs {sha,kind,mode} | 9.0 | | shared/store.js readTreeRecursive {path,mode,sha,kind} | 6.3 | | tail: regex match objects (engine), todo/metaidx view rows | ~16 |

Design decisions

  • The ticket's premise ("varying key order / varying sets / deletes") is MEASURABLY WRONG for quickjs: {a,b} vs {b,a} vs {a,b}+delete all cost the SAME one clone per object (micro, 100 k objects each). What quickjs charges is (1) one clone per multi-key object at any site whose prefix shapes are not held alive, and (2) the O(n^2) above when two dicts share a key chain. So classify's 12 push literals were NOT unified into one 15-key undefined-filled row: it buys nothing the two pins below do not, and it would cost the bucket semantics their readability (hard constraint).
  • cache.js: the five dicts become Map. That is the fix for 99.6% of the work, and Map is what jab's own fsw bundle already uses for wd->dir.
  • store.js/classify.js: shared/util/shape.js pin(keys) holds one live object per PREFIX of a hot literal's key order, which keeps every transition findable in the engine's shape table — the literals stay exactly where they are, no row factory. Measured -3.7% on the first frame ON TOP of the Map fix, and it also makes the rows SHARE one shape (one inline cache on JSC too). Micro (200 k 10-key rows): 276 ms -> 117 ms, clones 200,089 -> 99.
  • Why a pin is needed at all: quickjs caches shape transitions globally, but a ref_count == 1 hashed shape is MUTATED IN PLACE, which unlinks the intermediate — so the next object at the same literal re-clones from the empty shape forever.
  • pin keeps its chains in a module-level KEPT that the exported function reads: a caller's const PIN_X = ... is NOT captured by any inner function, so both engines drop it and the pins die (measured: without KEPT the clone count did not move at all).
  • Two pins name a C-built shape (git.tree's leaf, io.lstat's row) — documented JS-028/JS-021 contracts, pinned from be/ JS. No C edited. If those C layouts change the pin silently stops helping; it can never be wrong.

Consumer hazards (grepped before touching anything)

  • The five cache dicts are PRIVATE to cache.js — no .spot/wdOf/dirOf/armed/seen reader anywhere else in be/. The only enumerations were for (const k in S.spot) in bumpRoot and the two stats() counters; both rewritten (.keys(), .size).
  • dirOf keys are NUMBERS (fsw.records builds wd via dv.getInt32; armDir gates on typeof wd === "number"), so Map's no-stringify keying cannot collide or miss — and jab's fsw bundle already keys wd with a Map.
  • The pins never touch a real object, so no in/hasOwnProperty/Object.keys/JSON behaviour can change. Grepped anyway: be/ has ZERO "x" in row / hasOwnProperty tests; Object.keys/for..in run only over path-keyed dicts, never over classify rows; JSON.stringify only over strings (spell.js).
