17 modules grab a FUNCTION off a module at load time — const wtpath = require("../core/discover.js").wtpath; — instead of holding the module object and calling discover.wtpath(). CODE-028 puts core/discover.js and core/resolve_hash.js into load cycles cured by Object.assign(module.exports, {…}), which fills the exports object at the END of the body. A property grabbed while the target is mid-load therefore captures undefined and stays undefined for the process. NOTHING IS BROKEN TODAY: none of the 17 sits in discover/resolve_hash's own 11-module load chain. The guard is accidental, and the failure is silent.

Input

Context

Found auditing CODE-028's cycle cures 2026-08-04; verified by walking the top-level require graph of the CODE-028 worktree.

  • 12 sites grab discover.wtpath, 5 grab resolve_hash.resolve_hash — both targets are cycle members after CODE-028.
  • core/recurse.js:29, shared/cache.js:42, shared/checkout.js:25, shared/classify.js:54, shared/gitmodules.js:12, shared/stage.js:36, shared/subs.js:40 — .wtpath.
  • views/list/list.js:24, views/spot/search.js:30, verbs/post/fold-commit.js:34, verbs/post/fold-decide.js:37 — .wtpath.
  • verbs/get/get.js:41, verbs/head/head.js:36, verbs/patch/patch.js:42, verbs/post/post.js:38, views/cat/cat.js:17, views/tree/tree.js:37 — .resolve_hash.
  • The accidental guard: discover+resolve_hash load only branch, ingest, memidx, store, ulog, util/path, util/sha, util/stats, wtlog — no extractor among them.
  • The day any of those nine gains a require of gitmodules/cache/classify/recurse, all 17 go undefined with no error at load.

Goals

No module captures a cycle member's PROPERTY at load time; the shape is enforced, not remembered.

  • The 17 sites hold the module object and call the member at CALL time.
  • A check refuses a new top-level require(X).prop whose X is reachable in a require cycle.
  • The check is a TEST, not a habit: CODE-028's cures are invisible at the call site and this trap will be re-laid otherwise.

Constraints

Pure refactor, same as CODE-028: no behaviour change, no output bytes, no module identity change.

  • Do not re-introduce in-body require() — CODE-028 ruled that out; this is the OTHER half of the same shape.
  • The extra property lookup per call is not a concern (the callers are already per-path).
  • The 18 property-grab sites whose target is NOT a cycle member are out of scope unless the check flags them.

WIP

Design decisions

  • Cure: const discover = require("../core/discover.js"); + discover.wtpath(…) — what discover/resolve_hash's own cycle partners already do, and why they survive.
  • A local alias assigned INSIDE a function (const wtpath = discover.wtpath;) is fine — by then the exports object is filled.
  • The check belongs where the cycle detector lives; a cycle is not an error, a property grab ACROSS one is.
  • NOT an identity bug: cache[abs] is inserted before eval, so every require(X) for one resolved X already returns ONE object; it is EMPTY at that instant, and a property grab copies the empty slot.
  • The invariant: a cycle member FILLS module.exports, never REPLACES it — then identity is stable from byte one and holding the object is always safe.
  • A replacing member hands out DIFFERENT objects at different moments mid-cycle ({} before the line, the fn after); that is why CODE-028 had to move module.exports = get; above the fetchleg require.
  • Rejected: publishing exports at the TOP of the body — function declarations hoist, but resolve_hash.js:125 const workRoot = under("work"), todoRoot…, metaRoot… are load-time consts and would publish undefined, silently.
  • Rejected: a Proxy forwarding property reads until the fill — it breaks typeof/in and makes an honest undefined indistinguishable from a not-yet-filled one.
