Design decisions

  1. The reps walk gets a bound of its own, REP_CAP (2^21), apart from WALK_CAP: it stops at the FRONTIER of the revs found, so the bound is a brake and not the rule. Only a commit the walk EXPANDS spends it, and past it the queue is still read for revs: a bite costs depth, never a rev already in hand.
  2. A bite is io.log'd and left on the result as capped, so the empty-seed fold in index/weave.js:203:KB is never silent again.
  3. parentsOf memoises its CPAR rows per index handle (a WeakMap), so one diff walks the commit dag once for every path it folds.
  4. repsOf answers the MAXIMAL revs it found, not every one: a rev another found rev descends from already rides in that one's closure, so it stands for nothing of its own. On linux that is 345 -> 28 reps for i915_drv.c, 4045 -> 107 for MAINTAINERS. CODE-068 plans the same reduction inside floorRev; with this one in repsOf, that half of CODE-068 has nothing left to do.

Blockers and bummers

  • The complete walk for a path deleted 417743 commits ago costs 8.1 s and 673 MB RSS on ~/src/linux, paid once per diff (the next two paths cost 2.3 s and 1.1 s off the memo). That is the price of an answer where there was none at all, and REP_CAP is the one constant to turn if the trade is wrong.
  • view/status.js:223:vX only NOTES its cap: ahead/behind still truncate at WALK_CAP, since a full ancestor set is what the divergence algorithm itself wants — its own ticket, not this.
