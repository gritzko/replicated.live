QJAB-006: zero-copy views and stashed pointers outlive their mmap

A leaf hands JavaScript a no-copy Uint8Array that aliases a C-owned mmap (JABCBytesNoCopy with a NULL freer), or stashes raw run/memtable pointers in a static cursor — and nothing invalidates either when the mapping is later munmap'd by close/drop/put. The JS view (or the next cursor step) then reads unmapped or reused address space: a segfault at best, a cross-allocation info leak at worst. Contrast abc.close (cont.c:436) which deliberately transfer()-detaches its views so a stale read yields empty — the pup/idx run views skip that step. This is the lifetime twin of the re-entrancy bug QJAB-005; here no valueOf is needed, only a retained reference across a close.

Input

Context

  • JABCBytesNoCopy (arg.c:84) wraps caller memory with a caller-supplied freer; the pup/idx run leaves pass NULL, so the ArrayBuffer never owns or tracks the mmap it points at.
  • DOGPupClose / DROP / ThinTail FILEUnMap the run mappings; the memtable sync/collapse on _put reallocates DATA.
  • abc.close (cont.c:436) shows the intended mitigation: detach live views before freeing their backing.

Goals

A JS view or cursor can never dereference a mapping the handle has already released. Either the view is copy-backed, or close/drop detaches every live view first.

  • let v = idx.run(0); idx.close(); v[0] reads empty/throws, never unmapped memory.
  • idx.seek(k); idx.put(x); idx.next() cannot walk freed run pointers.

Constraints

  • Copying a whole run may be too costly for the audit path; prefer the detach-on-close route where the view must stay zero-copy.
  • Keep the per-handle cursor model; the fix is invalidation, not redesign.

WIP

Design decisions

  • Track live no-copy views per handle (or per Pup) and JS_DetachArrayBuffer them in close/drop, mirroring abc.close.
  • Cursor pointers (pup.c:456) must be re-derived in _next, or marked stale by any mutating leaf on the same handle.
  • Landed shape: the pupslot owns ONE ArrayBuffer per run index (pupview view[HIT_MAX_RUNS]) and every _run call mints a fresh Uint8Array over it, so JABCPupUnview detaches the whole family at once — no per-call list to grow, and the run cap bounds it. The slot also carries an epoch: JABCPupMoved (detach + bump) runs BEFORE every leaf that can unmap or move rows (open/put/commit/drop/close), and _next re-cuts the cursor from the live sources whenever the epoch moved under it.
  • The cursor keeps its own bound (last row pulled, exclusive) so a re-cut resumes exactly where the pull stood — the entries are derived state.
