QJAB-008: HASH leaves accept non-power-of-two / zero capacity -> OOB

Now
OPEN
Sev
HIGH

///quickjab

The _hash_<lane>_put/get/del leaves take any typed array, compute cap = bytes/esz (hash.c:78 JABCLaneArr) with NO check that cap is a nonzero power of two, then hand {bb, bb+cap} to abc HASH*. abc maps a key to a slot with a bitmask, ndx = hash & (LMASK = len-1) (HASHx.h:24, HASHx.h:100), and the fast HASHPut path has no sane() guard. So cap == 0 gives LMASK = SIZE_MAX and ndx = hash, a near-arbitrary OOB write at base + hash*esz (the key picks hash; mix64 is a bijection); a non-power-of-two cap (e.g. 100) lets the 16-wide line probe reach ~12 elements past the end. It is reachable through the NORMAL API: cont.c bytes() (cont.c:415) sizes a HASH region as slots*esz with no power-of-two rounding, so abc.ram('HASHu64', 100) already builds a corrupting table. The leaf is the trust boundary and must reject bad cap.

Input

Context

  • HASHx.h:4 states the contract: "the hash-table length MUST be a power of 2 … a non-power-of-2 length silently corrupts the table and may infinite- loop the probe." The C core trusts it; nothing enforces it at the boundary.
  • HASHPut (HASHx.h:100) masks with LMASK = len-1 before any bounds check; HASHscan's sane(... 0==($len&MASK)) is only on the Get/Del path.
  • cont.c bytes() (cont.c:415) does not round HASH slots up to a power of two, so the blessed abc.ram/abc.mmap path is affected, not just the raw underscore leaves.

Goals

A HASH table backed by a zero-length or non-power-of-two region is refused before any slot is addressed.

  • abc._hash_u64_put(new BigUint64Array(0), 5n) throws, never writes.
  • abc.ram('HASHu64', 100) either rounds to 128 or throws — never a silently-corrupting table.

Constraints

  • Reject at the leaf (the trust boundary), even if cont.c is also fixed to round — belt and suspenders.
  • No behavior change for a correct power-of-two, zeroed region.

WIP

Design decisions

  • Add cap == 0 || (cap & (cap-1)) rejection in JABCLaneArr (or each hash leaf) with a plain-words throw.
  • Round HASH slots up to a power of two in cont.c bytes() so the normal constructors cannot produce a bad size.

TODOs

  • hash.c (hash.c:78 and the put/get/del triple hash.c:96…hash.c:129): reject cap==0 || (cap & (cap-1)) before building {bb, bb+cap}.
  • cont.c bytes() (cont.c:415): round HASH-family slots up to a power of two (HEAP/LOG families keep their sizing).
  • Confirm abc.over/abc.mmap paths also land on a validated cap.
  • Repro test FIRST: empty and 100-slot BigUint64Array through _hash_u64_put under ASan, assert throw not OOB; then the fix.
  • Note: HEAP leaves (heap.c) are already safe (explicit n>=cap bounds, no masking) — no change there.

Blockers and bummers

  • Rounding up changes the byte size of a HASH file/region; check the mmap book on-disk layout tolerates the rounded capacity.
