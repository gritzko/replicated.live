jhttp_bytes (http.c:100) copies each JS string — method, uri, version, status, reason, and every header name/value — verbatim into the spell scratch (JS_ToCStringLen is length-exact, so embedded control bytes survive), and HTTPutf8Feed emits them as name: value\r\n with no validation. A field carrying a raw \r\n therefore injects arbitrary header lines or a second message into the composed head: classic HTTP request/response splitting. It is exploitable wherever any composed field derives from remote or otherwise untrusted input (a proxy forwarding a peer's header value, a reflected status reason). The lexer leg QJAB-004 is fine; this is the compose leg only.

Input

Context

  • http.c:100 jhttp_bytes: each component string is fed straight into the txt scratch, no scan for CR/LF/NUL/controls.
  • http.c:128 jhttp_slots: header name/value pairs go the same way.
  • HTTPutf8Feed frames them as name: value\r\n + terminating CRLF CRLF; a value's own \r\n closes the head early / adds lines.

Goals

A composed head cannot contain header/line-injection bytes from a field value.

  • A header value or reason with \r, \n, or a NUL is rejected (or the control bytes stripped) before it reaches the wire.
  • Well-formed heads compose byte-identically to today (drain->feed->drain round trip from QJAB-004 still holds).

Constraints

  • Decide reject-vs-sanitize with gritzko (API freeze rule); reject with a plain-words throw is the safer default.
  • Keep it in the compose path; do not touch the ragel drain leg.

WIP

Design decisions

  • Validate each field in jhttp_bytes/jhttp_slots against the RFC 7230 token/field-value grammar (no CR, LF, NUL; controls per field type).
  • Reason-phrase and header-value share the "no CTL except HTAB" rule; method and header-name are stricter tokens.
