BEE-029

bee has no StrictMark renderer: the http view's RENDER table (http.js:314:rq) maps only md and rst, so a .mkd page — the wiki's and the tickets' own dialect — serves as painted source, per LITE-037's deliberate punt; and the bee mark verb (view/mark.js:35:lc) cheats, feeding .mkd to the CommonMark parser, which mis-renders everything StrictMark adds — Key: value meta pairs, [Page] shortcut links, the 4-space blockquote. The real renderer exists in C as beagle/mark (MKDT block grammar + inline lexer driven from MARK.c, the MARKE ragel escaper), and quickjab already ships the same dog/tok/MKDT machinery — its tokens are what paint .mkd source today. So bee's mark/ wants a StrictMark parser of its own that feeds the ONE existing emitter (LITE-037: only the parser differs per dialect), driving MKDT tokens from JS as beagle/mark drives them from C, or porting the block rules where the hunk exposes too little.

Input

Context

The wiki, the tickets and the meta pages are all StrictMark .mkd; over http they read as highlighted source while .md neighbors get rendered pages, and bee mark output silently disagrees with beagle/mark on the same bytes.

  • http://localhost:8888/bee/cat/wiki/Page.mkd serves painted source; .md beside it serves a rendered page.
  • bee mark page.mkd renders Now: OPEN meta pairs as prose and [Page] shortcuts as dead brackets (CommonMark has neither).
  • beagle/mark/README.mkd and beagle/mark/INDEX.md document the C renderer's pipeline: MKDT classifies blocks and lexes inlines, mark only emits.
  • Spec: beagle-journal/wiki/StrictMark.mkd; the dialect's grammar lives in quickjab/dog/tok/MKDT.h + MKDTB.rl.c, already linked into bee's runtime.

Goals

A .mkd page renders as StrictMark on both render paths, through one new parser and the existing emitter.

  • mark/ gains a StrictMark parse entry producing the same AST/event shape mark/blocks.js + mark/inlines.js hand to mark/html.js, so the emitter, page shell and link door stay ONE set.
  • RENDER (http.js:314:rq) gains mkd, and view/mark.js:35:lc routes .mkd to the new parser instead of the CommonMark stand-in; .md/.rst render byte-identically to today.
  • StrictMark specifics render right: Key: value meta pairs, [Page]/[/pocket/Page] shortcut links resolved through the SAME door as .md links, *strong*/_emph_ per spec.
  • The YAML preamble rule stays where BEE-029 put it: entry via mark/front.js.
  • Painted .mkd source stays reachable (the pager still opens it); only the default cat page flips to rendered.

WIP

Design decisions

  • Survey settled it as (a): tok.parse(bytes, "mkd") (quickjab/tok.c:88) hands JS the WHOLE MKDTLexer stream, and its tokens TILE the source — every block quad is an R (indent, quote, - , ## , ` ` , ---, [x]:), a meta key is a T, a span delimiter a G, a fence body an H. That is beagle/mark's own input, so mark/strict.js drives tokens as MARK.c` drives them and never rescans bytes.
  • What did NOT reach JS: MKDTBlock's regions and the MKDTmark* inquiries are C-only. The lexer still delimits the marker quad; only "which shape is this quad" is ported (markList/markHeading/markFence/markRule), a 40-line mirror of MKDT.c:186:GT-225.
  • Emitter is not forked: parse builds mark/node.js nodes, mark/html.js emits, so pageHref, the autolink hook and the page shell work for all three dialects unchanged. A meta pair rides a custom_block <dl class="meta">, the shape mark/rst.js:260:jG already uses for definition lists.
  • Entry stays mark/front.js per BEE-029: the new front.strictToHtml is the same preamble strip plus the StrictMark parse, so no caller spells the pair.
  • An undefined shortcut becomes the implicit ./Page.mkd link (StrictMark:46) only when the brackets hold a NAME — no space, more than one char. The journal writes its TODOs 5 chars wide ( -[v] ), which is off MKDTB's 4-char marker grammar, so [v]/[ ] reach the inline lexer as shortcuts; unguarded they would mint v.mkd links.
  • A fence body is DEDENTED by the fence's own indent plus one quad (StrictMark:113 "the code is indented four chars"). beagle/mark keeps the gutter (MARK.c:592), which shows as four leading spaces on every code line.
