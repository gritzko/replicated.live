be's bug, learned once already: a top-repo-only tally under-reports every mount — bare add/rm descend every mounted sub, so the button that stages //WT acts on the subs and its count MUST say so (be views/todo/todo.js:507, SUBS-044). bee flags gitlinks in the quad but never descends them (view/status.js gitlink rows), and fork.js already gives every gitlink its own worktree — so a ticket wt routinely HAS dirty subs the frame would hide. Two halves, one ticket: the counts fold, and the staging verbs descend, or either alone lies.

Input

Context

  • A sub's tallies are a pure function of its own subtree — a boundary whose rev stands still replays from the memo instead of re-classifying (be's STATUS-019 discipline; bee has index/cache.js rev already).
  • The parent records a sub as ONE gitlink; after staging inside the sub AND committing there, the parent needs git add <subpath> to bump the gitlink — until then the parent's chg count keeps the dirty-sub row.
  • The COMMIT frame stays TOP-repo: ahbeh is the wt's own line, not its subs' (be todo.js:515).

Goals

  • wtstat.stat(root) un/st tallies fold every gitlink sub, depth-first, .gitmodules order, memoized per sub rev; an unreadable sub tallies nothing, never errors the row.
  • Bare add / add + / rm (BEE-036) descend: run the class command via git -C <sub> in each dirty sub, then git add -- <subpath> in the parent where the sub's HEAD moved.
  • Explicit-path forms do NOT descend — a named file is one repo's file.

Constraints

  • One walk spine for fold and verbs — never a second mount scanner (be's rule).
  • git via argv spawn; worktree and build of the assignee's own; no main-tree edit, no commit (work).
  • RED first over a nested fixture (parent + 2 subs, one clean); no existing test case edited. Comments per comment, BEE-040 on the change.

  • Sub discovery reads the gitlink rows the status model already holds plus .gitmodules paths — no readdir probing.

Outcome

  • ONE spine, index/subs.js (39 lines, new): mounts(root) reads the gitlinks off HEAD's tree (index.js:232 submodulePaths) and answers { path, wt, sha, head, live } — no readdir probe, no second scanner. sha vs head IS the bump test; an unreadable root or mount yields fewer mounts, never a throw.
  • COUNTS: view/wtstat.js +25 — foldSubs/addFold fold every live mount depth-first into the BEE-039 split, one status read per mount, memoized on the sub's own cache.rev (be's STATUS-019), grandchildren before the parent. The COMMIT frame is untouched: ahbeh stays the top repo's line.
  • VERBS: stage.js — the class became a { list, stage } pair parametrised on the repo, so sweep spends the very same pair in every mount. Bare verbs descend depth-first; the parent gitlink is bumped only where the recorded sha and the sub's HEAD differ. ONE report line, its count summed tree-wide; the explicit-path form still goes straight to some and never descends.
  • DEVIATION (needed, else the fold double-counts): view/status.js +11 — a declared gitlink is now a REPO BOUNDARY for scanUntracked (a sub's files were showing as the PARENT's untracked rows), and an uninitialised mount reads as unchanged via its recorded sha, as status.js:107 always claimed. add's lister took --ignore-submodules=all, since a dirty gitlink is the sweep's business, not the class's.
  • RED-first test/subfold/ (run.sh 190 + fold.js 122): parent ⊃ { s1 ⊃ g, s2 clean } plus a clone for the dead-mount case — 38 checks over the folded sums, the silent clean sub, the replay, the descent, the two bump timings and the pinned explicit path. Failed on the unmodified tree (add 2 staged, sub files counted as parent untracked); now green.
  • ctest -j16 -R '^JSRC': 49/49, the 48 that were green plus JSRCsubfold. Commit line: BEE-040: fold and stage the gitlink subs
