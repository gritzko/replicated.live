bee http has no front page: / is a 301 to the repo the server was started in (http.js:843:gw), and the registry ($HOME/.config/bee/repos, BEE-001) is never shown anywhere but as URL prefixes. This ticket adds ONE view, welcome: the mount table as a HIERARCHICAL list — a top-level repo, then its submodules indented under it — every entry carrying the worktree path, the origin URI and the first paragraph of its README. It is a view like list or todo: one hunk per top-level repo, so the pager and --plain paint it as a stacked list and the HTML page gets a welcome class to flow the same hunks into two columns on a wide viewport. Ruled 2026-09-08: topic BEE, submodules in, hierarchy over a flat card grid, README = first paragraph, upstream = remote.origin.url only.

Input

Context

  • index/mount.js:47:pN list() is the mount table: [{ name, root, prefix, own, top, dup }] in registry order, a line inside another line already a SUB with a prefix; index/subs.js mounts(root) lists the gitlinks a root carries (view/status.js:340:7E subRows is the recursive consumer).
  • http.js:843:gw: a repo-less URL is a 301 to /<home>/…; http.js:505:gw mounted(st) is the table the server answers for, the started-in repo included even when unregistered.
  • index/refs.js:85:PA branchConf is the one <gitdir>/config reader, a [section]/key = value line walk; it takes branch.<b> only. remote.<x>.url needs the same walk over a [remote "origin"] section.
  • view/mark.js:31:IP toHtmlOf picks the parser per ext (mark/front.js strictToHtml for .mkd, toHtml for .md); mark/front.js drops a YAML preamble. view/todo.js:20:i4 reads a ticket HEAD off one capped read (CAP), the shape an excerpt read wants.
  • render/html.js:330:bI hunkHtml paints a hunk as div.hunk > pre.body; render/html.js:444:bI page(title, body, tail) is the shell; blob/style.css:7:Qk .hunk, :15 the B elastic row. A B-tagged line is a flex row in HTML and an ellipsized field in the pager (BEE-030).
  • main.js:238:Za SIDE verbs write lines; a VIEW verb goes through the door (door.js) and the ONE mode pick (main.js:299:Za), so ansi/plain/html come free.

Goals

  • bee welcome (no args): one hunk per top-level mount, in registry order, the started-in repo included as bee http includes it; the hunk's rows: <name> (an F row clicking to list of that repo), <root path>, origin <url> (blank row omitted), the README paragraph as plain rows, then each submodule as the same block indented two spaces, recursively, in .gitmodules order.
  • README: the first of README.mkd, README.md, README.markdown, README.rst, README at the entry's root; the first PARAGRAPH after the title heading (a YAML preamble and a Key: value meta block skipped), capped at 4 lines of 64, an unreadable or absent README omitting the rows, never an error.
  • origin: remote.origin.url off <gitdir>/config through a remoteUrl(gitdir, name) beside branchConf in index/refs.js; no other remote, no tracked-branch logic.
  • bee http: / serves welcome instead of the 301; /welcome and /<repo>/welcome answer the same page; the sub's 301 (http.js:848:gw) stays. The page body wears class="welcome", blob/style.css flows .welcome .hunk into two columns above ~90em (columns:2 or grid, one rule), one column below.
  • ROUTE row, door.js verb row, INDEXES.mkd/README usage line; test/welcome/run.sh over a fixture registry of two repos with a submodule, checking the plain listing, the hierarchy, the origin and README rows, and the / page's welcome class.

Constraints

  • Existing pages paint byte-identical; / is the ONE routing change. Suite green, no test edits (work).
  • No manual parsing: .gitmodules, config and the README go through the readers that exist (index/subs.js, index/refs.js, mark/); no regex over a README.
  • A registry line that is no repo (dir gone, .git missing) lists its name and path with a ? row and no more; the view never throws on one entry.
  • Comment budgets per comment; worktree per bee; no commits, no push.

WIP

Design decisions

  • Hierarchy over cards (ruled 2026-09-08): a submodule is addressed through its parent (BEE-003 ruling 5), so it sits UNDER the parent in the listing rather than as a peer card; the hunk stays one per top-level repo, which is what the CSS flows into columns.
  • The excerpt is text, not HTML: the parser's AST gives the first paragraph's inline text, so the pager, plain and html read the same bytes; links inside it ride as F tokens the door already resolves.
  • Origin only, as ruled; a . or absent remote omits the row rather than printing a local ref.
