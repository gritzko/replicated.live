bee sym u8bFeed prints bare repo-qualified paths, 48 of them. Wanted (gritzko, 2026-08-24): HUNKS — every USE shown as the mention line with about one line of context before and after, the way bee's other views emit hunks, on all three surfaces. The index stores no positions by design (BEE-063): the verb OPENS each suspect and finds the mentions itself, which is the suspects contract's "precision comes from opening" made visible — a false suspect simply prints nothing and drops out.

Input

Context

  • Recognition stays the tokenizer's: the mentions are the tokens the MINT gate accepted (tags S/N/C, text equal VERBATIM), so the verb and the index can never disagree about what a mention is.
  • The hunk machinery exists: every view emits { banner, body } hunks through the one renderer stack (CLI/pager/HTML), and the pager/HTML side paints tokens and mints file:line links already.

Goals

  • EVERY HIT IS A HUNK, the canonical one (Hunk, dog/HUNK.h:34): uri = the ADDRESS <path>:<line>, text = the RAW window bytes (the mention line, one context line either side), toks = the file's own lexer tags with the mention marked. Two hunks MERGE when their windows OVERLAP. The neutral file-fragment verb (HUNK_VERB_HUNK): a search hit is a code snippet.
  • The address prints as the hunk banner, light-yellow background — the one banner drawer (THEME_BANNER, HUNKu8sFeedBanner) — at render time off the uri.
  • NO presentation in the view: no -- separators, no line numbers in the text, no gutter bytes — renderers and the pager derive the banner, the target and the paint from uri + toks.
  • The bytes are the WORKTREE file when it is present (that is the file the reader opens), else the tip blob the index named.
  • The BEE-063 cap discipline extends: past the cap the repo prints its suspect count and the "narrow the query" line instead of hunks.
  • A bare-paths mode stays for scripting (--plain or a flag), one path per line as today.
  • FILTTER ARGS (gritzko, 2026-08-24): bee sym u8sFeed .c and bee sym u8sFeed dog/abc/ — any further non-flag arg narrows the answer. A word starting with . and holding no / is an EXTENSION filter; anything else is a PATH filter, segment-aligned (dog/abc/ matches .../dog/abc/DNS.h, never .../catalog/abc...); both may combine. A path filter can PRUNE the descent through the val's seg0..seg3 hashlets before any tree is read; the extension filters at naming time.
  • Tests: window fusion, false-suspect dropout, worktree-over-blob choice, the cap.

Constraints

  • No regex over raw bytes and no second recognizer — the DOG-034 lexer through the one shared gate.
  • One emitter for the three surfaces, no per-surface forks.
  • A binary or over-cap blob prints its path bare, never a garbage hunk.
