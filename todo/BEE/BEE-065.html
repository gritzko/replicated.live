Ruling (gritzko, 2026-08-24): on ANY use an index has to be updated; the repo may be read-only, but .git/be is always rw. Today the registry fan-out does the opposite — every foreign index opens READ-ONLY and NONE is brought up (the BEE-002 suspects-contract rule), so a cold lane answers silence. Evidence: after the BEE-063 format bump every registered repo read as absent and bee sym u8bFeed answered ONE file where 48 exist; a hand-run bee index per repo fixed it. The silence is systematic, not a bump artifact: a newly registered repo, or one whose commits land outside bee (plain git push), answers stale until someone walks over and indexes it by hand.

Input

Context

  • The mark discipline makes bring-up-on-use cheap: an unmoved tip no-ops off one mark read (INDEXES.mkd, the lazy contract), so the cost is first-query-only — exactly the case that bit us.
  • DOG-046 accounted for parallel index readers/writers, so two queries bringing up the same repo concurrently should be survivable — verify, do not assume.
  • The read-only sites today: the SYM fan-out (index/lindex.js symForeign), the LINK suspects fan-out (same file), the hook's foreign target resolution (index/hook.js:177:foreignTarget), the BEE-003 partial-path fan-out.

Goals

  • A QUERY's fan-out brings each registered repo's index up before reading: the same passes bee index runs (commit walk, lindex, symdex), track: false, writing only <gitdir>/be.
  • A repo that cannot be brought up (unreadable gitdir, be/ unwritable after all) degrades to today's read-only open, then to silence — never an error.
  • A COLD huge repo (///linux) makes the verb say what it is doing — one progress line per repo being walked — rather than hang mute.
  • INDEXES.mkd follows: "opened READ-ONLY and NONE is brought up" goes; the suspects contract keeps its precision half, loses its staleness half.
  • Test: a registered repo with a cold (or swept-format) lane answers a bee sym / lindex query correctly on the FIRST query, and the second query no-ops off the mark.

Constraints

  • The HOOK's mid-commit foreign opens are the latency-sensitive case: walking a cold foreign history inside someone's git commit may not be acceptable — decide in review whether the hook keeps read-only opens or gets a bounded bring-up.
  • Worktrees stay untouched: only <gitdir>/be is written, never the tree, never refs.
