The index watermark says "this tip and all under it are indexed", so bringUp returns at index/index.js:1038 without reading a row. When a MARK lands for a tip whose CPAR rows did NOT, that ref is dead: every reader walks from a commit the index does not know, and no re-run can heal it because the mark is what stops the re-run. Hit 2026-08-23 by gritzko, who clicked ✓ on the board to commit in quickjab-QJAB-012; git stayed perfectly healthy throughout while log, status, wts and the web board each reported a different wrong answer.

Input

Context

Five symptoms, ONE cause. git status -sb said ## QJAB-012...main [ahead 1] and git status --porcelain was EMPTY the whole time.

  • bee log printed ONE row (the tip) where git walks 32.
  • bee todo / bee wts rowed [ ≡ 1⇄31 ] — 1 ahead, 31 behind, 31 being the WHOLE of main: no commit read as shared.
  • bee status rowed all 48 top-level paths as new, dog among them ("all of dog newly added" in the web iface), footer 48 upstream, 3 head.
  • bee index answered up to date: refs/heads/QJAB-012 12ab5ba2 and did nothing — the short-circuit, reporting success.
  • The index probe is decisive (probe.js, via index/dag.js):
12ab5ba2  indexed=false  parents=[]        <- the tip the MARK names
3b323920  indexed=true   parents=["26094…"] <- its parent, indexed fine
  • So the MARK for refs/heads/QJAB-012 names 12ab5ba, and 12ab5ba carries no CPAR row. Mark written, rows not.
  • index/index.js:1088 writes the MARK LAST for exactly this reason, so the window is not a plain mid-run kill — see Design decisions.

Goals

  • A MARK may never outlive the rows it vouches for; if it can, a reader must detect it rather than trust it.
  • bringUp short-circuits only when the tip really is indexed: dag.isIndexed(ix, hlOfSha(tip)) beside the mark test is one seek.
  • A repro test: stamp a MARK for an unindexed tip, then assert log, status and the ahead/behind pair still read the true history.
  • A poisoned ref must be recoverable WITHOUT discarding the index.

Constraints

  • No recovery exists today. markSet (index/index.js:423) unions every row on the key, so a bumped mark cannot retract an old one.
  • The bare-tip route is refused USING the broken index: bee log 12ab5ba in that worktree says "not in the history of refs/heads/QJAB-012". Circular.
  • Restarting bee http cannot help — the poison is on disk.
  • Only fix found: delete <gitdir>/be and re-index the whole repo.

WIP

Design decisions

The git commit the ✓ act runs (sync.js:92) touches no index, so the bad MARK was stamped by the NEXT bring-up in that worktree — the resident bee http re-reading the board right after the act.

  • SUSPECT, unproven: the resident server's index handle. DOG-032's bulk open is durable: false (index/index.js:328).
  • SUSPECT, unproven: sweep(o.dir) in openIndex retiring the shard that carried the CPAR rows while the MARK survived in another.
  • Evidence fits a shard loss: at 07:47 the dir held a 16791-byte shard dated 16:54 the day before, plus a 1584-byte one — too small to hold the revs of the commits made between (22:17, 07:45, 07:46).
  • A resident writer racing a CLI writer over one shard dir is the shape to test first; bee http is the only long-lived index holder.

Blockers and bummers

  • The git-visible state was never wrong, so nothing warns: the tree looks healthy and only bee's own views lie.

Outcome

Not fixed. The live tree was REPAIRED, not healed: <gitdir>/be moved aside and rebuilt, which restored every reader.

  • After the rebuild: board [ ≡ +1 ], bee log 32 rows, bee status 3 rows, footer 3 head.
  • Every quickjab worktree now agrees with git — main 31/31, QJAB-007 29/29, QJAB-008 31/31, QJAB-008-2 30/30, QJAB-012 32/32.
  • The rebuild also pulled the other trees' log horizon forward; they had been stopping at a135f3e0 (Fri 21).
  • be-index-0747 and be-index-0750 reproduce the state; probe.js is the four-line index query that proves it.
