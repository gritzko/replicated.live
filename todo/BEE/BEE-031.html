The index never learns about the commit that is being made: the planted hook is pre-commit alone, and its idx.bringUp(ctx, ix, {track: false}) (index/hook.js:393:_m) runs while HEAD is still the PARENT, so each commit indexes the one before it and the files it adds get their FSEG rows only at the next commit. Nothing closes that gap from the reading side either — the fan-out over registered repos opens every foreign lane READ-ONLY and never brings it up (door.js:302), so a page whose ticket code lives in another repo stays plain text until someone runs bee index THERE. The read-only half of BEE-002 is about the GIT side (gritzko, 2026-08-20): another repo's objects, refs and worktree are untouchable, while .git/be is bee's OWN derived lane and is bee's to write. Both halves are wanted: a post-commit hook so a commit indexes itself, and a bring-up on open so a reader is never the last to know.

Goals

A commit indexes itself, and a read refreshes the lane it reads.

  • bee install plants post-commit beside pre-commit, composing with a hook already there, idempotent, and says so in its report line (merge.js:200:rE).
  • The post-commit pass brings the repo's own lane up to the commit just made; git ignores its exit status, so it can never block or undo a commit.
  • It is QUIET on success — a summary line per commit is noise; failures still reach stderr.
  • The fan-out leg (door.js:327) brings a foreign lane up instead of opening it read-only, so a ticket code resolves the moment its page is committed elsewhere.
  • A repo with NO lane keeps its answer as today (anchored and boundary legs only): a browse must not turn into a first full index of someone's kernel clone.

Constraints

  • The GIT side of a foreign repo stays untouched — objects, refs, worktree, config; only .git/be, bee's own derived lane, is written (door.js:302 must say which half is which).
  • A foreign lane that cannot be written (permissions, read-only fs) falls back to the read-only open, never throws a page away.
  • Worktree and build of the assignee's own; no main-tree edit, no commit (work).
  • RED first: the repro fails on the base build; no existing test case edited.
  • Comments per comment: 8/4/2 lines, BEE-031 on the change.

WIP

Design decisions

  • Two legs, one ticket: they are the same gap seen from the writing and the reading side, and either alone still leaves a stale lane behind.
  • index/hook.js owns the plant (plant() at :479 today), so the post-commit line is planted by the same code and carries its own MARK comment.
  • The planted line runs the index verb rather than a new one: bee index is already the lazy incremental pass, all three of them (BEE-007, BEE-024).
  • An up-to-date bring-up costs one watermark check and no walk (index/index.js:879:cn), so the on-open leg is paid for only when someone actually committed.
  • Existing installs need bee install re-run to get the new hook; the verb is idempotent and reports installed when it wrote.

Blockers and bummers

  • A browse now WRITES derived rows into another repo's .git/be; the lane is derived and rm -rf-able, but a shared or root-owned clone still exercises the read-only fallback.
  • A post-commit index on a huge repo pays the tip-blob link scan per commit; if that bites, the hook wants a cheaper "commit walk only" mode, which is its own ticket.
