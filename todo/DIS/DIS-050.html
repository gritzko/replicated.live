DIS-050: be put ?<40hex> set-cur dispatch is inconsistent

Now
DONE

be put ?<40hex> (set cur's branch OUTRIGHT to a bare full sha — the reflog escape hatch, PUT) dispatches two different ways depending on what the sha resolves to: when it resolves to cur's OWN branch tip, native falls through PUTStage→PUTNONE (exit 206, NO ref row written) instead of writing the ref. Surfaced porting JS-049; no corruption either way (the resulting refs were byte-identical), but the canonical dispatch is unpinned, so the JS port can't claim byte-parity for this form. Issues.

Input

Context

  • Found in JS-049 probing: with the <40hex> resolving to cur's (trunk) tip, native be put ?<sha> → PUTStage→PUTNONE (206, no write); the JS set-path → exit 0 (writes a post ?#<sha> row). Refs ended byte-identical regardless.
  • The three primary ref forms (?br, ?br#sha, ?#sha) ARE parity-verified; only the bare-?<40hex> set-cur form is ambiguous (sniff/SNIFF.exe.c:~1021 dispatch + sniff/PUT.c::PUTSetBranch :1195).

Goals

  • Decide + document the canonical ?<40hex> dispatch: when it SETS the ref outright vs when it legitimately falls to PUTNONE (sha == cur tip = no-op?).
  • Make native + the JS-049 bin/put.js agree on it, then add a parity case.

Constraints

  • Spec/impl decision first (Verbs/PUT are the spec); a one-char-of-behavior change, but it must not regress the verified ?br/?br#sha/?#sha forms.

WIP

Design decisions

  • Repro corrected the premise: native does NOT hit PUTNONE — it resolves to PUTSetBranch (exit 0) in both cases. The real divergence is the idempotency dedup in REFSAppendVerb (keeper/REFS.c:146): a set to the value the ref already holds writes NO row (keeps .be/refs bit-identical across repeats).
  • RULING (Option 2): align JS to native's dedup — bin/put.js::refSet no-ops when resolveRef(branch) == sha. Preserves the shared bit-identity invariant (vs Option 1 "always write", which would special-case PUT and break it).

TODOs

  • Pin the canonical behavior; align native PUT dispatch + bin/put.js; add a ?<40hex> parity case to test/js/put/.

Blockers and bummers

  • Low priority — no data loss; the form is rare. Tracks the JS-049 residual.

Outcome

  • Landed 2ea762c2: bin/put.js::refSet dedups (no-op when the ref already resolves to sha), byte-parity with native; repro test/js/put/ref-set-sha (both sub-cases + an explicit refs-row count so CASE A can't pass vacuously). The put-harness isolation gap the repro needed was fixed in JS-050 (reanchor).
  • RESOLVED — delisted in the 2026-06-25 triage: landed 2ea762c2 (matches this ticket's own Outcome hash); put.js refSet dedup (be/verbs/put/put.js), repro test/put/ref-set-sha.
