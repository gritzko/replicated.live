DIS-077: put ?<40hex> writes a ref keyed off cur's query — a sha-named branch when detached, silently TRUNK after DIS-075; RULED: put #hex sets the BASE

Now: OPEN Sev: MED

put ?<40hex> (put.js:656, the set-cur arm) is a REF WRITE: it calls store.set(k.shard, branch, sha) (put.js:110) with the ref key taken from cur's recorded query (curQuery, put.js:697 — "Only curQuery is needed — it pins ?<40hex>'s target branch"). So its target is whatever cur happens to track, which breaks at both ends. On a DETACHED wt the old record was ?<sha> — the query held the sha, so the key WAS a 40-hex string and put ?<newsha> minted a ref literally named <40hex>. After DIS-075 the detached record is #<sha> (query ABSENT), so curQuery reads "" and the SAME command silently advances TRUNK while the wt is detached. RULED 2026-07-15 (gritzko): "put #hex should probably set the base commit to that hex" — the sha belongs in the FRAGMENT (DIS-071 law #3: the fragment carries the base), never in the query. Found by the DIS-075 worker, which refused to pick a side (correctly — both behaviors are wrong).

Input

Context

The set-cur arm conflates two motions: moving the worktree's base, and writing a branch ref.

  • put.js:656 dispatches the arm: hasQ && !hasPath && !hasAuth && !hasFrag && isFullSha(q) — a bare full sha in the QUERY.
  • put.js:697 reads curQuery = (cur && cur.query) || "" and pins the ref key to it; put.js:110 store.set(k.shard, branch, sha) writes it.
  • Detached, pre-DIS-075: curQuery was the 40-hex sha → a ref keyed <40hex> (a sha-named branch, addressable by nothing).
  • Detached, post-DIS-075: the record is #<sha>, curQuery is "" → the same spell moves TRUNK, unasked, while detached.
  • DIS-050 (DONE) already found this arm's dispatch inconsistent; it fixed the dispatch, not the target-key rule.
  • A sha in the QUERY contradicts DIS-071 law #1 anyway: a bare hash is not a branch/remote/worktree, so it is not a trackable thing.

Goals

Split the two motions along the URI grammar: fragment = base, query = ref.

  • put #<hex> sets the worktree's BASE commit to that hex (RULED) — a wt-local motion, no ref touched.
  • put ?<branch> keeps writing the branch ref (put.js:96,110) — unchanged.
  • Decide put ?<40hex>'s fate: an error naming the #hex form, or a detach — it must NOT silently key a ref off cur.
  • Repro each: detached wt + put #<hex> moves the base only; put ?<40hex> never mints a sha-named ref nor moves trunk.

Constraints

The base is a recorded row, not a ref — and #hex must not become a third resolver.

  • Resolution through be/core ONLY ([resolve-hash-mandatory]): the hex resolves via the existing store.resolveHexAny/resolve_hash, never a hand-rolled lookup.
  • Setting the base means recording a row that the ONE attach reader (wtlog.attachedBranch, DIS-059) reads back correctly — do not invent a shape; follow DIS-075's records.
  • Read-compat: old ?<40hex>-keyed refs may exist in stores; resolveRef must keep reading them. No migration.
  • Repro-first; minimal — the set-cur arm only.
