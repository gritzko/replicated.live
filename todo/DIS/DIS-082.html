DIS-082: append-only weave — body + tok32-pair index, tombs as entries

Now: OPEN

-- design settled with gritzko, 2026-07-30

Today's 'W' blob is rewritten whole on every fold (dog/WEAVE.h:100) because DELETION MUTATES stored tokens: a later commit sets rm and pushes into 'M', so earlier bytes cannot be final. Make deletion its own index entry and the BODY becomes strictly append-only — a commit's text bytes are final forever, the small parent-sorted INDEX merges per commit, and the merge-time renumbering that DIS-081 exists to fix never happens. The shape: a BODY of text pieces, an INDEX of tok32 pairs carrying the CT parent/child relation, and a per-commit table of bounds. 'X'/'K'/'I'/'M'/'C'/'A' collapse into three streams.

Input

Context

The current six-column layout pays for in-place tombstones.

  • WEAVENext re-emits the entire weave per fold, so writes are O(history); WEAVEMerge then permutes commits[] and remaps every ins/rms.
  • 'A' is a u64 anchor hash per token — on word tokens the anchor column can outweigh the text it anchors.
  • 'M' needs the tok32 custom bit as a multi-remover escape, spending the one spare bit in the token.
  • Literature fit: run collapsing (YATA/Yjs), columnar delta encoding (Automerge), local indices instead of global ids (Chronofold).

Goals

An append-only format where a commit's bytes are final once written.

  • Deletion is an appended index entry, never a mutation of the deleted token.
  • Body offsets serve as identity, causal rank, and blame key at once — one number replaces 'C', 'I' and 'A'.
  • Scope is a bound plus a small exclusion list, not a bitmap over commits.
  • Free the tok32 bits the diff class/color set needs, without touching the syntax tag.

Constraints

Weaves are derived data; git is the oplog.

  • A weave is a local materialization, rebuildable from the commit DAG — different builds never meet, so offsets MAY be arrival-local.
  • RENDERED MERGE BYTES must agree across clones, so the RGA sibling tie-break reads the canonical hash, NEVER a body offset.
  • Sources over MAX_SOURCE_SIZE (4 MB) stay blobs, untokenised — big generated files are not diffed and do not enter a weave.
  • The 24-bit tok32 offset caps the BODY at 16 MiB, matching MAX_SOURCE_MARKED_UP; the exposure is churn over history, not file size.

WIP

Streams

Three streams replace the six columns; TLV tags below are PROPOSALS, pin them before coding. The BODY is append-only, the INDEX is SORTED — not the same property.

  • BODY 'B': u8, the text of every token ever inserted, live and dead, in append order; a commit appends only the tokens it inserts. Strictly append-only.
  • INDEX 'E': tokv32 entries — a declared PAIR of tok32 (parent, child), 64 bits — sorted by parent offset then by sibling order.
  • tokv32 is a real ABC record type with fixed bit layout, so the index is a tokv32cs/tokv32b and sorting/search go through the typed slice API, not pointer work.
  • The index is PARENT-SORTED and is RE-SORTED after each commit: a commit's new entries merge into the sorted array, so the index is rewritten per commit.
  • APPEND-ONLY IS A PROPERTY OF THE BODY ALONE. The index is not append-only, not "append-only except at forks" — it is a sorted array maintained by merge.
  • That is still the win: the body is the larger stream and never moves, and merging a small sorted batch is one sequential pass, not WEAVENext's whole-weave re-emit.
  • COMMITS 'C': per commit, the record (id, body range [start,end), L, K, P, ignore-set); append order is build order.
  • IGNORE 'G': pool of ignored-commit-INDEX lists referenced by 'C' records, so a commit record stays fixed-size; consecutive indices may compress to ranges — compression, not correctness.
  • Nothing else is stored per token: no anchor hash, no inserter index, no remover list, no side bits.

Entry shapes

The child tok32's TAG field carries the entry TYPE; a syntax tag means an ordinary token, a reserved letter means tomb or terminator.

  • INSERT: parent = body offset of the left-neighbour token (the CT parent), child = this token, tag = syntax tag, offset = its first body byte.
  • TOMB: parent = body offset of the target token, child tag = the tomb letter, child offset = the DELETING commit's INDEX in 'C'.
  • TERMINATOR: closes one inserted chain, flagged by its own letter; parent = the chain's last token, child offset = termpos, the chain's end.
  • A tomb carries NO body bytes, so its offset field names a commit, not a token — a body range cannot: pure-delete commits append nothing, so consecutive ones share identical [start,end).
  • Multiple removers are multiple tomb children of one target; the 'M' count+N escape and the custom bit both disappear.
  • Token LENGTH is implicit inside a chain — the next entry's offset — and explicit only at the terminator, so chains cost no length column.
  • A chain costs one entry per token plus one terminator; parent-sorted and offset-sorted coincide within a chain, which is why the implicit length works.
  • A FORK (two children of one parent) breaks that coincidence, which is exactly what the terminator escape covers.

Reading

Document order is a preorder walk of the CT; visibility is a bound plus an exclusion.

  • ORDER: DFS from the root — emit a token, then recurse into its children in RGA sibling order: causally related siblings descendant-first; the TIE-BREAK for CONCURRENT siblings is canonical commit hash DESC, then ordinal ASC within a commit.
  • Siblings are contiguous in 'E' because it is parent-sorted, so the walk is a scan plus a binary search per fork, never a hash lookup.
  • ANCESTRY is already stored: u precedes v iff idx(u) < K_v and u not in ignore(v) — the sibling compare is two lookups, no topo rank is ever recomputed.
  • VISIBLE to commit c: offset < L_c and the inserting commit not in c's ignore-set; a TOMB is visible iff its deleting commit's index is under K_c and not ignored.
  • For linear history the ignore-set is empty, so visibility is one integer compare — the weavescope bitmap is not needed at all.
  • L_c is the body length at c, K_c the commit-index cut; P_c is the MATERIALIZED length at c — an allocation size for the render and an integrity check on the walk.
  • BLAME: binary search a token's body offset in the 'C' range table (empty pure-delete ranges never cover an offset); why: needs no per-token inserter at all.
  • MERGE: nothing splices, nothing shifts, no table is renumbered — the merge record only carries its own cut K and ignore-set.
  • The general rule: ignore(c) = [0, K_c) \ closure(parents(c)), closure supplied by the caller (graf owns the DAG, the shape WEAVEScope takes today); two-parent intuition: a commit hides only when NEITHER parent saw it.

Design decisions

Settled in conversation; the rest is Blockers.

  • Deletion-as-entry is the load-bearing change — everything append-only follows from it, and nothing else in the format forces a rewrite.
  • Offsets are arrival-local and that is ACCEPTED, because weaves are never exchanged; only the sibling tie-break must be canonical.
  • Freed tok32 bits: custom (no multi-remover escape) plus side (a tomb entry IS the removal) — 3 bits, enough for the diff class/color set.
  • The syntax tag does not move; it stays in the child tok32 exactly as today.
  • Declare tokv32 (a tok32 pair, 64-bit fixed layout) so the index gets the typed slice/buffer family rather than ad-hoc pair handling.
  • Index maintenance is a per-commit MERGE: sort the commit's new entries, merge into the parent-sorted array, one sequential pass. Not an overflow region, not sort-at-load.

Blockers and bummers

  • JS cannot reach a tomb's DELETING commit: cfoldtok is {off,end,tag,alive} and _cfold_blame names inserters only, so why:'s ?a..b surfaced-delete wash approximates with the range HEAD; exact colouring needs a tomb accessor (e.g. the iterator yielding the tomb's commit index, or the freed class bits).
  • LEFT-ORIGIN ONLY: the index stores a parent, not a right origin — Fugue (Weidner/Kleppmann 2023) shows left-only anchoring interleaves concurrent runs; the ORDERING question stays open.
  • The Dirty interior-insertion test needs no stored right origin: the right neighbour at insert time is DERIVABLE (next token visible to the inserting commit) — but the derivation must be specified.
  • Fork frequency is unmeasured: chains carry the format's efficiency, so if real edits fork often the terminator escape stops being an escape.
  • The ignore-set is assumed small; nothing has measured it on real branchy history yet.
