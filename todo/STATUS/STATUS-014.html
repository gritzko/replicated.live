STATUS-014: quad status recursion into subs — pin-derived columns

Now
OPEN

Input

Context

The quad reporter (/wiki/Status, /todo/BRO/BRO-030) recurses mounted subs by opening each sub's OWN wtlog track — the DIS-072 self-referential pin — so a sub's track column mostly mirrors its base and the recursed hunk shows little beyond wt dirt. RULING (gritzko 2026-07-17): a recursed sub's quad columns derive from the PARENT's trees, not the sub's self-ref row.

Goals

Teach status recursion the pin-derived model, so a sub's quad reads consistently with the parent's gitlink row:

  • base column: the BASE PIN — the gitlink sha at the sub's path in the parent's base tree.
  • track column: the TRACK PIN — the gitlink sha at the sub's path in the parent's track tip tree.
  • wt column: figured from the FILES — the sub's own classify (unchanged).
  • patch column: figured from the sub's WTLOG — its in-scope patch rows (unchanged).
  • root = LCA(track pin, base pin) in the sub's shard; commit rows = sub commits vs that root (an off-pin sub's own posts read .o..).

Constraints

  • The pins resolve through the existing quad model inputs (quadOf/quadModel already take explicit base/track) — inject, don't re-derive; RULE ZERO for any URI resolution.
  • Depth: a sub-of-sub takes its pins from ITS immediate parent's trees, recursively.
  • /wiki/Status needs a short Recursion section recording this once landed.

WIP

Design decisions

  • quadModel is already pure over { base, track, patches, wtRows } — the recursion only changes WHERE emitRepo gets base/track for a sub: read the two pins from the parent's already-open tree ULOGs (the gitlink rows), pass them down.
