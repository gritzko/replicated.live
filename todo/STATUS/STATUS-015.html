STATUS-015: status ?ref — status relative to a named ref, not the track

Now: OPEN

Input

Context

Ruling (gritzko 2026-07-18): when a ref is given as an arg, status compares the worktree against THAT ref instead of the tracked one — a relative status. Same query-slot family every verb speaks (?branch/?../?/?., DIS-054 resolution); status today always diffs against its track/base.

  • Use case: "what would land if I posted to ?X" / "how far is my wt from trunk" — status ? answers against the trunk without touching the track.
  • Composes with dir scoping (/todo/BRO/BRO-032): status ///be/verbs/ ?feat clips to the subtree AND compares to ?feat.

Goals

status [path] ?ref renders the usual rows with the comparison base swapped to the ref's tip tree.

  • ? trunk, ?. own branch, ?.. parent, ?name named — resolved by the ONE dot-path/branch codec (shared/branch.js), no status-local parsing.
  • Row verdicts (add/mod/del/unk, quad marks) computed wt-vs-ref-tree; the banner names the ref (///be/ ?feat: status-form) so bar and content agree.
  • No-arg behavior unchanged (tracked base); an unresolvable ref refuses with the standard hint, never falls back silently.

Constraints

  • Resolution via resolveRef/resolve_hash — no new ref grammar; classify keeps ONE comparison seam, the base tree is a parameter, not a fork of the walk.
  • Read-only: status ?ref must not touch REFS, the track row, or the wtlog.
  • pty + plain legs, per the standing verification rule.
