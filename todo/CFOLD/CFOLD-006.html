RULING (gritzko 2026-09-22): bee builds every merge weave the way be's patch does — the per-path commit DAG floored at the LCA, every path-changing commit on both sides folded under its own id, plus ONE de-facto blob from the fs folded as WT_SRC over ours' view; joined under one id and read with mergedLive. The inputs are always commit hashes plus the on-disk bytes, never three blobs. weave3 is the fast-forward corner case (get: old tip, new tip, edited file) and becomes a thin wrapper over that builder; the git merge driver takes its committed sides as hashes (HEAD, MERGE_HEAD, their base) and the fs blob, not %O %A %B temp files. patch and diff after a patch consider the whole LCA story, so the bytes patch writes and the washes diff paints come off one construction.

Goals

  • One builder in index/weave.js: weaveDiff fed the tips (ours HEAD, theirs) builds one weave off the REV index floored at their LCA; foldWt lands the fs blob as WT_SRC over ours' view; merge under one join id; mergedLive → { bytes, spans }.
  • patch (verb/patchwalk.js leaf) is be's mergeApply over that builder: ours = HEAD tip + on-disk bytes, theirs = the source tip, base = the LCA baseOf found; no blob triple.
  • diff on a path with patch.log rows in scope is be's expectedOf + three-layer fold: EXPECTED = HEAD ⊕ the in-scope theirs tips off the SAME builder, folded between base and wt; tokens carry the theirs bit.
  • 4 washes ported from be/view/theme.js:125 into render/theme.js, render/ansi.js cellAnsi, render/html.js; --plain byte-identical.
  • weave3(baseSha, theirsSha, wtBytes, path) is a thin wrapper over the builder: the two tips, the fs blob, same join and read; no fold chain of its own.
  • The merge driver resolves its committed sides to hashes — HEAD, MERGE_HEAD and their merge base in the repo it runs in, %P naming the path — and reads the fs blob; %O %A %B are not the inputs. Its write and exit contract (over %A, non-zero on spans) is unchanged.
  • The git merge-file fallback (verb/patchwalk.js:99:5l, merge.js:55:sQ) goes with it: an unweavable pair keeps ours and is a conflict, no <<<< anywhere.
  • RED first: a two-sided edit over a real history (commits on both sides above the LCA); assert patch's bytes equal the diff's EXPECTED ⊕ wt reading, --color shows 155/215 beside 157/217, the wrapper answers the same bytes as the builder for a ff pair, no fences.

WIP

Design decisions

  • The builder is index/weave.js weaveMerge(r, ix, path, tips, wtBytes, ext, floorChl) -> {bytes, spans} or null: weaveDiff (the buildDag twin off the REV index) folds the path's DAG, foldWt lands the fs blob as WT_SRC over tips[0]'s view, every view joins under JOIN_ID and mergedLive reads it. N tips STACK, one mergedLive group each (be expected.js:97).
  • The floor is a PARAMETER, not always the LCA. verb/patch.js baseOf already resolves three bases — the LCA of a line, a cherry's first parent, a re-run's prior head — and the weave must fold from THAT commit up, else a patch <sha> carries the whole line and a re-run doubles its own output (both measured RED on test/patch). weaveDiff grew floorChl; absent, the floor is still the tips' LCA, so every other caller is unmoved.
  • With an EXPLICIT floor, a tip holding no rev at or above it IS the floor — its committed view was already carried into the wt by the previous absorb. Folding its own blob back in (the old unrepresented-tip arm) spells a removal nobody made; that arm is now skipped when the floor is explicit.
  • diff's EXPECTED mirrors baseOf so the two come off ONE construction: a lone picked head row stands on that commit's first parent, anything else on the LCA. No new patch.log row was needed for it.
  • weave3(baseSha, theirsSha, wtBytes, path) opens the repo at io.cwd() itself (its callers hold no index) and is 6 lines over weaveMerge.
  • The driver learns theirs from io.environ(), not from MERGE_HEAD, which git has not written yet at driver time (Blockers); it brings the index up on that tip inside the driver, as verb/patch.js:148:zY does, since git may hand over a commit the index has never seen. The de-facto blob is %A's bytes — ours' content as git staged it, plus whatever the tree holds.
  • patch.log's scope() grew paths, the gate on the EXPECTED axis: with no patch row in scope diff opens no index and pays nothing (DIFF-016's rule).
  • Provenance rides tok32 bit 26, render/ansi.js cellAnsi(tag, pass, side, cls) picks the family, render/html.js a .patched class — --plain is byte-identical, asserted in test/cfold.

Blockers and bummers

  • WAS a blocker, now closed: git does NOT write MERGE_HEAD before it calls a merge driver (measured, git 2.52 — a probe driver's gitdir mid-merge held COMMIT_EDITMSG HEAD ORIG_HEAD config description hooks index index.lock info logs objects refs and no more). What git does hand over is one GITHEAD_<sha>=<label> per merge head. RULING (gritzko 2026-09-22): quickjab grew io.environ() (QJAB-016, io.c:809) and the driver scans it — ours is rev-parse HEAD, theirs is the one GITHEAD_ sha that is not ours, and none or several is refused in words (an octopus is not this driver's). Verified end to end: two branches editing different WORDS of one line, where stock git conflicts, now land clean through a real git merge.
  • A live mmap of %A handed straight to the writer is a SIGBUS: the truncating open pulls the mapping out from under it. fsBytes copies (merge.js:95:sQ).
