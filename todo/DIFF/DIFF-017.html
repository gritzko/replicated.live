DIFF-017: mid-line EQ runs break line-ification — glued indents and torn statements

Now: OPEN

A diff hunk where an EQ token run starts or ends mid-line renders inconsistently: a line whose only change is leading whitespace is emitted ONCE with both sides' indents concatenated (6 new spaces + 8 old spaces back to back), while an EQ run bracketed by changes on both sides is DUPLICATED into the rm and in rows with pale wash. Weave-order emission then tears statements apart: the new side's continuation line lands after the old side's closing brace, three rows from its opener. Found by gritzko 2026-07-29 reviewing jab diff //POST-035/verbs/post/post.js (trunk jab, pre-existing — not DIFF-016).

Input

Context

  • Repro: jab diff --color '//POST-035/verbs/post/post.js' | cat, the POST-035 conflict pre-flight hunk (~L878). Old: 3-line throw refuse(...refuse(named,\n"conflict marker...")); + }; new: 2-line throw refuse(...refuse(named, "conflict in...")); at one indent less.
  • Symptom 1: shared line throw refuse(named + " (--force overrides)", renders once as [bg194] [bg224] [bg49]throw refuse(... — both indent variants glued, a 14-space line matching neither side.
  • Symptom 2: row order comes out throw(shared) / old refuse(named, / old "conflict marker..." / old } / new refuse(named,...) — the new statement's tail is separated from its opener by the whole old block.
  • Symptom 3 (the inconsistency): the refuse ( named , EQ tokens are duplicated into BOTH rows wearing pale wash (bg224/bg194), while the throw line's EQ content single-emits on default bg — same shape, two renderings.

Goals

  1. One rule for EQ runs crossing line boundaries: a display row belongs to ONE side (or is fully EQ); a whitespace-only line change renders as rm-row + in-row (or one row with only the indent marked), never a glued chimera.
  2. Row grouping per change region: rm rows contiguous, then in rows — a statement's lines stay adjacent to their side, no old/new interleave inside one region.
  3. C HUNK.c and JS bro.js lockstep ([inline-vs-split-metric-max] discipline); row weights must not double-count duplicated EQ tokens.

Constraints

  • Fix in the emit walk / row builder (views/diff emitDiff consumption, view/bro.js; C twin beagle HUNK.c) — the weave itself is fine, this is line-ification.
  • Verify through the real UI path (pty render), plus --color | cat goldens ([verify-through-real-ui-path]).

WIP

Design decisions

  • DIAGNOSIS: symptom 3 is the CORRECT rendering (a split rm row = EQ pale salmon + RM strong; the in row its salad twin), symptom 1 is the odd one out. lineKind sent the indent-only line to K_MOD_INLINE (changed*4 < total: 8 changed bytes against 44 shared), and an INLINE row is PASS_NORMAL — nothing is hidden, so both indents paint back to back. Symptom 2 falls out of that: an inline row is a block BOUNDARY in walkHunk, so the opener left the change region and the new tail landed after the whole old block.
  • THE RULE (view/bro.js lineKind): an inline row carries BOTH sides, so it may only hold changes a reader can tell apart IN PLACE. A two-sided change is refused inline — and SPLITS into an rm row + an in row — when it
    • GLUES THE INDENTS: the segment's leading-whitespace run carries both IN and RM bytes (li.glue), or
    • IS INVISIBLE: every changed byte on both sides is whitespace (li.wsOnly).

    Otherwise the BRO-041 gate stands unchanged. So a row is one-sided or fully EQ wherever the two sides are not distinguishable inline; a symmetric VISIBLE swap (-[ ] -> -[x], test/diff/13) still renders as ONE inline row — that test is pinned by BRO-041 and may not be edited.

  • CHOSEN over "one row with only the indent marked": rm-row + in-row also cures symptom 2 (the split line rejoins its change region, so walkHunk emits old opener/old body/old } then new opener/new body — the new statement whole), while the single-marked-indent row would leave the tear in place.
  • classifyLines grew the two flags only: lead/leadIn/leadRm walk the segment's leading-whitespace run, nwIn/nwRm count VISIBLE changed bytes. No new pass, no extra allocation, lo/hi/inB/rmB/eqB/pIn/pRm/bnd untouched.
  • METRIC: unchanged and already correct — eqB is counted ONCE per segment in classifyLines, so an EQ run duplicated into the rm and in rows is not double-charged; row weight stays max(inB,rmB), total max + eqB ([inline-vs-split-metric-max], DIFF-016's patched-in extension intact).
  • DIFF-016's provenance is untouched: the wash FAMILY is picked by tokClasses (bit-26 runs), this ticket only decides WHICH ROW a byte lands on. Its three tests stay green with NO regold.
