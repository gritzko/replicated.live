DIFF-018: fold aligner spends rm+in on identical tokens — phantom doubled bracket

Now
OPEN

Same source as DIFF-017 (gritzko reviewing jab diff //POST-035/shared/wtlog.js#L328, 2026-07-29): old if (p && !seen.has(p)) { vs new if (p && !seen.has(p) && !acked.has(p)) { renders as …!acked.has(p))) — a green inserted ) glued to a red removed ). Each bracket IS a token (doghili confirms), but the wt-fold aligner anchored greedily: at the first mismatch (old ) vs new &&) it inserted the run INCLUDING its trailing ) and removed the old if-closer, instead of sliding the insertion boundary one token left and keeping the shared ) EQ. One needless edit pair of byte-identical tokens; the doubled bracket reads as a syntax error.

Input

Context

  • Repro: jab diff --color '//POST-035/shared/wtlog.js' | cat, the conflicts() hunk (~L336): row = EQ !seen.has(p) + green && !acked.has(p)) (bg194) + red ) (bg224) + EQ {.
  • The alignment happens where wt bytes are folded against the base weave (weave fold's token diff), not in the renderer — DIFF-017's row splitting can't fix a wrong weave: the rm/in pair is real in the fold, and the two )s get distinct weave ids permanently.
  • Minimal alignment exists (insert 8 tokens, remove 0) but the differ resyncs greedily past ambiguous repeated closers; no common-suffix trim, no slide heuristic. Line-level analog is git's indent/slider heuristic.

Goals

  1. The fold's token diff never pays rm+in for byte-identical tokens at an insertion/removal boundary: either common-prefix/suffix trimming inside the mismatch window, or a post-pass that slides edit-run boundaries across equal tokens (canonical position — prefer widening EQ; pick one, document).
  2. The wtlog.js shape renders as pure insertion: …!seen.has(p) EQ + green && !acked.has(p) + EQ ) {. Repeated-closer cases ()), }}, ]]) covered by tests.
  3. Determinism: same bytes → same fold on every replica (the slide rule must be canonical, no tie-break on anything positional-random).

Constraints

  • Fix at the fold/diff layer (shared/weave.js foldWt path or the token-diff it calls), NOT the renderer; DIFF-017's lineKind rule stays as is.
  • Beware stored weaves: already-folded commits keep their alignment — the fix changes only new folds; no rewriting history.
  • C twin: the dog-side weave/diff (beagle) has the same greedy anchor — record the exact fn for lockstep, C is read-only in the journal tree.
