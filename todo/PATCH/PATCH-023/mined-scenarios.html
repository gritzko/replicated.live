PATCH-023 attachment: merge scenarios mined from git's test suite

Corpus: ~/tmp/git/t (shallow clone, 2026-07-24), 22k lines of merge tests mined by 4 workers, 54 raw scenarios deduped to the 40 below. Each entry: source test, neutral topology, git's answer, predicted patch answer (SAME / DIFFERS / RULING = gritzko must decide first). Verdicts marked "impl-known" were resolved against be/verbs/patch/patch.js facts, not guessed.

A. Criss-cross / multi-base — the weave's home turf

Cases where snapshot 3-way needs virtual ancestors or gives arbitrary answers; the full-history weave has a definite one. Prime differential material.

  • A1 (t6401 criss-cross): two disjoint single-line edits threaded through a mutual-merge criss-cross, each line's newest write on the opposite tip → clean merge, newest value per line. git -s resolve FAILS here; recursive/ort pass. Predicted SAME — the canonical positive anchor. [H]
  • A2 (t6416 nested-conflict ladder): 3-deep criss-cross re-asserting one divergent appended line per side → git manufactures NESTED conflict markers (3 marker levels) from recursive virtual bases; the weave sees one left-vs-right divergence → single fence. DIFFERS, showcase. [H]
  • A3 (t6404 ambiguous bases): criss-cross lattice over TWO unrelated roots, file overwritten at every commit → git's own test says "fragile, relies on ambiguous merge-base resolution". Weave is deterministic. DIFFERS — pin the stable answer git cannot give. [H]
  • A4 (t6416 criss-cross mod/del): intermediates resolved a modify-vs-delete opposite ways, outer merge of the two → must fence mod/del, never auto-pick a side. Predicted SAME in outcome. [H]
  • A5 (t6427 no common ancestor): two orphan roots both add the same path → full-span add/add fence. RULING: fence labeling when no base side exists. [M]
  • A6 (t6430 identical empty bases): multiple merge bases all content-identical → clean no-op, no spurious refusal. SAME anchor. [M]

B. Dirty-worktree-as-ours — model divergences to pin

git refuses/aborts around dirty state; patch folds wt bytes in as ours (BE-010). Every case here pins that model against git's abort.

  • B1 (t6436 untracked in the way): both sides add path P, wt also holds an UNTRACKED P with distinct bytes → git aborts; patch folds/overwrites? Pin what writeLeaf does to untracked bytes. RULING. [H]
  • B2 (t6416 §4a dirty subset): theirs' change is a subset of ours', wt holds a third uncommitted rewrite → git leaves wt bytes untouched (merge reads committed trees only); patch weaves them as ours. RULING on expected fold/fence. [H]
  • B3 (t6415 dirty under retype): uncommitted edit on a/b/c/d while theirs retypes dir a/b into a symlink → git fails to protect; patch = mod/del-vs-retype fold. RULING. [H]
  • B4 (t3507 dirty cherry): cherry whose path the wt has uncommitted edits on → git refuses outright; patch proceeds, wt bytes fence against the picked change. Pin. [H]
  • B5 (t6424 unrelated dirty survives): dirty/extra files on paths the patch does not touch → byte+mtime identical after. SAME; folds into the PATCH-invariant "stamp only written files". [M]

C. Types, modes, binary — classifier collisions

The weave merges bytes per path; these cases collide at the type/mode/tree-shape level where bytes have no answer.

  • C1 (t6407/t6404 binary): both sides mutate the same binary blob → git refuses to content-merge binaries. Does patch detect binary or blindly token-weave NUL bytes into fences (corrupting)? RULING + guard; feeds PATCH-016's overflow arm. [H]
  • C2 (t6400/t6430 file-vs-dir): path is a blob on one side, a tree prefix on the other → git D/F-conflicts with ~rev sidecars. Patch per-path model can produce an un-materializable file+dir set. RULING on on-disk shape. [H]
  • C3 (t6400 letters): modify/delete + file→dir retype + a sibling that sorts BETWEEN letters and letters/file → multi-signal classifier/ordering stress. [H]
  • C4 (t6405 symlink-vs-file): same path symlink on one side, regular file on the other → type conflict; which type materializes? RULING. [H]
  • C5 (t6405/t6416 symlink targets): add/add and criss-cross modify/modify on a symlink's TARGET → is the target woven as bytes (fence inside a link target?) or atomic conflict? RULING. [H]
  • C6 (t6415 dir→symlink sibling): a/b becomes a symlink while sibling a/b-2 subtree must survive — prefix-aliasing regression bait for the classifier. [H]
  • C7 (t6411/t6416 exec bit): both add identical bytes, one +x; exec-only change propagation; criss-cross mode conflict (git itself expect-FAILs there) → does patch merge modes at all? RULING; extends exec-symlink which only covers adds. [M]
  • C8 (t6403 no-final-LF): both sides edit the unterminated last line → fence + no silently appended newline. [M]
  • C9 (t6403 moved function): C-file where a function is removed/added shifting repeated boilerplate → git's answer is diff-algorithm-dependent; does the RGA weave over-conflict on repeated tokens? [M]

D. No-rename-detection pins

patch has no rename detection: a git "rename" is per-path delete+add. Impl-known: BOTH mod/del arms keep the content side (modl, patch.js:147,152) — so no silent byte loss; the hazards are duplication, stranded paths, and dropped intent. Pin each loudly.

  • D1 (t6402 rename-vs-edit): ours edits A, theirs renames A→B (+edit) → git fuses both into B. Patch: A kept via modl with ours' edit (impl-known, content wins), B clean-added with theirs' → DIVERGENT DUPLICATION across two paths, no loss. Pin. [H]
  • D2 (t6422 rename/rename 1to2): A renamed to B by ours, to C by theirs → git conflicts; patch: A both-deleted clean, B and C both added CLEAN — git's conflict silently vanishes into two copies. Pin. [H]
  • D3 (t6423 dir-rename stranded adds): ours renames dir z/→y/, theirs adds z/d, z/e/f → git moves the adds into y/; patch leaves them stranded under the "deleted" z/. Pin verbatim landing. [H]
  • D4 (t6422 rename/rename 2to1): two files renamed onto one name, sources edited → git: one conflict; patch: THREE (add/add at target + modl at both sources). Noisier but safe. Pin. [M]
  • D5 (t6425 rename/delete): ours deletes A, theirs renames A→B → git conflicts; patch: A gone clean, B added clean — ours' delete INTENT silently overridden by resurrection at B. RULING. [M]
  • D6 (t6422 rename-target-vs-dir): rename target collides with a directory on the other side → same un-materializable set as C2. [M]
  • D7 (t6402/t6429 convergent renames): identical rename both sides converges clean (SAME anchor); re-adding the old name afterward yields a spurious mod/del fence git avoids. Pin both. [L]

E. Cherry-pick semantics

#sha: theirs=commit, fork=first parent, picked-header dedup. Root cherry refusal already in PATCH-017.

  • E1 (t3502 cherry a merge commit): git refuses without -m; patch has no -m — fork is unconditionally the FIRST parent, so it proceeds and absorbs the second-parent side. Pin (result tree == the merge commit's, git -m 1 equivalent). [H]
  • E2 (t3502 -m 2): picking the delta against the SECOND parent is inexpressible in patch. Document the conscious gap so it is never a silent wrong answer. [M]
  • E3 (t3505 already-applied-by-content): pick a commit whose change an unrelated commit already made → git stops ("now empty"); the weave folds to a silent no-op — but the picked-header dedup does NOT fire (different sha). RULING: silent vs notice; row written or not. [H]
  • E4 (t3507 conflicted-cherry leftover): the resting-state contract — fences + durable con rows, no CHERRY_PICK_HEAD/staging, next status/patch sees a coherent tree. Joins PATCH-020's con-row leg and PATCH-021's rerun-atop-fences ruling. [H]

F. Submodules

patch recurses gitlinks and stages nothing; git never descends.

  • F1 (t6438 gitlink-vs-blob): same path is a sub on one side, a regular file on the other → no per-token model applies. RULING: where the blob lands, how the con reads. [H]
  • F2 (t6437/t6416 divergent sub pins): both sides advance the same sub to divergent pins (incl. a criss-cross INSIDE the sub, and a no-common-sub-commit variant) → git leaves the gitlink unmerged; patch recurses and the sub-weave may merge CLEANLY (disjoint adds). RULING: how the merged sub state is recorded given patch stages nothing. [H]
  • F3 (t6438 interior files): incoming superproject add under a live sub's directory → the sub's own files must neither block nor be clobbered. [M]

G. Ancestor / no-op anchors
