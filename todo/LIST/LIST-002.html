bee list and the /<repo>/list/ page list the TREE AT THE REV, never the worktree, so a file that is not committed yet has no row at all; the view's own header says why (view/list.js:5:Zl, "there is no ignore machinery"). That is outdated: since STATUS-020 bee status walks untracked files through the gitignore chain (view/status.js::'function ignoStack', view/status.js::'function scanUntracked') and lists them as ...o rows. The list view must show them too, unless gitignored.

Input

Context

  • Repro (scratch repo, 2026-09-24): .gitignore = *.log; untracked.txt, noise.log, newdir/new.txt on disk. bee list prints .gitignore and a.txt only; bee status prints ...o newdir/new.txt and ...o untracked.txt.
  • test/list/run.sh asserts the old model outright: "an untracked file has no row (lite lists the tracked tree)"; be's own list had a new marker bucket (run.sh:16:05g).
  • Runtime for the tests: LITEJAB=~/src/quickjab/build-unbundled /bin/quickjab sh test/list/run.sh from the tree (jsrc -> .).

Goals

  • An untracked, not-ignored file in the listed dir is a row with the new marker, no commit summary; an untracked dir is a dir row (its files show when listed).
  • A gitignored file or dir has no row; .git never has.
  • ?<rev> listings stay the tree at that rev, no worktree rows.
  • run.sh flips its untracked check to expect the new row and adds an ignored file that must stay hidden.

Constraints

  • Reuse status.js's ignore chain and walk: export or lift them, no second gitignore reader and no manual glob parsing.
  • One readdir of the listed dir, not a subtree walk per row; the fused tree rows and their attribution stay byte-identical.
  • Repro-first per work; comment budgets per comment.

WIP

Design decisions

  • view/list.js::'function untrackedOf': one readdir of the listed dir, each name tested on status.js's exported ignoStack (info/exclude, root and ancestor .gitignores).
  • scanUntracked is not reused: it walks the whole subtree.
  • Untracked rows carry no sha, so they skip attribution and have no summary or age; new takes be's green slot W.
  • Rows merge in git tree order with the gitlink sort key; a ?<rev> listing never reads the worktree.
  • A staged, never committed file is new too (not in the tree).
