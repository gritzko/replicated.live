BRO-007: jab pager — collapse status-line hints to h: help, add a help: screen (shortcuts + URI schemes)

Now:
DONE

The jab/JS pager (be/views/bro/pager.js) ends its status line with a hardcoded hint blob (j/k space g/G : q) (_statusLine, :215) — noisy, partial (omits m / Enter / . # ? / / back), and it grows every time a key is added. Replace it with a single h: help hint, and bind h to open a HELP screen listing the pager shortcuts AND the URI schemes you can type at the : address bar. The screen fits the existing model as a help: URI/view: h runs the help: spell like any typed URI, so it PUSHES onto the view stack and -/BS backs out — no new pager state machine. Method: Issues.

Input

Context

  • Status line: _statusLine (be/views/bro/pager.js:200-218) appends a literal (j/k space g/G : q) after statusURI + pos. The other keys (m, Enter, . # ? /, -/BS back) are undocumented in the UI.
  • Keys: _keyScroll (:249-276) — q quit, j/k line, space/b page, g/G top/bottom, m mouse (BRO-005), : address bar (+ . # ? / pre-insert, JAB-030), Enter follow-row URI, -/BS/^H back (popView). h (0x68) is currently UNBOUND — free for help.
  • Spell / view-stack model: a typed URI runs via _runSpell (:298) → driveSpell → pushView (back-navigable stack, popView :108). So h → _runSpell("help:") reuses the whole path — the help screen is just another pushed view (- returns).
  • URI schemes = the registry's views (be/core/registry.js; views/<v>/<v>.js): blob, cat, commit, diff, grep, log, ls, lsr, refs, regex, sha1, size, spot, status, tree, type (+ bro). These are what a help: screen enumerates.
  • C bro has NO in-pager help (only a -h/--help CLI flag, bro/BRO.exe.c:106), so this is a jab-first feature; C parity is a follow-up, not a blocker.

Goals

  • The scroll-mode status line ends with exactly h: help (drop the (j/k space g/G : q) blob); statusURI#L + TOP/%/BOT position stay.
  • h opens a help screen showing: (1) the pager SHORTCUTS — every _keyScroll binding, one line each (key → action); (2) the URI SCHEMES typeable at : (scheme → one-line description), e.g. commit:<rev>, diff:<path>?<rev>, log:, tree:<path>, blob:<path>, status:, ls:<dir>, cat:<file>, grep:#<word>, …
  • The screen is a normal pushed view: scrollable, -/BS returns to the prior view, q quits.

Constraints

  • Prefer a help: URI/view so h reuses _runSpell/pushView — NO bespoke "help mode" state machine. PRESERVE BRO-005 mouse-nav, the BRO-006 U click-targets, and the pale-yellow header band.
  • Plain/colour/tlv: the help hunk is an ordinary dog/HUNK (text + tok32), rendered by the pager like any view. Repro-first (CLAUDE §17).

WIP

Design decisions

  • (open) help: as a REAL producer view (be/views/help/help.js, auto-dispatched by the registry so be help: works outside the pager too) vs a pager-built synthetic hunk. A view is more consistent; but the SHORTCUT list is pager-internal, so a producer would duplicate/drift from _keyScroll. Candidate split: the help: view emits the URI-SCHEME table (sourced from the registry), the pager prepends its own LIVE shortcut table; OR the view owns both and is documented as "the jab pager help".
  • (open) URI-scheme table: auto-list the registry view names (no prose) vs a curated scheme → description table (small drift risk, far more readable). Likely curated.
  • (open) C parity (help: view + the h: help hint in C bro bro/) — a follow-up, out of scope here unless wanted.
