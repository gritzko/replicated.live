BRO-036: elastic fields — tag B marks ONE span per line the pager shrinks (ellipsis) or pads to fit cols (no-wrap mode)

Now
DONE

Ruled 2026-07-31, implementation not yet ordered. In tabular views (the work view's commit-message column, todo's ticket title) a line often overflows the viewport; BRO-014's no-wrap mode hard-truncates the whole line at the right edge, which eats the trailing fields. Ruling: the producer tags the field's bytes with tok32 tag B (both-ways elastic); in no-wrap mode the pager ellipsizes that span when the line is too wide and space-pads it to cols when too narrow, so the columns after it stay visible and flush right. Wrap stays pure presentation — producers only tag, never pre-shorten or pad.

Input

Context

  • BRO-014 no-wrap truncates the display row at cols, so in the work view a long commit message pushes the trailing columns off-screen entirely.
  • Today the hunk token stream has no notion of a shortenable field; the pager is field-blind and can only cut at the viewport edge.
  • Open modelling question: is the commit message ONE token in the hunk stream or MANY (syntax-coloured words)? An elastic TAG must span the whole field either way.

Goals

  • Decide whether elastic-field shortening is worth having, and if yes, pick the mechanism: a token type / tag (like the U click-target tag) marking the shortenable span.
  • In no-wrap mode the pager shortens only the tagged field (ellipsis), so fixed columns after it stay visible and aligned.
  • Soft-wrap mode is untouched — elastic tags are ignored there.

Constraints

  • Producers stay presentation-agnostic: they tag the field, the pager decides how much to cut at the live width — no width knowledge in producers.
  • Must compose with existing per-token tags (colour, U click targets) and with BRO-014's wrap toggle; piped --plain/--color output is unaffected.
  • One elastic field per line at most; multi-elastic layout negotiation is out of scope.

WIP

Design decisions

  • RULING (gritzko 2026-07-31): tag B — the ONE elastic tag, always both-ways; the field's bytes carry B as their tok32 tag directly (no hidden marker), so the field is one span, one theme color.
  • B was the only free letter in A–Z (jab/dog/THEME.h claims the rest for fg/bg/status roles); its theme slot renders neutral (ANSI_DEFAULT) like S.
  • No-wrap mode, line wider than cols: the pager ellipsizes the B span (… at the cut) so trailing columns stay visible; still too wide after full shrink → hard-clip at the edge as today.
  • Line narrower than cols: the pager space-pads the B span until the line hits cols, so trailing columns end flush right, aligned across rows.
  • Soft-wrap mode and piped --plain/--color output ignore B entirely — bytes pass verbatim, no trim, no pad.
  • One B span per line at most (unchanged constraint); first producers: work (commit message) and todo (ticket title).
