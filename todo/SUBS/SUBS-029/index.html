SUBS-029: recursive post stages a phantom no-op gitlink put in a sub shard and leaves it uncommitted

Now
DONE

A recursive be post at the parent stages a 160000 gitlink bump INSIDE a sub's shard for a grand-sub that never changed, then leaves it uncommitted — the sub shard is left dirty with an orphaned no-op put. Live capture (glitch): posting beagle-journal left beagle reading 1 put (put abc) while abc stayed clean at the SAME pin 6e3b93f8, no commit. This is the inverse of SUBS-026 (a real bump DROPPED) and violates SUBS-027's POSTNONE→no-bump contract. See Submodules.

Input

Context

Two-level mount beagle-journal → beagle → abc; abc clean and pinned at 6e3b93f8 throughout. Full transcript in glitch.

  • Before post: status:beagle/abc ?6e3b93f8… 237 ok — clean, pinned, nothing staged.
  • be post 'JS-015..JS-024…' recursed post-order: printed post beagle/abc then put beagle#5b11dad9 (the legit parent gitlink bump), committed parent ?7a97cec1.
  • After post: status:beagle shows 17:16 put beagle/abc / 1280 ok, 1 put; cd beagle confirms 17:16 put abc; cd abc shows ?6e3b93f8… 237 ok — same sha, NO commit.
  • So the recursion stamped a gitlink put-row for abc in beagle's shard though abc is unchanged (no Advanced bit) AND beagle made no commit (POSTNONE) — the row is a phantom, left dangling.
  • Manual be put beagle/ (no recursion) earlier did NOT do this; only the recursive post did.

Goals

  • A recursive be post stages a sub gitlink bump ONLY when the sub's pinned tip differs from the parent gitlink (Advanced); an unchanged pin yields PUTNONE, never a put-row.
  • A sub that makes no commit (POSTNONE) leaves NO staged gitlink put in its shard — no orphaned half-apply after the parent post returns.

Constraints

  • Reuse SUBS-027's SUBSDirty Advanced axis (R4.base DESCENDS R1) to gate the bump; do not re-parse the tree per verb.
  • ABC style; sniff/keeper edits, no hand parsing, not abc/.
  • SERIALIZE with SUBS-026 / SUBS-027b / PATCH-001 — same gitlink-bump path (work.mkd non-FF hazard).
