ABC-023: slotless RO file maps — close(fd) right after mmap

Big read-mostly views (todo, work) map hundreds of files; every RO map pins its fd until JS GC collects the view, so a real drive outruns the collector and dies with "too many open files" (~1000 maps; ulimit -n 1024 == FILE_MAX_OPEN). Ruling (gritzko, 2026-08-04): at the very minimal level, close the fd right after mmapping. A PROT_READ map needs no fd after mmap, so RO maps leave the fd-keyed registry entirely — no slot, no collision.

Input

Context

  • The fd number IS the registry key: FILE_WANT_BUFSfd slot, FILE_RW bitmap, JABC_MAP_GEN are all fd-indexed (FILE.c, io.cpp).
  • That killed naive close-after-mmap in ABC-014: a reused fd collides with a live slot, GC closes a stranger's fd.
  • Release is GC-only in practice: ABC-020 found any read materializes the buffer, then abc.close silently no-ops.
  • The common JS idiom io.mmap(p,"r").data().slice() never closes at all (diff.js:520, why.js:32, ignore.js, gitmodules.js).
  • The .slice() copy is cargo cult: view or copy, the fd dies at the same GC; the memcpy buys nothing for the leak (gritzko).
  • io._ram already has the wanted release shape: plain munmap finalizer JABCRamFree off a per-array length box (io.cpp:620).
  • ABC-020 established FILEReMap/pread are unreachable from the JS RO path; post-mmap the fd serves only as slot identity.

Goals

Kill fd exhaustion on read paths with zero JS call-site changes: a view's fd cost becomes 1-at-a-time and RO maps stop occupying the 1024-slot FILE_WANT_BUFS table.

  • PROT_READ maps: open, mmap, close(fd) at once, register NO slot.
  • GC finalizer = plain munmap(base, len), len carried in a ctx box (the io._ram pattern); no gen/ABA machinery needed.
  • io._munmap stays idempotent and handles both map kinds.
  • Red-first repro: loop io.mmap(path,"r") + a read leg under a lowered RLIMIT_NOFILE; exhausts today, stays flat after.

Constraints

  • New FILE.h leaf for the tight RO map (slice out, fd closed inside) plus its plain-munmap counterpart; io.cpp reuses them, no reimplementation of open/mmap logic in the binding.
  • dog-internal C callers of FILEMapRO keep the slotted API.
  • "rw"/"c" modes unchanged (slot + fd as today); the RW rework is ABC-020's REWORK-1 ruling, out of scope here.
  • User-facing errors in plain words; ABC idioms per abc.

WIP

Design decisions

  • New leaves FILEMapOnce (open+mmap+close, fills the CALLER's u8b, no slot) / FILEUnMapOnce (plain munmap of the RECORD's whole range b[3]-b[0]); both reuse FILEOpen/FILESize/FILEClose, wrapper+worker so the fd dies on every exit path. LANDED 2026-08-04 under the ruled names (was ...ROSlotless/...Slotless with a base+len unmap — rejected, no fd/len in the API).
  • io.cpp: "r" → slotless + JABCMapROFree finalizer off a malloc'd length box (the JABCRamFree pattern); "rw"/"c" untouched, keep the slot + the (gen,fd) JABCMapFree guard.
  • RULING (gritzko, 2026-08-04): slotless maps are OK to unmap at GC — the deviation below is approved as the design.
  • RULING (gritzko, 2026-08-04): the API is FILEMapOnce(u8bp, path8s) / FILEUnMapOnce(u8bp) — NO fd in the API; an empty file maps to the empty record, unmapping it is a noop.
  • FILEUnMapOnce guards cross-pairing: a slot-backed record is refused (FILEBookedFD >= 0), so a leaked fd cannot go silent. The reverse misuse already fails NONE, left as is.
  • Empty file: FILEMapOnce skips mmap (length 0 is EINVAL) and yields the empty record (all four pointers NULL); io.cpp turns that into a plain 0-length Uint8Array — JSObjectMakeTypedArray- WithBytesNoCopy SEGVs on a NULL base (verified, exit 139).
  • DEVIATION: io._munmap does NOT eagerly release a slotless map — it stays the silent no-op it already is for a non-FILE base. Reasons: (1) eager release needs base→box lookup, i.e. a side table, and without a released-flag it reintroduces exactly the ABA the ticket says needs no machinery; (2) it would be dead code anyway — abc.close hands _munmap the TRANSFERRED husk, and on any materialized (i.e. every real) read transfer COPIES, so the husk's base is not the mapping's (ABC-020 evidence). With no fd left, deferring the munmap to GC costs VA only.
  • abc.close on "r": transfer detaches the views, msync/_munmap find nothing, no throw — verified in the test, no code change.
