Sx.h csFind walks one element per iteration calling memcmp(*haystack, &needle, sizeof(T)) — for T=u8 that is a naive byte loop where memchr (word-at-a-time in musl, SIMD in glibc) does the same job several times faster. perf on lite index of git.git (2026-08-13, quickjab build-no-bundle): u8csFind is 18.27% SELF of all user cycles, entirely under GITTreeDiff -> git_td_next -> GITu8sDrainTree (NUL find, 12.30%) + GITu8sFileSplit (space find, 4.21%) — 210,407 tree diffs parse both sides entry by entry. Every dog that parses bytes pays this tax.

Input

Context

DOG-030 made the per-commit tree work one C call, which promoted the entry parse to the hot loop; the find inside it is the single hottest symbol in the whole index run.

  • Sx.h:362 csFind: for (; !$empty(haystack); ++*haystack) if (memcmp(*haystack, &needle, sizeof(T)) == 0) — correct for any T, slow for bytes.
  • csRevFind mirrors it right-to-left; memrchr is the byte twin (musl and glibc both carry it).
  • Contract to preserve exactly: on hit haystack[0] advances TO the match (OK); on miss the slice goes empty (NONE); RevFind retreats haystack[1] so the match is last.

Goals

The u8 instantiation of sFind/csFind (and csRevFind) runs on memchr/memrchr; wider T keep the generic loop.

  • Mechanism is the worker's design decision — e.g. a sizeof(T) == 1 branch inside the template (the compiler folds it away per-instantiation), which keeps every call site untouched.
  • Call sites do not change; behavior is bit-identical incl. empty slices and needle-at-head/term.
  • Measure: a find micro-bench plus the real lite index git.git run (u8csFind self% before/after; expect ~15% of user CPU back).

Constraints

dog/abc is the shared floor under jab, quickjab and be — a regression here is everyone's regression.

  • Semantics locked by existing tests; all abc/dog/quickjab suites green (ctest -j16).
  • jab/ is read-only; the fix lands in dog/abc (///jab/dog/), quickjab picks it up through its dog sub.
  • No new API, no call-site edits; scratch in ~/tmp; put + report, no VC ops.

WIP

Design decisions

  • A sizeof(T) == 1 branch inside csFind itself, not a hand-written u8csFind override: objdump confirms the memchr call is emitted only in the u8/i8 instantiations, while u64/u128 keep the loop. No API, no call sites, and sFind/csFindS/sFindS inherit it for free.
  • The needle is read as *(u8 const *)&needle, not cast to int: the dead branch must still compile for struct T (u128, u256), and a signed i8 needle maps to the right raw byte this way.
  • $empty guard before the call, so the contract is bit-identical: NULL / empty slice returns NONE untouched, a miss leaves haystack[0] == haystack[1], a hit advances haystack[0] to the match — exactly what the loop did (also keeps memchr(NULL, c, 0) out of the picture).
  • csRevFind left on the loop. memrchr is a GNU extension: absent on macOS and gated behind _GNU_SOURCE on musl, and Sx.h is a header everything includes, so that define cannot live here. The profiled 18% is all in the forward find anyway.

Blockers and bummers

  • The profiled quickjab/build-no-bundle compiles with no -O flag at all (CMAKE_BUILD_TYPE empty; 19 of 348 TUs carry any -O). That unoptimised byte loop is a big part of the measured 18%.
  • On this box (Alpine musl 1.2.5, Ryzen 7840U) memchr is word-at-a-time, not SIMD, and it loses to the compiler-vectorised loop when the hit is only ~20 bytes away — which is exactly the git tree entry case at -O2/-O3. See Outcome; needs a ruling.

Outcome

abc/Sx.h:362 csFind gained a sizeof(T) == 1 branch on memchr; everything else untouched. Correctness harness (202,311 cases: empty, NULL, needle at head / at term-1 / just past the term, absent, all-equal, NUL and 0xFF needles, 64 unaligned starts, repeated walk, 200k random fuzz) — new impl matches the old loop on return code and on both slice bounds, 0 failures; clean under gcc, clang and UBSan. ctest -j16 78/78.

Micro-bench, ~/tmp/abc024_bench.c, real u8csFind out of line, old and new built from the same source (Alpine musl 1.2.5, Ryzen 7840U):

| workload | -O0 old | -O0 new | -O2 old | -O2 new | |---------------------------------------|---------|---------|---------|---------| | 193k git tree entries, 2 finds each | 92.8 ms | 51.4 ms | 29.7 ms | 44.3 ms | | 4 KiB chunks over 16 MiB | 195 ms | 14.4 ms | 38.6 ms | 13.8 ms | | one 16 MiB scan, needle at term-1 | 353 ms | 19.2 ms | 65.9 ms | 18.7 ms |

So: a clean win everywhere unoptimised (1.8x on tree entries, 13-18x on long slices) and 2.8-3.5x on medium/long slices at any -O — but a *1.5x regression on short git tree entries at -O2* (1.4x at -O3), because musl's word-at-a-time memchr plus the call costs more than the vectorised loop when the NUL sits ~20 bytes in. Two variants were tried and rejected: a length threshold (useless — DrainTree's haystack runs to the end of the buffer, so the length is huge while the hit is near) and an inline head scan before memchr (best case 31.1 ms, still short of the plain loop's 29.7, and it wrecks the -O0 numbers). Open question for gritzko: ship as is, or is the real cure to give the profiled build an -O flag?
