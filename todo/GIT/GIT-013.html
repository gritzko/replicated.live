GIT-013 JS: POST push over the wire (ssh:/http: receive-pack)

GIT-012 gave the JS wire a FETCH client (upload-pack) over ssh: and http:, but be/shared/wire.js exports fetch only — there is NO push, so be post //host / post ssh://host?br / post https://host?br (FF-advance a remote branch with cur's commits) is unimplemented in jab. This ticket adds the send-pack write direction: a shared wire.push() that advertises git-receive-pack, sends <old> <new> <ref> update commands plus a packfile of the objects the remote lacks, and parses report-status — over ssh: (spawn) and http: (curl POST), non-blocking over pol. POST stays FF-only; the unconstrained ref-write/force is its sibling GIT-014, reusing this core. Method: Issues.

Input

Context

  • GIT-012 landed the upload-pack FETCH client; be/shared/wire.js exports fetch only — no receive-pack/send-pack (grep finds no push path), so jab cannot push.
  • be post //host / post ssh://host?br / post https://host?br (FF-push cur's tip to a remote) therefore no-ops or errors in jab; native C be pushes via keeper/WIRECLI.c send-pack.
  • The smart-protocol PUSH service is git-receive-pack: same pkt-line frame as fetch, opposite direction — client sends update commands + a pack, then reads report-status.
  • Motivating case: jab post //origin to publish Beagle's own beagle-ext changes (the task that opened GIT-012) needs a working push.

Goals

  • Add a shared wire.push(remoteUri, updates, pack) receive-pack client used by jab post, over ssh: (spawn) and http: (curl), mirroring GIT-012's transports.
  • FF-only: POST refuses a non-fast-forward advance (the remote tip must be an ancestor of the new sha) per Invariants; force is PUT/GIT-014's job.
  • Reuse GIT-012 verbatim: pkt.js, the curl adapter + pol pump, classify() (add a receive-pack verb route), parseAdvLine.
  • Build the push pack from the local store (objects the remote lacks) by delegating to keeper's pack builder — do not reimplement a pack writer in JS.

Constraints

  • receive-pack over ssh (spawn git-receive-pack) + http (curl POST …/git-receive-pack); non-blocking over pol; no new TLS binding (curl owns https), all as GIT-012.
  • No git:// push: the daemon refuses receive-pack by default (anonymous push unsafe) — out of scope, as in GIT-012.
  • FF-only gate enforced BEFORE any wire write; a non-FF target errors without sending a pack.
  • ABC/JS norms: reuse before adding, ≤2-line GIT-013 comments, greppable, ticket-coded commits; do not regress the fetch path or ssh/local.

WIP

Design decisions

  • wire.push(remoteUri, updates, packBytes): advertise receive-pack, send <old> <new> <ref>\0<caps> pkt-lines + flush + the pack, then parse unpack ok / ok <ref> / ng <ref> <reason>.
  • http: GET <U>/info/refs?service=git-receive-pack (skip the # service… preamble), then POST <U>/git-receive-pack, types application/x-git-receive-pack-{request,result}; ssh: spawn git-receive-pack <path>.
  • Caps minimal: report-status ofs-delta, no side-band — so the response is plain report-status pkt-lines, the same demux-free choice as GIT-012 fetch.
  • Pack building: compute the not-yet-present object closure (advertised-remote-tip..cur) and emit a packfile via keeper (keeper pack/serve builder); the JS never writes a pack itself.
  • FF check: read the advertised tip for the target ref and require it be an ancestor of cur via the local DAG (or empty for a new ref) — else refuse before any write.
