GIT-017 JS: remote-tracking refs must record host + FULL ABSOLUTE branch

A remote-tracking ref row must identify BOTH the remote host AND the remote branch, in full absolute form (?/project/branch/…) — but the JS writer drops the branch: shared/ingest.js saveRemoteRef (and clone/add) do remoteUri.replace(/\?.*/, "?"), recording //host?#tip with the query stripped to a bare ?. So every branch of one host collapses onto the trunk key even though store.eachRemote keys by authority + query and COULD tell them apart: a second branch push overwrites the first, and a cached be head //origin?branch cannot resolve the right per-branch tip. Fix: record {verb:"get", uri: <scheme>://<host>?/<abs-branch>#<tip>} — host kept, branch kept and RESOLVED to absolute — across every remote-track writer. Split from GIT-016 T3 (saveRemoteRef); JS only (be/, via jab). Method: work.

Input

Context

  • shared/ingest.js saveRemoteRef(shard, remoteUri, tip) writes {verb:"get", uri: remoteUri.replace(/\?.*/,"?") + "#" + tip} — the \?.*→? strip discards the branch, so the row is //host?#tip (host present, branch GONE).
  • ingest.clone/add do the SAME origin = remoteUri.replace(/\?.*/,"?") strip — the whole remote-track convention loses the branch, not just the push path.
  • store.eachRemote (shared/store.js ~L451) keys rows by (u.authority) + (u.query) + "#"; the reader ALREADY distinguishes branches — the WRITER is the defect. With query stripped to ?, two branches of one host share one key and the newer clobbers the older.
  • Callers of saveRemoteRef: verbs/post/post.js pushRemote, verbs/put/put.js pushWire, and (GIT-016 T4) the head verb — all inherit the branch loss.

Goals

  • Record a remote-tracking row carrying the remote HOST (authority/scheme) AND the remote BRANCH in FULL ABSOLUTE form (?/project/branch/…), never a bare ? and never a relative branch.
  • store.eachRemote / a cached be head //origin?branch / get's remote-track resolve return the correct PER-BRANCH tip; multiple branches of one host coexist.
  • Repro-first: record two branches of one host and assert both tips are retrievable distinctly (fails today — the second overwrites the first).

Constraints

  • JS only, be/, run via jab. Do NOT run native be; do NOT open beagle/.
  • Reuse the URI resolver for the absolute-branch form (the ?/project/branch shape, see URI); do NOT hand-assemble ref strings. Reuse resolveRef/the ref resolution already shared in GIT-016.
  • ABC/JS norms: ≤2-line GIT-017 comments, greppable, ticket-coded ≤64-char commit. No new deps.
  • Keep clone/add/get's cached-read + update path working — the ?-strip is an established convention there; changing it must not regress a fresh clone's default-branch row.

WIP

Design decisions

  • The branch MUST be stored ABSOLUTE (/project/branch): a relative/bare form is ambiguous once detached from the push context, and eachRemote's key needs a stable per-branch discriminant.
  • A clone's default-branch row MAY legitimately stay ? (the trunk), but a branch-scoped fetch/push must record that branch — decide the split in clone/add vs saveRemoteRef.
