GIT-029: git plumbing verbs — cat-file/ls-tree/rev-parse/ls-files/merge-base with git-parity output

Now:
OPEN

The tooling layer of the git compat story: the plumbing subset that editors, CI, and scripts actually shell out to. These are raw store reads — they must NOT round-trip through be verbs; they map straight onto the store reader / dog-core primitives jab already binds. Output byte-parity with real git for the common invocations is the whole point: a tool that parses git ls-tree output must parse ours. Lives in the same compat repo as the GIT-028 porcelain shims.

Input

Context

  • Store access exists: shared/store.js open/reader, the serve-side closure walk, tree reads via core/discover.treeAt — plumbing is a thin formatting pass over these.
  • Reference C for pack/tree walking is ///jab/dog/; jab-side plumbing stays JS over the same store, no new native binding.
  • All name/hashlet → sha resolution goes through core/resolve_hash.js — the mandated single path; a hashlet is any 6..40 hex prefix.
  • Consumers to satisfy first: editor gutters/plugins and CI scripts — rev-parse + cat-file + ls-files cover most of what they spawn.

Goals

  • Read-only plumbing verbs over a .be store: cat-file (-t/-s/-p and the bare blob form), ls-tree, rev-parse (ref or hashlet → sha), ls-files, merge-base, hash-object (hash only, no -w).
  • Output parity: for the supported invocations, stdout is byte-equal to real git on the same repo content — proven by a diff harness in tests.
  • Errors in plain words when a rev does not resolve or a path is not tracked, on stderr, exit codes matching git's 0/1/128 convention.

Constraints

  • Read-only surface: no verb here writes the store (hash-object -w is excluded; writing belongs to the be verbs).
  • Resolution reuses resolve_hash.js — NO parallel ref/hashlet parsing.
  • Formatting only: any missing store capability (say, a walk order) is filed against the core, not hacked into the plumbing verb.

WIP

Design decisions

  • One jsrc/verbs/<name>/ per command in the compat repo, sharing one small formatter module for the git output shapes (mode, type, sha, QUOTED paths per git's c-style quoting).
  • Parity harness: a fixture repo readable by BOTH git and jab; each test runs the same invocation twice and diffs stdout byte-for-byte.

Blockers and bummers

  • git's c-style path quoting and mode strings are fiddly parity traps — the harness must include a path with spaces/UTF-8 from day one.
  • ls-files semantics depend on the staged-set reading (stage.js); divergence there surfaces here first and is its OWN ticket.
