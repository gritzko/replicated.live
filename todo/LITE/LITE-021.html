gritzko's ask 2026-08-14: in lite commit the hashes are dead text — make them clickable, with commit: and tree: links. The view (index/commit.js, LITE-009) deliberately dropped be's hidden U click-targets when it was ported; LITE-017 has since built exactly the machinery they need: the pager's verb door (a U target like tree /root/sub/ or blob <sha> opens that view in place) and the tree/blob views themselves. So this ticket re-arms the commit view: its own commit <sha40> banner row, every parent <sha40> header line → a commit <sha> target; the tree <sha40> header line → a tree <sha> target — Enter on the row or a click on the hash follows, - goes back.

Input

Context

All in the //LITE-018/ tree (which carries LITE-017's work):

  • view/pager.js: U spans are BRO-006 click targets — hidden bytes after a visible token ARE the target; Enter takes the row's first target, a click the span it landed in; LITE-017 rows carry TWO per row (Enter + click). The door resolves <verb> <arg> targets for the LITE-017 views already.
  • index/commit.js (LITE-009): emits the commit header block verbatim (tree/parent/author/date lines, folded continuations) as one hunk; its mission comment records dropping be's U/F spans — that drop is what this ticket reverts, for hashes only.
  • index/tree.js exists (LITE-017): tree <hex> resolves any 6..40 hexlet. lite commit <hex> likewise. So the targets are plain commit <sha40> / tree <sha40> verb-arg strings; no new resolution.
  • --plain/piped commit output is the raw git cat-file commit bytes (LITE-009 contract) — U bytes are invisible in the pager but MUST NOT leak into plain: plain stays byte-identical.
  • be's commit view carries clickable hashes (its U spans) — the be shape to consult, not to re-port wholesale.

Goals

In the pager, a commit page's hashes navigate: the banner sha and each parent sha open that commit's page (commit: link), the tree sha opens the tree listing (tree: link); plain bytes unchanged.

  • parent <sha> lines: the sha token gets the click target commit <sha>; the banner commit <sha40> row targets its own sha too (self-refresh is acceptable, be-parity) or is skipped — worker decides from be's shape and records it.
  • tree <sha> line: target tree <sha> — opens the LITE-017 tree view at that tree... a tree sha, not a commit: confirm lite tree accepts a raw TREE object sha (not just a commit rev) and make it so if not, that is part of this ticket.
  • Enter on a header row follows its hash; a click lands on the hash token itself; - returns to the commit page.
  • --plain/piped bytes byte-identical to today (pinned with cmp in tests).
  • A merge commit's SEVERAL parent lines each carry their own target.

WIP

Design decisions

Confirmed against the code, then built on.

  • Targets ride the LITE-017 two-span-per-row pattern: U after the field NAME span (Enter lands on the row's first span) AND after the sha span (a click lands in the sha). Both carry the same target string.
  • BANNER sha: NO target. be's own ruling, recorded verbatim in be/views/commit/commit.js:242 — "the synthetic commit header IS the page" (PROJ.c:431-436). Self-refresh was the alternative; be-parity won.
  • The tree-sha "gap" is NOT REAL: index/tree.js:62 (LITE-017) already returns {tree: <hexlet>} on o.type === "tree". Verified on a root tree AND a subtree sha, plain bytes vs git ls-tree. NO tree.js edit.
  • Pager door: commit was ALREADY a door verb (main.js VERBS.commit, LITE-009/017). No main.js edit.
  • Plain stays byte-identical by carrying TWO bodies, be's shape: out.text/out.toks U-free (what --plain and a pipe write), out.textU/out.toksU with the targets spliced in — hunk() hands the pager the latter. spansOf grew a third nav element per span; withTargets() does the splice.
  • gpgsig/mergetag continuations and the message body stay span-free, as ruled.
