gritzko 2026-08-14: minting rides the commit — a hook scans the changed files for NEW file:line(:col) refs and rewrites them into file:OFF:HASHLET permalinks (LITE-025 form, BLOB hashlet only). Beagle and git repos alike need one; lite deals only with git, so there it is a git hook planted by the install routine. Commit time is exactly when every staged blob's hash is known, while the commit id is not — which is why the LITE-025 hashlet is blob-only.

Input

Context

LITE-025 defines the permalink: ron64 byte offset into the named blob + the blob's hashlet (min 4, even, non-digit, unique in the path's own blob history, earliest match wins). The transient file.c:12:24 form is what humans and compilers write; committed text is where it rots — the hook upgrades it at the last moment it is still current.

  • Only ADDED lines are scanned — existing text is never rewritten.
  • The target's blob = its staged blob when the commit changes it, else HEAD's; either hash exists pre-commit.
  • Rewriting a staged file changes its blob: the hook re-stages the rewritten file; standard pre-commit practice.
  • Same-file self-links are excluded (LITE-025: the rewrite would change the blob the link names) — left as line:col.

Goals

A pre-commit hook + its installation, lite/git only; the beagle-native (post-verb) counterpart is separate ground, not this ticket.

  • Hook: diff staged vs HEAD, scan added lines for path:line(:col) refs (all-digit anchors) whose path resolves in the repo; compute the target line's byte offset in the target blob; rewrite to path:OFF:HASHLET; re-stage.
  • Refs that do not resolve (no such file, line out of range) are left untouched — the hook never guesses.
  • Install routine plants the hook into .git/hooks/pre-commit, composing with a pre-existing hook rather than clobbering it.
  • Shared helpers with LITE-025: ron64 packing, hashlet extension, offset math — one implementation, no parallel copy.

Constraints

  • ///lite worktree only; no VC ops; the hook itself is the only thing allowed to re-stage, and only files it rewrote.
  • Ref detection rides the lexer's fused F anchors, not a regex re-scan (no manual URI parsing).
  • Verify end to end: a repo fixture where a commit with a fresh file:line ref lands with the permalink form in the committed blob, and a follow through the LITE-025 resolver hits the right line.

WIP

Design decisions

  • ADDED TEXT is read off the weave, not off a diff: one HEAD->staged CFOLD pair, and an alive token the HEAD side does not carry is new. The token carries its own tag, so the F anchor and the addedness come from the SAME walk — no unified-diff parsing, no regex.
  • The mint is a bounded FIXPOINT: rewriting file A moves the blob a link in B names, so the hashlets are re-minted until the images stop moving (4 rounds; still moving = nothing is written).
  • The hook line is planted FIRST (after the shebang), not appended: a pre-existing hook gating on its own exit 0 would never reach an appended line, and a linter later in the file then sees the rewritten text.
  • gritzko's ruling 2026-08-14: the rewrite lands in the INDEX — the working file is NEVER used as a proxy for what a commit takes. hash-object -w + update-index --cacheinfo, then the SAME upgrades over the working file ref for ref, so an unstaged diff never shows a link-form difference. The earlier "partially staged file is left alone" skip is RETIRED.
  • The working-file half substitutes by TOKEN, never by substring: FSW.c:9 is a prefix of FSW.c:90, so the lexer decides what a ref is on that side too. A ref that exists only on disk was not part of this commit and waits.
  • gritzko's ruling 2026-08-14: the FIRST commit mints too — the empty tree is the diff-index base, the staged set alone resolves every path, and the hashlet scope degenerates to that one staged blob. openRepo's HEAD gate is right for the read verbs and stays; hook.js owns the HEAD-less handle.
