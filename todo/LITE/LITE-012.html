lite index calls ix.commit() every IDX_BATCH (200) rows; every such commit is a DURABLE seal (DOGPupCommit -> FILESync -> fsync). Measured 2026-08-13 on a git.git hardlink clone (81,726 commits, 776,548 rows): 3,884 fsyncs at 8ms each = 30s of a 81.6s run is BLOCKED time, not work. The fix is a cadence change in lite/index/index.js alone: batches seal through the memtable AUTO-seal (which never fsyncs), and ONE durable commit lands at the end, where the MARK row already goes.

Input

Context

The per-batch commit was inherited from be/shared/ingest.js idxWriter; its "one 4KB page per batch" discipline is about seal-prefix atomicity, not durability. The durable fsync per batch buys nothing the lazy contract needs, and dominates the wall clock.

  • Lane bench, same 776k wh128 puts: commit-per-200 = 35.0s wall / 3.5s user; auto-seal only = 4.3s wall / 3.4s user. Identical CPU, identical resulting runs — the whole 30s difference is fsync blocking (~8ms each on this disk).
  • End to end: with the commit leaf no-op'd the full git.git index run drops 81.6s -> 44.7s (wall == user, zero blocked time), byte-identical row/rev/commit counts.
  • Linux extrapolation: 1.46M commits -> 14M rows -> 70k fsyncs — on the order of 9 MINUTES of the current 10 min first index.
  • DOG-032 attributes the 9ms/seal to "sorts+dedups DATA, writes a run, climbs the ladder" — measured, that CPU is 1ms/seal; the ~8ms is the fsync wait. The 1MB memtable still helps (fewer seals, fewer ladder climbs) and COMPOSES with this; this ticket is the smaller, JS-only cut.

Goals

bringUp's writer stops issuing durable seals mid-run; wall time ≈ user time on an SSD.

  • idxWriter keeps its put loop but drops the per-200-rows ix.commit(); rows reach runs via DOGPupPut's full-page auto-seal (sort+dedup+seal+ladder, NO fsync).
  • ONE ix.commit() at the end of the run: seals the final partial page, fsyncs once, and the MARK stays the LAST write (DOG-027).
  • Measure: git.git wall before/after (expect 82s -> 45s here); linux first index re-timed on gritzko's box.

Constraints

The lazy contract (INDEXES.mkd) is untouched — it already absorbs every consequence of this cadence.

  • A seal persists a PREFIX of what was put and run rename stays atomic; CPAR-last per commit and the top re-put guard already handle a kill between auto-seals (a redundant re-walk, never a lie).
  • Durability against POWER loss is explicitly not owed: .git/be is derived — a torn post-crash state is rm -rf + re-derive.
  • The fault goldens (_faultMid, _faultAfter) encode the contract via wr.seal(); they must stay green — expected unchanged, since seal() keeps calling ix.commit() on the remaining page.
  • lite/ edits only; no dog/, no quickjab edits; scratch in ~/tmp; put + report, no VC ops.
