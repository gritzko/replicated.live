Beagle-lite reads a git repo's history (LITE-006 index, LITE-007 log) but cannot show ONE commit. be has that view already — be/views/commit/commit.js renders the keeper metadata hunk — so this is a PORT, not a design: the output machinery (tok32 hunk, view/bro.js theme, view/pager.js) is the same, only the store access differs (be's shared/store.js vs lite's git.getHex over the repo's own ODB). Order of the work: borrow be's renderer, replace its store and nav layers, verify the bytes against git cat-file commit.

Input

Context

be's views/commit/commit.js is the source; lite/index/log.js is the shape a lite view takes (hunk build, tty-vs-plain split in main.js).

  • be's KEY FINDING, verified there: commit: plain output is EXACTLY "commit <sha40>\n" + the RAW commit object bytes, verbatim.
  • The colour is layered on top of those same bytes: field names R, sha values L, author/committer G, subject N, message body W, line terminators S.
  • be reads the object through shared/store.js and walks the headers RAW (not git.parseCommit, which drops header order and non-canonical headers like gpgsig/mergetag).
  • lite's ODB door is git.getHex(h, hexlet) — it takes any 6..40 hexlet, so a commit hashlet IS an object name (LITE-007 uses this).
  • What be's commit.js drags in that lite has NO equivalent of: shared/wtlog.js, shared/nav.js, shared/ticket.js, core/recurse.js, shared/ambient.js — all of it is nav/sub/ticket layering, none of it is the metadata hunk.

Goals

lite commit <hex> prints the be commit: bytes for that commit: a coloured hunk in the pager at a terminal, the bare bytes when piped or under --plain.

  • Arg is a 6..40 hexlet, resolved through the ODB; a non-commit or an unknown name fails in plain words, the way LITE-007 seedOf refuses one.
  • Plain output byte-equals "commit <sha40>\n" + git cat-file commit <sha> — that is the whole acceptance test, and it is exact, not approximate.
  • Ordered headers survive verbatim, including folded RFC-822 continuations and gpgsig/mergetag — pick a signed commit as a fixture and prove it.
  • tty leg goes through main.js pageHunks unchanged, so the pager, banner and status bar are the ones a file arg already gets.

WIP

Design decisions

Leads, not rulings — the worker confirms each one against the code before building on it.

  • A commit view is PURE ODB: no lane read, no bringUp, no $HOME/.config/be/tracks line — so lite commit stays fast on a repo whose index is cold.
  • Whether an unindexed / off-branch commit should still render: it CAN (the ODB has it), and refusing would need the lane; the default is to render it and say nothing.
  • The header walk is be's parseHeaders (a literal \n scan + first-space split + leading-space continuation folding); port it, do not re-derive it.
  • Hunk shape is {uri, verb:"hunk", text, toks}, built the way index/log.js hunk() builds one (a growing io.buf, feedStr, one span per tag).
  • Tag codes are letters minus 'A': R=17, L=11, G=6, N=13, S=18, W=22 — view/bro.js's THEME already maps every one.
  • be's hidden U click-targets and F ticket-key spans are NOT carried over (lite has no nav layer), exactly as LITE-007 ruled for log rows.
