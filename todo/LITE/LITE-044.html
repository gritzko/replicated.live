On the linux tree, /list/include/drm/ fuses every FILE row but leaves the dirs amd/ bridge/ clients/ display/ with no commit message at all (gritzko, 2026-08-15, http://localhost:8888). The dir half of the LITE-017 fuse walks only the newest DIR_WALK_CAP = 512 commits, and at linux scale everything below the first level starves: the four dirs' newest commits sit 2072, 32176, 94935 and 151871 commits behind the tip. The file half never starves — one exact lane prefix scan — and that asymmetry is the bug.

Input

Context

lite/index/list.js dirCommits: CPAR ancestry newest-first, rd.entryAt per dir per commit, capped at 512 (LITE-013 style); past the cap a row keeps no summary and no age — documented ceiling behaviour that is fine on small repos and useless on linux.

  • Root dirs (arch/ drivers/ fs/...) DO fuse — merges touch them within the newest 512 — so the blanking hits exactly the dirs a browser is for: one level down and deeper.
  • Files are exact at any depth: fileLog is one prefix scan of the path's path_hl on the LITE-006 lane, no walk, no cap.
  • list.js's own header records WHY dirs walk: the lane hashes a path one way, so it cannot enumerate what lies under a dir.

Goals

A dir row's attribution is as exact as a file row's, at any repo scale: /list/include/drm/ shows the newest commit UNDER each of amd/ bridge/ clients/ display/, with an age, on the served linux tree.

  • Lead candidate: index DIR revs — descend() (index/index.js) already visits every CHANGED dir of every commit while pruning unchanged subtrees, so emitting REV rows for dirs (the dir path's path_hl, blob = subtree sha) makes the dir fuse the SAME one-prefix-scan as the file fuse; the capped ancestry walk and DIR_WALK_CAP retire.
  • Rejected up front: raising the cap (linux needs a ~152k walk — no number works, and numbers are exact here); per-listing recursive subtree scans (O(subtree) lane scans per dir, unbounded at the root).
  • An OLD index has no dir rows and (LITE-028/2026-08-13 ruling) presence is the walk boundary, so already-indexed commits never re-derive: the fix must make stale indexes rebuild or top up — settle it in Design decisions and pin it with a test.

Constraints

  • Worktree //LITE-044 (clone ///lite/ per /meta/work), lite/ only; no VC ops; repro FIRST as a test.
  • The MAIN TREE lite/ carries uncommitted edits landing separately (wt-marker column removal: list rows open with the name, no eq/mod column, one U span after the name). Do NOT reintroduce marker greps or the marker span if the clone predates them; keep new checks self-contained either way.
  • Fuse semantics stay LITE-017's: newest commit whose subtree sha differs from its first parent's; lite log/lindex behaviour must not change; suites test/list test/first test/serve green under a fresh quickjab build (stale ~/bin/jab lacks git.getTreeDiff — always run with LITEJAB=<quickjab build>).

WIP

Design decisions

The indexer says WHEN a dir changed; the fuse reads the newest of those rows. No history walk survives on either side, so depth and scale cost nothing.

  1. descend() (index/index.js) already visits exactly the CHANGED dirs of a commit — it prunes any subtree equal to a parent's — so it now emits a node for each of them too, the parent before its children, tagged dir: true.
  2. emit() mints a DIR rev as ONE row: REV-CMMT, key path_hl(dir)|rev|2, val the commit. Nothing else: no REV-BLOB (a subtree sha is no blob), no REV-PARS (a dir has no content to fold), no B2P, no FSEG (that names a FILE for resolve.js's descent, which only ever answers files). No new kind.
  3. A hot dir changes in most commits, so its rev chain is as long as the HISTORY. Folding it whole the way loadPath folds a file's brings back the LITE-028 stall — MEASURED on its own fixture: the reads doubled with the lane, 227/4002 then 457/8004, against a bound of 64/116. Rev chains are DENSE, so the highest rev is found by galloping and then bisecting EXACT-key probes (lastRev): O(log k) seeks and not one row of the chain. loadDir fills the indexer's arrival state from it.
  4. The fuse (index/list.js lastCommits) is one lookup per entry, off that entry's OWN rows: a FILE folds its chain through fileLog as before (short, and PARS is what orders a rewritten file history), a DIR takes its last rev straight. dirCommits, the CPAR ancestry, DIR_WALK_CAP and opts.cap are all gone — there is no tip and no ceiling in the dir answer any more.
  5. STALE INDEXES. Presence is the walk boundary, so an old lane's commits never re-derive and its dirs would stay blank forever. The lane FORMAT is therefore its file EXTENSION — .lite.idx becomes .lite2.idx — and openIndex SWEEPS (unlinks) every file of an outdated format before the family is opened. No reader ever opens a lane it cannot answer from, and the next run derives from scratch. Cost: one full re-derive per repo.
  6. lindex skips the dir nodes descend now yields; no other consumer exists.

Blockers and bummers

  • The lead design taken literally — dir revs down the SAME emit path as files (BLOB+CMMT+PARS+B2P, state through loadPath) — WORKS and breaks LITE-028's pinned bound, because a dir chain is O(history). Steps 2-3 amend it; they do not abandon it.
  • A pre-LITE-044 index is DELETED on first contact. ~/src/linux carries a 232 MB .lite.idx built 2026-08-14: the first lite verb run there with this code unlinks it and re-derives 1.46M commits. Nothing in this session ran against that repo.
  • The lane grows: +40 % on a 2000-commit fixture (160 KB -> 225 KB).
  • The ticket could not be edited in a worktree — jab get ///todo/, and the trunk clone it resolves to, dies on the jab sub ("none of the sources tried has that commit"). This text was written outside a clone.
