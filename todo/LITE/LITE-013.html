Ruling (gritzko 2026-08-13): the capped tty log walks LAZILY, git's own default order. Today lite log on linux (1.46M commits, index warm, release build) takes ~12-14s to show 256 rows: ancestry() builds the WHOLE CPAR DAG before emitting — the max cap bounds only the emit loop and the ODB reads. Measured 2026-08-13 (probe on the indexed linux repo, 13.7s total): 1,463,369 pup.range calls (one cparOf per commit, 5.3s native) + 8.4s of JS Map/BigInt churn building par/kids/deg/byHex over 1.46M keys; the ODB side is already lazy (541 readCommit, 26ms).

Input

Context

index/log.js ancestry() is a reverse Kahn over the full reachable set: BFS first (the 1.4M range calls), in-degrees from the kids counts, then a MAX-heap drain that max cuts short. The strict "--date-order" guarantee is exactly what forces the full BFS — in-degrees need total reachability.

  • fileLog is NOT affected: a file's history is one prefix scan of its path_hl, already O(that file's revs).
  • The pager view calls log with the 256-row default cap (main.js); piped/--plain and log 0 ask for everything.
  • git's own DEFAULT order (plain git log, no --topo-order/--date-order) is the lazy walk this ticket adopts: pop newest by committer date, push its parents, repeat.

Goals

lite log at a terminal opens in milliseconds on a linux-sized history; output order for a capped walk is git's default order.

  • In ancestry(ix, r, seed, max): when max > 0, walk LAZILY — a MAX-heap on (committer ts, tie-break hex) seeded with the tip; pop → emit; push each parent on FIRST discovery (seen set guards the push; tsOf = the existing lazy readCommit); stop at max rows; more = heap non-empty.
  • Cost becomes O(rows shown + frontier): max cparOf range calls and max ODB reads — the 256-row page does ~500 of each, not 1.4M.
  • max == 0 (a full log 0 / piped dump) KEEPS the exact reverse Kahn — the strict no-parent-before-its-children guarantee stays available where the whole history is being materialized anyway.
  • Known, accepted deviation of the lazy order (same as git's default): under clock skew a parent can print before a not-yet-discovered child. --date-order strictness is not claimed for capped walks; update the log.js header comment that currently claims it.
  • log <hex> takes the same lazy path (same ancestry); seedOf's indexed-check is untouched.

Constraints

lite/ edits only (index/log.js, comment in main.js if its cap note names the order); no index format change, no new records, no dog/quickjab edits.

  • Byte-identical rows for histories where the two orders agree — the existing test/ log goldens must stay green unedited; if a golden encodes a skew case where the orders genuinely differ, STOP and report, do not edit it.
  • The lazy and Kahn paths share cparOf/parentsOf/rowParts; no second row renderer.
  • Verify on the real repos: git.git and linux, log tty-cap timing before/after, and lite log | head vs git log --format=... order spot-check.
  • Scratch in ~/tmp; put + report, no VC ops.

WIP

Design decisions

  • The lazy walk is its OWN function, lazyAncestry(ix, r, seed, max), and ancestry is one line: if (max > 0) return lazyAncestry(...). The Kahn body below it is untouched byte for byte, so log 0 cannot regress.
  • The heap is the SAME idx.heap(true) on (committer ts, 15-hex), so the two walks break date ties identically — that is why the capped prefix comes out equal to the Kahn prefix on both real repos, not merely "close".
  • seen guards the PUSH (a hl60 Set), so a commit enters the heap once; the tiny byHex map only carries the popped name back to its hl60, since the shared heap keys on strings.
  • main.js NOT touched: its cap note says nothing about order (nothing to correct), and the live tree has an uncommitted 1000 -> 256 tweak on exactly those lines — editing them would only make a collision.

Outcome

DONE (2026-08-13). index/log.js only: lazyAncestry() + the one-line branch in ancestry() + the header's order paragraph. main.js untouched.

PERF (release quickjab, warm index, own --local clones of linux and git.git in ~/tmp). linux (1.46M commits), log 256 rows: 12,590 ms -> 59 ms in the probe, 46 ms end-to-end through the real CLI. pup.range calls 1,463,369 -> 256; idx.readCommit 541 -> 545 (unchanged, it was already lazy); the 7.8 s of JS Map/BigInt churn is gone entirely. git.git (81,726 commits), 256 rows: 668 ms -> 35 ms, pup.range 81,726 -> 256. max == 0 on git.git: 4.15 s -> 4.02 s and the 81,726-row output is BYTE-IDENTICAL to the pre-change dump.

ORDER — no deviation found anywhere:

  • lazy vs git log --format=%H at 256 / 1000 / 5000 / 20000 rows, on BOTH git.git and linux: 0 differing positions, 0 membership differences.
  • lazy vs the OLD Kahn on the same data (the Kahn prefix = head -N of the full walk) at the same four depths on both repos: 0 differing rows.
  • log <hex> 300 (seed 5000 commits down git.git): identical to git.
  • cap above the history (99,999 on git.git): 81,726 rows, capped false.

The accepted skew deviation stays theoretical on these two histories.
