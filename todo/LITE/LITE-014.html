Two halves, one feature: port be's CRDT 3-way weave merge to lite, then let lite install register it in a git repo as a custom merge driver. The merge core is be/shared/weave.js weave3(base, ours, theirs, ext) (GET-056b): base folds first, ours and theirs fold CONCURRENTLY on it (each diffs against base, not sequentially), a contentless merge joins all three, and mergedLive (PATCH-025/DIS-080) renders the RGA live bytes MARKERLESS with {bytes, spans} conflict ranges. All of it is plain JS over abc.ram("CFOLD", …), which lite already links since LITE-010 — quickjab carries cfold.c/weave.c, so this is a JS-only port, ZERO quickjab edits expected.

Input

Context

git invokes a custom merge driver per conflicting file: .git/config defines merge.<name>.driver = <cmd>, .gitattributes/.git/info/attributes maps paths to it (*.c merge=<name>), and git runs the cmd with temp files substituted for %O (base) %A (ours, also the output) %B (theirs); exit 0 = clean, non-zero = conflict. %P passes the REAL repo path (the temps have junk names), %L the marker size. Wiki precedent: Spot registers itself exactly this way.

  • Source to port: be/shared/weave.js — weave3 + mergedLive + fold/merge wrappers + bytesEq + the MAX_SOURCE_SIZE/MAX_SOURCE_MARKED_UP caps; the DAG-reconstruction half (build/buildDag/foldCommit) is NOT needed — the driver gets three blobs, no history walk.
  • weave3 trivial paths: ours==theirs → ours, ours==base → theirs, theirs==base → ours, all span-free; over-cap input returns null (BLOB, not weavable) — the driver must NOT silent-ours on null.
  • The tokenizer is picked by file EXTENSION (extOf); the temps %O %A %B have junk names, so the ext MUST come from %P.
  • lite/index/diff.js already allocates abc.ram("CFOLD", MAX_SOURCE_MARKED_UP) and carries a local copy of the size caps — the port shares one home with it, not a third copy.
  • Per-repo install is two writes: the driver def in .git/config (git NEVER reads driver commands from tracked files) and the pattern map, .git/info/attributes for a purely local uncommitted install.
  • be's weave-merge test coverage lives in be/test/patch/*/run.sh scenarios — conflict, same-anchor-conflict, stacked-conflict, dirty-overlap, multiedit-line, readd-line — edit scripts plus expected merged bytes, driven through be verbs.

Goals

lite merge is the driver: three input files in, markerless merged bytes out, exit code says clean/conflict. lite install wires it into a repo so a plain git merge routes file-level conflicts through the weave.

  • lite merge <base> <ours> <theirs> [-o <out>] [-p <path>] (exact argv is the worker's Design decision, reported before building): weave3 the three files, write bytes to <out> (default: over <ours>, the driver contract), exit 0 when spans is empty, non-zero when not.
  • lite install [<repo>]: same repo resolution as lite index (root, .git dir or gitfile, default cwd); writes merge.lite.name/merge.lite.driver into .git/config and the attribute map into .git/info/attributes; a second run is a no-op, not a duplicate append.
  • End-to-end proof: a real git merge in a fixture repo hits the driver, disjoint edits land clean where stock git conflicts (the CRDT selling point), a genuine overlap leaves git in conflicted state with markerless woven bytes in the worktree.
  • weave3 null (binary/over-cap) falls back to git's stock text merge (git merge-file), never a silent ours.

WIP

Design decisions

As built, ZERO quickjab edits — the port is plain JS over the CFOLD container quickjab already ships.

  • Port home is a NEW lite/index/weave.js, not a fold into diff.js: the merge core touches no ODB, no worktree and no HUNK render, so lite merge must not drag the diff view in. It now owns the ONE source-size policy AND the one "can we weave it" gate (MAX_SOURCE_SIZE/MAX_SOURCE_MARKED_UP, isBinary, extOf, bytesEq); diff.js imports all of them and re-exports its old surface unchanged.
  • weave3 gained ONE line over be's: a binary side returns null too. be gates blobs out before it ever calls weave3; a merge driver is handed whatever git has, so the gate belongs in the function.
  • Verb bodies in lite/index/merge.js (merge + install), main.js keeps its thin runMerge/runInstall wrappers, exactly as the other verbs are wired.
  • Driver command as proposed: <abs lite> merge %O %A %B -o %A -p %P. The abs path is /proc/self/exe (realpath of argv[0] as the fallback) — git runs the driver from the repo root with no PATH promise.
  • Argv: three positionals in git's own %O %A %B order, -o defaults to <ours>, -p feeds extOf (no -p = the generic "" lexer). %L ignored — there are no markers to size.
  • Attribute pattern is * merge=lite, as proposed: the generic "" lexer handles any unknown ext, and a known-ext pattern list would silently route the rest back to git's line merge. LITE-005's KnownExt gate is a PAGER paint question, not a merge one.
  • Idempotence: git config --get --fixed-value merge.lite.driver <cmd> — the value compares byte for byte, so no path of ours is ever read as a regex. The attributes file is read whole and its LINES compared to the exact line; nothing parses a config format.
  • Repo resolution is idx.openRepo(arg||cwd) with NO climb — byte-for-byte what lite index does. So lite install from a subdirectory fails the same way lite index does there; changing that is a separate ruling for both verbs.
  • Exit 1 is a THROW: quickjab has no process.exit binding and maps an uncaught throw to rc 1, which is exactly what git reads as a conflict. Cost: the runtime prefixes the plain-words message with JS exception: on stderr.
  • Conflict SIDE ORDER differs from be's goldens (XY where be has YX): be's RGA tie-break runs on real commit shas, the driver's three blobs fold under fixed synthetic ids. Same bytes on both sides, same span count, markerless — only the order is a function of the ids.

Blockers and bummers

  • JS exception: on every conflict. A driver's only non-zero exit is a throw, and the runtime stamps that prefix on the message before git prints its own CONFLICT (content) line. A quiet-exit binding in quickjab would clear it — out of scope here (zero quickjab edits), worth its own ticket.
  • A BINARY file falls back to git merge-file, which refuses binaries outright (rc 255): the output keeps the ours bytes and we exit non-zero saying so. Loud, not silent, but there is no content merge to be had — git's own binary behaviour is the same.
  • 4 of the 6 ported scenarios reproduce be's golden bytes exactly (dirty-overlap, multiedit-line, readd-line, plus stacked-conflict's three-sided reading); the two same-anchor cases differ in side order only, for the id reason above.
