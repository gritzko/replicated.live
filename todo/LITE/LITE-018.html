gritzko's ruling 2026-08-14: lite must give a SEAMLESS first experience. Bare lite (no view/verb specified) run inside a git repo indexes everything and opens the LITE-017 list view of the repo. Today bare lite at a tty opens an empty pager viewport and piped it throws usage (main.js:57 BROUSAGE, :329); the index exists only as the explicit lite index verb (LITE-006, lazy/watermark) and list never indexes. First run = index from scratch + list; every later bare run = the watermark no-op + list, instantly.

Input

Context

The pieces all exist; this ticket is WIRING, not new machinery.

  • main.js arg loop: no-args tty = empty pager, piped = BROUSAGE throw; a bare path arg opens the fs pager — that stays, only the ZERO-arg case changes.
  • lite index (LITE-006): resolves cwd to a git repo (root/.git/gitfile), builds <repo>/.git/be/, lists it in $HOME/.config/be/tracks; reentrant, indexes only the gap.
  • lite log/lite list already bringUp the index themselves where they need it — the precedent that a view owns its freshness.
  • lite list (LITE-017, staged in work/LITE-017): the github-style browser; its last-commit fuse rides the LITE-006 lane, so an unindexed repo is exactly the case where it starves.
  • Not in a git repo: bare lite keeps today's behavior (empty pager at a tty, usage when piped) — the fs pager story is not this ticket.

Goals

cd <any git repo>; lite — one command, no setup: first run visibly indexes (the LITE-006 progress reporting as-is), then the list view of the repo root opens; subsequent bare runs open list immediately.

  • Bare lite (zero args, no verb) in a git repo == lite index && lite list semantically, ONE process, index first.
  • --plain/piped bare run emits the list rows plain after the same bring-up — scripts get the board too.
  • Not a git repo → exactly today's bare behavior, byte for byte.
  • First-run cost is the LITE-006 full index; no new caps, no partial index — seamless beats instant on run one.
  • Reuse the ported be tests where they pin list output (LITE-017 test/list); the new legs cover: fresh repo first run (index built + list shown), second run (watermark no-op, same list), non-repo cwd (unchanged behavior), piped plain.

WIP

Design decisions

Made, not proposed — each confirmed against the code before it was built on.

  • THE THIRD LEAD WON: lite list OWNS the bring-up and the zero-arg branch just calls it (the lite log precedent). So bare lite, lite list and a clicked list row are the same code path and the same bytes — pinned by a cmp of lite against lite list --plain. Three lines in main.js total.
  • list already called bringUp, but only as a top-up: it opened the lane at the SMALL handle, so a repo with no .git/be at all was derived with a durable seal per commit. It now opens at idx.openIndex(gitdir, idx.fresh(gitdir)) — the bulk handle lite index uses. Measured on a 1468-commit repo: first run 1.39 s → 0.73 s (sys 76 ms → 8 ms), second run 71 ms.
  • THE PROBE CLIMBS, deliberately against the ticket's own lead. Every lite view opens with idx.openRepo(cwd, true) — list, cat, tree, blob, log, diff and main.js's own openPartial — so a no-climb probe would make bare lite the ONE thing in lite that dies in a subdirectory while lite list works. main.js inRepo() is that same call, used as a probe only: it closes what it opened and lets list open the repo for real, so no error of the view's is swallowed. Bare lite in a subdir lists the repo ROOT, exactly as bare lite list there already did.
  • BARE lite TRACKS, lite list DOES NOT. The goal says bare lite == lite index && lite list, and the tracks row is the index half; a read verb writing to $HOME is LITE-007's own no. One option, list(arg, {track:true}), default off. Both halves are pinned.
  • NO NEW OUTPUT. The first run reports through the LITE-006 stderr progress as-is and prints no summary line — a bare lite | grep gets the board and nothing else. list() completes the whole bring-up before it returns hunks, so the pager takes the tty strictly after indexing.
  • A PATH ARG IS UNCHANGED, in a repo or out of one: the zero-arg case is the only one this ticket touched, and both are pinned so nobody "fixes" it. A repo with no commits yet (git init, no HEAD) fails the probe and gets today's behaviour, not a crash.
  • ZERO quickjab edits.
