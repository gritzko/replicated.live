GET-045

be get <url>?<branch> fetches the DEFAULT branch and then records it under the name you asked for. pickWant turns a bare update into refs/update, which matches no advertised ref, so the lookup falls through to the HEAD-sha arm and returns refs/heads/main — and the wtlog row is written as ?update#<main tip>. The worktree now believes it sits on update at a commit that is not on update; a later get lines up against the wrong branch and a post would parent onto it. Every ?<branch> fetch to date resolved by LUCK: ?main looked right only because HEAD == main, so the fallback happened to land on the same sha.

  • The cell: shared/wire.js:136 — const full = wantRef.indexOf("refs/") === 0 ? wantRef : ("refs/" + wantRef); then an EXACT-name scan. "update" → "refs/update"; the ref is refs/heads/update, so nothing matches.
  • The fallthrough that hides it: wire.js:138-143 — HEAD-sha arm, then refs/heads/main, then refs/heads/master, then the first head, then refs[0]. An explicitly-named ref that was NOT found gets the same treatment as "no ref named at all".
  • Contract mismatch: the comment at wire.js:129-131 lists the accepted forms as "", "heads/x", "tags/x", "refs/…", a 40-hex — a BARE branch name is not among them, yet verbs/get/get.js hands rem.branch (bare, from <url>?<branch>) straight in. Caller and callee never agreed.
  • Blast radius: pickWant is shared by the spawned transports (ssh / local jab upload-pack) and by fetchHttp — every transport, and be head too, since it resolves the same way.

Goals

be get <url>?<branch> fetches THAT branch or fails by name — it never substitutes another branch, and never records a sha under a branch it does not belong to.

  • A bare <name> resolves as a branch: try refs/heads/<name>, then refs/tags/<name>, keeping the existing refs/…, heads/x, tags/x and 40-hex forms working.
  • An explicit wantRef that matches NOTHING is a named error in plain words ("no branch update on <url>", listing nothing else) — never a fallback. The HEAD → main → master → first-head chain stays, but ONLY for the empty-wantRef (default-branch) case.
  • Repro test with a two-branch local source asserting BOTH halves: ?<branch> lands that branch's tip, and ?<absent> errors instead of cloning the default.
  • Audit the pin the wtlog/refs rows carry after every form, so no row can name a branch the sha is not on.

Constraints

  • One fix in pickWant — it serves http and the spawned transports alike; do not fork per-transport matching.
  • The branch codec stays authoritative: refReturn → branchlib.fromWireRef(name, "") with main → trunk "" (SUBS-050); do not hand-roll a name→branch mapping.
  • Do not touch the advert drain (drainAdvert) or the want/have body — this is ref SELECTION only.
  • Errors in plain words, no bare codes.

WIP

Design decisions

  • The candidate list is a FUNCTION of the wantRef shape (wantCandidates), not a chain of ifs at the match site: refs/… → itself; heads/x → refs/heads/x; tags/x → refs/tags/x then refs/heads/tags/x (see below); anything else is a BARE BRANCH NAME → refs/heads/<name> then refs/tags/<name>. One fix, all transports (http + spawned ssh/local), no per-transport forking.
  • A NON-EMPTY wantRef that matches no candidate THROWS in pickWant — the default chain (HEAD sha → main → master → first head → refs[0]) is now unreachable unless wantRef is empty. That is the whole cure: the fallback arms were never wrong, they were reached by a caller who HAD named a ref.
  • The error names the branch AND the remote: pickWant takes an optional 4th arg where (fetch passes remoteUri, fetchHttp passes url), so the message reads `wire.fetch: no branch update on https://… — no bare codes, nothing else listed. The noun follows the form asked for: branch for a bare name, tag for tags/x, ref for a full refs/…`.
  • A tags/x gets a SECOND candidate, refs/heads/tags/x: a be store keys a tag as the ref tags/x and serve.js advertises EVERY key through branchlib.wireRef, so the git-shaped refs/tags/x misses on a be peer — be get be:<store>/.be?tags/v1 silently cloned main (verified, RED below). Same bug, same cell, so it is cured here rather than left for a second ticket.
  • refReturn / branchlib.fromWireRef UNTOUCHED — the branch codec stays the only name→branch mapping, per Constraints.
  • The recorded track keeps coming from rem.branch in get.js (?main still records ?main, not trunk ""). Normalising main→trunk at the RECORD is NOT this ticket: on a peer whose HEAD is master while main also exists, a wt recorded as trunk would re-resolve through the empty-wantRef chain and land MASTER — the same class of silent switch this ticket kills. Left for gritzko as a separate question.
  • The new failure path had to be made CLEAN, because it is new: (a) seedRemote minted <wt>/.be + the shard BEFORE the fetch, and a failed fetch left them behind — an empty .be then CRASHES the obvious retry (pre-existing, see Blockers), so the fetch is now try/caught and sheds exactly what THIS run created; (b) the local-exec peer answered the hung-up client with a courtesy NAK and dumped a JS stack (Error: Broken pipe) over the user's plain-words error — serve.js now treats a hung-up client as a clean end of session.
