GET-045: ?/<project>/<branch> — the branch form status prints does not resolve; get rejects its own display form

Now
OPEN
Sev
HIGH

status renders a sub's branch project-qualified (?/libdog/.jab/JS-101) and the sub ANCHOR stores that same qualified string, but REFS only ever knows the bare .jab/JS-101. get hands the whole string to resolveRef, gets nothing, and dies with cannot resolve. Pasting back what status just printed is a hard error, and the qualified name in the anchor is unresolvable too — which is what leaves GET-042's no-op with no escape hatch.

Input

Context

Found 2026-07-14 on journal/jab/dog: the branch named in every display and in the anchor cannot be resolved by the verb that consumes it.

  • jab get ?/libdog/.jab/JS-101 (quoted or not) -> be get: cannot resolve ?/libdog/.jab/JS-101.
  • jab status prints exactly that name: ?/libdog/.jab/JS-101 367 ok (behind 1).
  • Probed on the sub store: resolveRef("/libdog/.jab/JS-101") -> nothing; resolveRef(".jab/JS-101") -> 8ebbfd35.
  • Also unresolvable: libdog/.jab/JS-101, /libdog/.jab, JS-101 — only the exact bare .jab/JS-101 hits.
  • The anchor tip row stores the QUALIFIED form ?/libdog/.jab/JS-101#79612854 — the stored branch is itself unresolvable.
  • /libdog is the PROJECT selector (as in ?/libdog), not part of the ref — ?/<project>/<branch> is never split.

Goals

The branch name status prints round-trips: get accepts it, and the anchor stores a form that resolves.

  • Split ?/<project>/<branch> into project + branch before resolveRef, or stop qualifying the display.
  • One canonical branch spelling shared by status, the anchor writer, and get's resolver.
  • An unresolvable branch stays a LOUD error — this ticket removes the false negative, not the error.

Constraints

Repro test first (work); fix in beagle-ext (JS), no C changes; minimal diff.

  • Never parse the URI by hand or with a regex (work "Things NOT TO DO") — go through the URI class.
  • Sub-branch shape is /<title>/.<parent>[/<parent_branch>] (shared/submount.js header) — check vs what REFS stores.
  • Check native C be get/be status spelling before settling the canonical form (parity).

WIP

Design decisions

Open — the ambiguity is real and needs a rule, since a branch name may itself contain /.

  • ?/libdog/.jab/JS-101 splits only if the FIRST segment is read as a project selector; no such rule exists today.
  • Suspect the anchor writer and display share one qualifier while resolveRef wants the bare ref — find the ONE divergence.
  • Fixing the display alone is not enough: the anchor's stored branch must resolve, or GET-042 stays broken.
