GET-059: get content-tests a file equal to the target, then discards the verdict — stamp it

RULING (gritzko, 2026-08-04): status never restamps (membership only, STATUS-011 stands); the restamp belongs to the verbs that already paid for the content test — unknown timestamp → test (maybe write) → stamp. get's tested-equal skip (verbs/get/get.js:1062-1064) reads the on-disk file, proves it byte-equal to the incoming target via checkout.leafUnchanged, and returns with NO stamp. The file's bytes ARE the new baseline blob — the identical truth claim the GET-049 clean-overwrite stamp makes 30 lines down (get.js:1096-1099) — but the mtime stays off the stamp-set, so EVERY later be status re-opens and re-hashes it, forever. Measured: be status in be/ opens ~780 tracked files per run (test/ tree, mtimes from git checkout/editors). Siblings: GET-049 (stamp what get writes), GET-050 (band-stamp carried/woven), POST-037 (post's half of the same ruling).

Goals

get leaves every file it content-proved equal to the new base carrying a stamp-set mtime, so the next status confirms it clean with zero content reads.

  • Repro-first: a wt whose files byte-equal the incoming target but carry off-stamp-set mtimes → get → assert every tested-equal file's mtime ∈ the wtlog stamp-set AND the next status does zero content reads on them (the STATUS-011 observable; test/post/restamp/run.sh + its .stampchk.js checker is the pattern to reuse).
  • The GET-058 noop cell verified either way and the finding recorded here.

Constraints

  • A still-dirty file (bytes != new base) must NEVER be stamped — stamp only what a content test THIS RUN proved equal to the new base.
  • Row-before-stamp: the mtime is always an ASSIGNED wtlog row ts (g.stampTs), never a resampled now — POST-029's ordering holds.
  • Symlinks stay unstamped (setMtime follows the link, get.js:1099 guard); stampTs == null legs stay no-stamp.
  • No new reads: never descend a Merkle-pruned subtree to stamp it.
  • Minimal diff in verbs/get/get.js (+ shared/checkout.js only if the equal-test must surface its verdict); status/classify untouched — status stays a strict reader.

WIP

Design decisions

  1. The stamp goes AT the skip, not after it. The skip's own if IS the content test, so the verdict never has to travel: the return grows a body carrying the GET-049 line verbatim — if (g.stampTs != null && kind !== "l") trySetMtime(full, g.stampTs). shared/checkout.js is untouched: nothing needs to surface a verdict that is already local.
  2. Same guards, same ts, no new state. g.stampTs is the ASSIGNED get row ts (POST-029), symlinks stay unstamped (setMtime follows the link), and the stampTs == null legs stay no-stamp — restorePath builds its own ctx._get with NO stampTs field at all, so g.stampTs != null is false there by construction.
  3. ZERO new reads. The stamp rides a test get had already paid for; a Merkle-pruned subtree is never visited, so nothing under it is opened, read or stamped (the GET-050 carried/pruned files keep their own band/clone stamps).
  4. The dirty side is untouched: bytes that FAIL the equal test fall through to the quad exactly as before (weave/ours/con → bandStamp under the ceiling), so no still-dirty file can be laundered into the stamp-set. The test asserts that in the same run.
  5. The GET-058 noop cell gets NO stamp — and the reason is stronger than "it did not content-test" (see below).

The GET-058 noop cell (verified, not assumed)

v === "noop" in the WRITE leaf takes no stamp, on two independent grounds:

  1. Ordering: the leafUnchanged skip runs EARLIER in the same leaf. So every path that reaches the quad either does not exist on disk (nothing to stamp), or was just content-tested and proved NOT equal to the target. wtChar may well have read the bytes to reach the verdict — it compares them to the BASE blob — but the run's verdict about the NEW BASE is already in: not equal. A stamp there would be exactly the false clean claim the ruling forbids.
  2. Reachability: the cell is dead in this leaf anyway. noop needs the quad key .., .x or xx; xx needs track x, impossible past the if (!newSha) delete branch; ../.x need trackChar(oldSha, newSha) === '.', i.e. oldSha === newSha — and reconcileDir Merkle-prunes precisely those entries (ne.sha === oe.sha → continue) unless g.noPrune. But noPrune = force || (sameTip && !fresh) while recover = !force && sameTip && !fresh: with force the whole quad block is bypassed (if (!g.force && !g.fresh)), and without it noPrune implies recover, which forces tch = CH.advanced. restorePath (the other noPrune: true leg) sets force = true. So the track char is never . there.

Both legs were checked on the live binary, not on paper: (a) an instrumented leaf() shows that the one natural "equal shas" candidate — a mode-only change (chmod +x, identical blob) — never even reaches the leaf, because the prune compares blob shas; (b) rigging if (v === "noop") to THROW left the whole 354-case suite green (only the pre-existing rowcache pty failure), so no case in the suite enters the cell.

Side observation, NOT this ticket: since the prune is sha-only and status is mode-blind, a mode-only change (chmod +x with identical bytes) is silently DROPPED by get and then reads clean. Worth its own ticket if that matters.
