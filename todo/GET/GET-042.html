GET-042: get on a mounted sub re-gets the anchor's own pin — a success-shaped no-op that can never advance

Now:
OPEN
Sev:
HIGH

get on a mounted sub reads the checkout target from the SUB ANCHOR's recorded tip row, so it "advances" to the pin it is already at, prints a normal get record, and exits 0. The parent's gitlink and the sub's branch tip are both ignored. When they move ahead the sub is stuck FOREVER: every get reports success, status keeps saying behind 1, and no command moves the tree. Nothing is missing — the target commit is already in the local store.

Input

Context

Found 2026-07-14 on journal/jab/dog, where every source of truth already named 8ebbfd35 and only the wt lagged at 79612854.

  • Parent journal/jab pins dog -> 8ebbfd35; sub branch .jab/JS-101 tip -> 8ebbfd35; the object is PRESENT locally.
  • Sub wt baseline sits at 79612854; jab get ///jab/dog prints get ?.jab/JS-101#79612854 and exits 0.
  • jab status after that get is byte-identical to before: 367 ok (behind 1) + a miss ?8ebbfd35#bump libabc ver... row.
  • The anchor's tip row is the culprit source: 26710IOvB_ get ?/libdog/.jab/JS-101#79612854... — get honours THAT pin.
  • No fetch can help (the object is local), so this is a target-selection bug, not a transport one.
  • Consequence: a sub whose parent gitlink advances is unreachable by get — the only documented update verb (work).

Goals

get on a mounted sub advances to the intended commit, or refuses LOUDLY — never a success-shaped no-op.

  • Decide and document the authority: the parent's gitlink pin, the sub's tracked branch tip, or an explicit rev arg.
  • A get that changes nothing because it is ALREADY at the target says so; a get that cannot reach the target fails.
  • status's behind N must be actionable — some command must clear it.

Constraints

Repro test first (work); fix in beagle-ext (JS), no C changes; minimal diff.

  • SUBS-053 is reordering mount() in the same area — coordinate, do not collide.
  • Check native C be get for a behind sub before choosing the authority (parity target).
  • Do not weaken GET-037 atomicity or the Submodules pin semantics.

WIP

Design decisions

Nothing settled — the authority question is genuinely open and gritzko should rule.

  • Candidate A: the parent gitlink is authoritative (a sub is a pin). Then a bare get in the SUB should refuse, not no-op.
  • Candidate B: the sub's tracked branch tip is authoritative. Then get must resolve the branch, not replay the pin.
  • The anchor's recorded pin is a HISTORY row, not a target — reading it as the target is what makes the no-op.
  • GET-045 blocks the explicit escape hatch: the branch form status prints does not resolve.
