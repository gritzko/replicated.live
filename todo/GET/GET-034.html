GET-034: graf/GET.c base_ids/tgt_ids membership maps sized 4096 but GET_MAX_VERS=200000 → silent id drop (u8bFeed1 SNOROOM) for a file with >4096 versions

graf/GET.c builds per-side membership maps base_ids / tgt_ids with only 4096 slots, while the version cap GET_MAX_VERS is 200000. A file with more than 4096 versions overruns the map: u8bFeed1 returns SNOROOM and the id is SILENTLY DROPPED (no error surfaced), so membership is computed against an incomplete set — a correctness loss, not a crash. Spotted auditing the weave path while fixing PATCH-004; out of that ticket's scope. Method Issues.

Input

Context

  • graf/GET.c sizes base_ids/tgt_ids at 4096 entries; GET_MAX_VERS = 200000. The two limits disagree by ~50x, so any file with >4096 versions exceeds the map.
  • The overflow path is u8bFeed1(...) returning SNOROOM whose result is not gated, so the membership id is dropped without a trace (silent wrong answer in get/diff sizing).
  • Found by the PATCH-004 worker (cherry-pick hashlet fix); flagged, not acted on, as it is unrelated to the cherry-pick use-after-scope.

Goals

  • Membership maps cover the full version range (size to GET_MAX_VERS, or grow on demand) so no id is dropped for a large-history file.
  • Any capacity overrun is a LOUD error (checked u8bFeed1/sFeed return), never a silent SNOROOM drop.

Constraints

  • Native graf. ABC bounds-checking (no fixed cap that just moves the cliff). Repro-first (CLAUDE.md §17): a file with >4096 versions exercised through the graf GET path, asserting every membership id is present (RED today). Don't regress small-history get.
