GET-055: a clone into a wt that already has an EMPTY .be DIR dies with a raw ToBigInt TypeError after the pack has landed

Now:
OPEN
Sev:
MED

mkdir .be in an otherwise green-field worktree is enough: jab get <remote> fetches, lands the pack, writes refs and wtlog — and then throws TypeError: Invalid argument type in ToBigInt operation, checking out ZERO files. Remove the empty .be and the identical clone succeeds. The store is left complete-but-unchecked-out, so a retry in the same dir now takes the update path over a wtlog it never finished. Found while converting the clone path to KEEP-006's repack (JAB-020); NOT caused by it — baseline be/ sources on the tmp-pack path fail identically, so the bug predates the conversion and is transport- and repo-independent. Also breaks the plain-words rule: a raw JSC TypeError is not a user-facing error (Errors). Method Issues.

Input

Context

  • Repro (2026-07-27), no submodules, 6 objects: mkdir -p wt/.be && cd wt && jab get ssh://localhost/<bare> → get: 6/6 objects, 0 MB in, 1 log(s) then JS exception: TypeError: Invalid argument type in ToBigInt operation; ls = 0 files.
  • The SAME command in a wt with no .be at all: clean clone, files checked out, jab log walks the history.
  • Not the repack: baseline ~/jsrc sources (GET-044 tmp-pack path, ~/bin/jab) throw the identical TypeError on the identical setup.
  • Not submodule-related: first hit on c-rdx (has .gitmodules), reproduced on a 1-commit bare repo with none.
  • The shard IS complete when it throws: 0000000001.keeper + a .keeper.idx run + refs + .be/wtlog all written.
  • How the empty .be arises in practice: a FAILED fetch leaves one behind (bad remote path → wire.fetch: peer advertised no usable ref), so the user's natural retry hits this on the second run.

Goals

A clone into a wt carrying an empty (or otherwise unusable) .be either completes or refuses in plain words — never a raw engine TypeError with a half-populated store.

  • Decide what an empty .be DIR means: green-field to adopt, or a wt to refuse.
  • Whatever the ruling, the failure path says so in normal words (Errors).
  • No half state: a refusal must not leave a landed pack and a wtlog behind.

Constraints

  • Plain words at the boundary, never an ok64 code or an engine type error.
  • A .be that is a redirect FILE (secondary wt) is a DIFFERENT case and already works — do not disturb it (GET-041).

WIP

Design decisions

Nothing ruled yet. The suspicion — unverified, stated as such — is the branch pick in verbs/get/get.js seedRemote: be.treeAt(wt) sees a .be and yields an anchor with no usable baseline, so the UPDATE leg runs (oldTipOf(info.bePath) over an absent wtlog) instead of the green-field one. The ToBigInt is then a BigInt(undefined) downstream of that. NOT confirmed — no stack is available (the release build deliberately does not read .stack), so the first task is to localise it.
