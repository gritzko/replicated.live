GET-044 JS: wire.fetch buffers the WHOLE pack in RAM — stream to a tmp file in the shard

Now
OPEN
Sev
HIGH

jab get of a big remote holds the entire packfile in process memory: wire.js fetch reads the raw pack to EOF into a chunks[] array and then CONCATENATES it into one Uint8Array — peak RSS 2× pack size — and ingest writes that single buffer out afterwards. Observed live this session: jab get ssh://git@github.com/torvalds/linux.git (pid 14199) at RSS 2.78 GB after 2.7 GB received, fd table shows NO store file open (only the ssh pipe) — a Linux-scale pack (3.5 GB) peaks at ~7 GB and OOMs modest boxes. Fix = git's own model: stream the pack into a tmp_pack_* file INSIDE the destination shard, hash as it streams, index/ingest off mmap, atomically rename into place on a verified trailer. Method: work.

Context

  • Live evidence 2026-07-14: jab get ssh://git@github.com/torvalds/linux.git from ~/tmp/try; ssh child moving ~2.8 MB/s; jab RSS tracked received bytes 1:1 (2 785 424 kB RSS vs rchar 2.7 GB); /proc/14199/fd = tty, urandom, pipe, timerfd — no store fd, nothing durable until EOF.
  • Locus: be/shared/wire.js "read the raw pack to EOF" (fetch L143-156, same shape in the second reader L174-191): chunks.push(...) then out.set(c, off) — chunks + out live simultaneously, so peak = 2× pack.
  • Downstream be/shared/ingest.js (clone/add → writeBytes, e.g. 0000000001.keeper) takes the whole buffer; verbs/get/get.js L208/L218/L230 passes f.pack around by value.
  • An abort/OOM mid-fetch loses everything received; nothing is resumable and nothing partial ever touches disk for later salvage.
  • CONFIRMED HARD FAIL 2026-07-14: the same clone DIED at EOF concat — JS exception: RangeError: length too large / Uint8Array@[native code] / readToEof@ / fetch@ / seedRemote@ / handleSeed@ / get@ — the pack exceeds the engine's max Uint8Array length, so ANY large-repo clone deterministically crashes after the full download (~50 min discarded). Not just an OOM risk; bumped MED→HIGH.

Goals

  • wire.fetch streams the incoming pack to a tmp file (e.g. tmp_pack_*) in the DESTINATION shard dir, constant memory, hashing the trailer as it streams.
  • ingest.clone/ingest.add accept the tmp-file path (read/mmap), and land it by ATOMIC rename once the pack sha trailer verifies; abort = unlink the tmp file, store untouched.
  • A Linux-scale clone (multi-GB pack) completes with bounded RSS (target: tens of MB, not pack-sized).

Constraints

  • Tmp file lives in the shard's own dir (same filesystem → rename is atomic); NOT /tmp (often tmpfs = RAM again, and cross-device rename isn't atomic).
  • JS only (be/, run via jab); keep the fetch() -> {pack, refs, ...} callers working — the small local/be:// paths may keep the in-memory shape if that simplifies, but the ssh/git wire path must stream.
  • Repro-first per work: a test with a pack ≫ some artificial RSS cap (or an instrumented byte counter) proving bounded buffering; no editing unrelated tests.
  • ≤2-line GET-044 comments; ticket-coded ≤64-char commits.

WIP

Design decisions

  • Follow git's quarantine pattern: stream → tmp_pack_<rand> in the shard, verify the 20-byte sha1 trailer, then rename into the keeper log name (or hand the verified file to ingest).
  • Stretch (separate ticket if pursued): resumable fetch off a kept tmp file; ingest reading via mmap instead of a full read.
