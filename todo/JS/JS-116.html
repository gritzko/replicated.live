JS-116: keeper.idx run lifecycle — compact, tail-index, ron60 run names

Now: DONE

The shard's .keeper.idx LSM runs only ever accumulate: every land()/post adds a run, patch adds two (per-log + reindexShard), nothing ever compacts or unlinks, and the native leaves hard-cap queries at 64 runs (jab/index.hpp "too many runs"). Staleness is undetected: store.js diskIndex() checks only that ONE run exists, so a .keeper log landed without its run leaves objects silently unlocatable (TEST-003 quirk, PATCH-011's motive). This ticket wires the maintenance loop into be/ over the existing abc.index leaves (JS-056).

Input

Context

  • be/shared/store.js:206-217 diskIndex(): existence-only check; opens ALL runs; no compaction, no staleness check; a run present but short → silent misses (locate() only skips unknown-file_id rows, store.js:278).
  • be/shared/ingest.js buildIndex()/land()/reindexShard(): one run per landed pack, plus a combined run per patch fetch (verbs/patch/fetchleg.js:57-58,96-97); land() writes the log THEN the run (ingest.js:155-157) — a crash between leaves the exact stale state.
  • jab/cont.cpp abc.index: compact() exists (1/8 ladder via _compact_wh128) but names merged runs String(seq).padStart(8)+ext with _seq = parseInt(name,10) — NaN on ron-named runs, and 00000000.keeper.idx sorts BEFORE ron64 names, corrupting oldest-first/newest-wins order.
  • Run PACK summary rows already carry coverage: key=(12<<20|file_id)<<4|0xF, val=count<<32|logBytes-12 (ingest.js:47-49,100-104) — last-indexed-file-and-length is recoverable by ranging the 0xF rows.
  • Spec-code discrepancy filed off this ticket as JS-117: writers open a NEW .keeper log per post/land where PackLog wants tail-append — once that lands, goal 5's grown-last-file case becomes a local reality, not native-interop-only.

Goals

  1. Compact on open when the shard has >32 .keeper.idx runs (half the native 64-run cap).
  2. After adding a run (land/post/reindex): if the stack violates the 1/8 invariant, compact (the _compact_ leaf returns m; loop while m>=2, as abc.index.compact already does).
  3. The index exposes its run file list, so be/ can unlink collapsed runs and report coverage.
  4. Maintenance triggers from any verb that opens the idx (the lazy diskIndex() path in store.locate()).
  5. On open: no run at all, OR the 0xF coverage rows short of io.stat over NNNNNNNNNN.keeper logs (unindexed file / grown last file) → build the tail run via buildIndex(), persisted, replacing today's ephemeral full in-RAM rebuild (store.js:223-252).

Constraints

  • Run naming scheme is ron60: merged/tail runs are <ron60>.keeper.idx like buildIndex's, so name-sort == age-sort; abc.index's _seq/padStart naming must not leak into shard dirs (fix in cont.cpp or override naming from be/).
  • Read path stays native-leaf-only (JS-056 rule: no format logic in JS beyond marshalling); compaction reuses HITwh128Compact via the existing _compact_wh128 leaf.
  • Writers must stay crash-safe: temp + rename for merged runs (abc.index.compact already books .tmp + renames); sources unlinked only after the rename.
  • Do not break the read-only open: a verb on a read-only store must still open a stale/overfull idx (skip maintenance on EROFS, warn or fall back).

WIP

Design decisions

  • Coverage check = range the 0xF PACK rows (newest-wins across runs), compare per-file logBytes against io.stat; both missing files and a grown tail fall out of the one comparison.
  • reindexShard() becomes redundant once 2+5 land — patch's fetchleg drops to land() alone; delist after verifying.
