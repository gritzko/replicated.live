JS-026: richer extension exit codes (jabc has no process.exit)

Now: OPEN Sev: LOW

Surfaced by JS-025. be <name> forks jabc bin/<name>.js; the script's exit becomes be's exit. But jabc exposes no process.exit(code), so a script can only signal 0 (clean return) or non-zero (an uncaught throw → exit 1). An extension that wants a specific exit code (e.g. be status-style "1 = dirty") cannot set it. Method: Issues.

Input

Context

  • JS-025 dispatch makes the script's process exit be's exit code, but jabc (js/main.cpp) only maps clean-return→0 / uncaught-exception→1.
  • A bin/status.js reimplementation (the SDK-validation goal) wants the same exit semantics as native be status (0 clean, non-zero dirty/ahead/behind).

Goals

  • Add process.exit(code) (and/or a process.exitCode settable global) to the jabc runtime so a script can set its own process exit status.
  • be <name> then propagates that exact code (already wired by JS-025).

Constraints

  • Small js/main.cpp change; must still drain the event loop / run GC deallocators before exit (the existing teardown order — context release before FILECloseAll). process.exit should flush + tear down cleanly, not _exit.
  • Keep JABC rule #4 (no held JS refs); a Node-ish process.exitCode honored at natural drain is the cleaner fit than an abrupt exit().

WIP

Design decisions

  • (open) process.exitCode (read at end of run, Node-style) vs process.exit(n) (immediate). Prefer exitCode to preserve the loop-drain + GC teardown.
