JS-120: the JS readers never close() their maps — one why drive eats ~1000 fds, blinding the wt oracle

Now:
OPEN
Sev:
HIGH

RULING (gritzko, chat 2026-07-20): abc.close()/the buffer close now REALLY closes the file and unmaps (the ABC-020 release binding landed in jab, io.cpp:578 io._munmap = munmap + close(fd) + fd=-1) — so the remaining defect is on the JS side: *be/ JS maps and never closes*. Double-check the jab-side semantics first, then make every JS reader release deterministically. Discovered as the root cause of BRO-040 (pager context rot); recurrence of the same disease as JSQUE-021DONE (verb-load path) in the ulog/store read path.

Input

Context

  • shared/ulog.js:42-48 each() maps (abc.mmap("ULOG", path, "r")), iterates, and RETURNS — no close on ANY path, success or throw; _withRo (:265) already has the map-run-close idiom the readers should use.
  • Measured (BRO-040, pty + headless): ONE why <file> drive consumes 1007 fds; ordinary cat/status drives leak 17-20 each. Differential proof: under ulimit -n 64, jab status completes, jab why CMakeLists.txt dies Error: No file descriptors available.
  • Downstream damage (why this is HIGH, not hygiene): exhaustion makes abc.mmap throw, ulog.each swallows it (catch (e) { return; } → zero rows), anchors() reads that as "no worktree", the pager's file→dir oracle blinds, and a FILE persists as a dir context segment — the BRO-040 rot, with the error kind varying by which layer notices first.
  • ABC-020 evidence (2026-07-19 probe, that ticket): a baseline with no release exhausts at ~1000 maps — exactly the number measured here, so the JS path is mapping once per object and never releasing.
  • Ancestor JSQUE-021DONE fixed the resident verb-load leg; the read path was never converted. JS-100DONE already flagged "an uncertain ulog reader map".

Goals

  • Every JS map is released deterministically at its owner's boundary: readers map → use → close, and a resident session's fd count PLATEAUS across repeated drives instead of climbing.
  • Verify FIRST, in ./jab, that the close/unmap binding does what the ruling says: munmap + close(2) + fd=-1, idempotent, and safe against the GC finalizer firing later on the same record. Report the finding before relying on it.
  • Repro-gated: an fd-count (or lowered-RLIMIT) probe over N × why/status drives is flat after the fix; the BRO-040 4-step click dance stops corrupting the context.

Constraints

  • Cure is close-after-use / open-once — NEVER a parallel reader or a byte-copy read path (that shape was rm -rf-ed once already; see the BE-050/JSQUE-021 lineage).
  • Do NOT reimplement unmap/close logic in JS or in a new binding — use what jab exposes; if the binding is wrong, report, do not patch around it.
  • The ABC-020 in-ticket "REWORK RULING" (fd at close, munmap at GC) is DISAVOWED by gritzko — do not build to it; the live ruling is release-everything-on-close.
  • A stale view after close must not crash the reader — check what the landed binding actually leaves behind before converting call sites.
  • Mask half is BRO-040 (b): ulog.each must tell an absent log from a resource error; coordinate, do not duplicate.

Blockers and bummers

  • BLOCKED on a jab-side ruling: abc.close does NOT release a map whose bytes were already MATERIALIZED — and every real reader materializes. abc.close (cont.cpp:422) is transfer-first (b.transfer() → husk → msync → trim → io._munmap(husk)); after any byte-pointer materialization (the native cursor next(), the row getters abc._ulog_time/_verb/_uri — all GetTypedArrayBytesPtr), ArrayBuffer.transfer() COPIES instead of moving, so the husk carries no mapping, io._munmap(husk) finds no live FILE map at that base, returns NONE silently, and the fd survives to GC.
  • Orchestrator-verified 2026-07-20 (differential probe, scratch fdprobe.js, N cycles of map+close on a real .be ULOG): under ulimit -n 64, the NO-READ variant runs 400 cycles flat; the variant that adds ONE log.next() dies No file descriptors available after *57 cycles*. Unbounded, both finish 1500 — so release is DEFERRED TO GC, not absent; a fast drive (1005 maps) simply outruns the collector. jab's own test/mmapfd.js passes because it never reads through the container.
  • The obvious reorder is NOT free: munmap-live-then-transfer SIGSEGVs (transfer's copy reads unmapped pages), so neutralizing stale views and releasing the fd need a mechanism other than transfer(). This is ABC-020 design space, whose rework rulings gritzko DISAVOWED — needs his verdict, not a worker's.
  • Consequence for this ticket: the JS conversion is correct and staged but INERT until the binding releases read maps; forced-release measurement shows it then plateaus (93/93/94/93/93 fds over 6 why drives), so no store/why/blame sweep is needed.
  • BRO-040 (b) mask is NOT made trivial by this fix — each() keeps catch (e) { return; }; keep (b) open.
