JS-117: every post/land opens a new .keeper log; PackLog spec wants tail-append

Now
DONE

Spec-code discrepancy (filed off JS-116). PackLog rules: "one log holds many packs back-to-back; a new log starts only past a size threshold, so a lone local commit appends to the tail rather than opening a file". The be JS writers never append: every event that lands objects books a complete standalone pack as the next-numbered NNNNNNNNNN.keeper. A working shard accumulates one tiny log per commit and per fetch — file_id is 20 bits (1M logs), each log costs a readdir entry, an mmap, and a fidMap slot (store.js), and the wire reframer loses the batch-sendfile shape the spec's back-to-back layout buys.

Input

Context

  • New-log events today: verbs/post/fold-commit.js:155 writePack() → nextLogName() per EVERY post; shared/ingest.js:147-158 land() → logName(max+1) per EVERY fetched/pushed pack (patch/fetchleg per fetch); clone() → 0000000001.keeper.
  • All three ride git.pack.book/.feed/.finish (jab cont.cpp) + writeBytes() — create/truncate only; no tail-append path exists in be JS.
  • The idx format already supports many packs per log: the 0xF bookmark row key=(first_off<<20|file_id)<<4|0xF, val=count<<32|extent marks each appended pack (ingest.js:47-49); object rows carry absolute in-file offsets (offset40).
  • Extent comes from the INDEX, not the PACK header (PackLog "extent is its byte length, no trailer") — so a torn tail past the last bookmark is invisible to readers, making append crash-tolerant by construction.

Goals

  1. Tail-append: post and land() append the new pack's records to the highest-numbered .keeper log while it is under the size threshold; a new log only past the threshold (and at clone).
  2. Each appended pack gets its 0xF bookmark row (first_off = pre-append length) and object rows with absolute offsets, in a fresh ron60 .keeper.idx run — same recipe as buildIndex, offsets rebased.
  3. Crash order: append records, sync, THEN write the idx run; on a torn append, recovery = truncate the log to the last indexed extent (or just leave it — unindexed bytes are dead).
  4. Wire reframing and locate() keep working on multi-pack logs (bookmark extents drive per-pack reconstruction, PackLog "no varint scan").

Constraints

  • git.pack.book writes a 12-byte PACK header + finish; an append needs a records-only feed at an offset — likely a jab binding gap (cont.cpp append mode or a records-only book) — measure before building; if jab work is needed, split it out and link here.
  • pk.scan (PIDXScan) reads the header object count — it cannot index the appended tail; tail indexing must come from the writer (it knows its records) or a bookmark-driven scan, NOT from re-scanning the whole log (JS-116 goal 5 must stay compatible: its coverage check compares against bookmark extents, not header count).
  • Existing logs are never mutated in place (PackLog "never mutated"): append only at the tail, offsets stay stable.
  • OFS_DELTA stays pack-local (the PackLog invariant): deltas in an appended pack must only reference records within that same appended pack.
  • Size threshold: pick one (spec names none); offset40 allows 1 TiB/file — something like 64-512 MiB; make it one named const, not scattered.

WIP

Design decisions

  • Ruled 2026-07-10 (gritzko): new-log-count per op is 0 in most cases, 1 only on clone — the three goldens asserting a NEW .keeper per landing (patch-fetch-cross-store, patch-fetch-wt-cross-store, wire-ssh-update-secondary) are amended to detect landing positively and assert count-unchanged.
  • Implemented: threshold KEEP_LOG_MAX = 64 MiB (one const, ingest.js); no jab binding needed — records composed in a RAM scratch pack, appended via io.resize + mapped tail-copy + msync.
