APPROVED (gritzko, 2026-08-11): vendor rpmalloc as quickjab's JS-runtime allocator. Post-STATUS-022-sweep profile: musl mallocng is 45.9% of quickjab's 4.27 s cold frame (1.01 M minor faults — mallocng punts big allocations to mmap/munmap); JAB-036's shadow experiment already measured the cure: rpmalloc 1.4.5 (one .c) wired as JSMallocFunctions via JS_NewRuntime2, engine untouched, io/libdog still on musl — 7.0 -> 4.6 s (-33%) pre-fixes, output byte-identical, +20 KB stripped. This ticket lands it: vendored+pinned, build-gated, measured on the current tree.

WIP

Design decisions

  • Gate: option(QJAB_RPMALLOC "..." ON) in quickjab/CMakeLists.txt, one greppable name for both the cmake option and the C define (target_compile_definitions(quickjab PRIVATE QJAB_RPMALLOC), same for the quickjab_boot jsrcpack leg). OFF appends nothing and defines nothing: rpmalloc.c is not even compiled, main.c takes the plain JS_NewRuntime() arm — that is the ASAN/leak leg.
  • Shim table, all 5 JSMallocFunctions fields of quickjs-ng v0.10.1 (quickjs.h:398) covered, exactly the set the shadow shimmed: js_calloc->rpcalloc, js_malloc->rpmalloc, js_free->rpfree, js_realloc->rprealloc, js_malloc_usable_size->rpmalloc_usable_size. qjs calls usable_size on EVERY alloc/free for its malloc_size accounting (quickjs.c:1467-1536), so a stub would break JS_GetMemoryUsage/GC pacing — it is shimmed for real.
  • Lifecycle, same as the shadow: rpmalloc_initialize() first line of JSInit, no rpmalloc_finalize() anywhere; rpmalloc's spans die with the process. No rpmalloc_thread_initialize needed: the linked qjs target is cutils+libregexp+libunicode+quickjs+xsum WITHOUT quickjs-libc, so there is no Worker/js_thread, and quickjab's own .c files call no pthread_create — the runtime is single-threaded. Not finalizing is also WHY the OFF leg has to exist for leak CI.
  • Scope unchanged from the approval: only JSMallocFunctions is swapped, io/libdog/abc/main keep musl malloc. Nothing in qjs/ patched, nothing in jab/ or be/ touched.
  • DEVIATION from the shadow main.c (deliberate, the rest is lifted verbatim): the shadow's experiment scaffolding is NOT landed — the RP_N[4] per-call counters + QJ_ALLOC_STATS dump, and the RP_WANT / prof_interrupt / QJ_JS_PROF alloc-clock JS stack sampler (JAB-036's measuring rig). They cost a counter increment on every js_malloc and only served the profile. Shim bodies are otherwise identical to the shadow's, sans the counters.
  • ALSO not lifted: the shadow tree predates STATUS-020, so its CMakeLists/main.c diff removes igno.c / JABCInstallIgno / JABCUninstallIgno / the JABCigno test. Those removals are shadow staleness, not wiring — dropped; the rp copy keeps igno intact.
  • rpmalloc LOCAL MODIFICATIONS: exactly one, a 2-line vendor stamp prepended to each of rpmalloc.c and rpmalloc.h naming version + upstream URL (the ticket's vendoring rule; upstream carries no version string in either file). Bodies are byte-verbatim — the shadow copies are bit-identical to ~/tmp/rpmalloc.ch as downloaded (md5 e50f32676267832a173b9139f39a5107 / 515f705df10773997440d137a6612edf), zero code edits. UNVERIFIED offline: that the download really is 1.4.5 — neither file carries a version macro, so "1.4.5" rests on JAB-036's provenance note, not on anything in the bytes.
  • Build is warning-free at -O3 (rpmalloc.c compiles clean under the tree's -std=c23 -fno-strict-aliasing). Stripped size +24 KB (2,336,416 -> 2,360,992 B), matching JAB-036's +20 KB estimate.

Measure 2026-08-11, current tree (post-sweep, post-STATUS-020)

Method: $HOME/tmp/JAB036/ptyrun.py <bin> todo, first byte to the tty = first frame, cwd = /home/gritzko/src/journal/work/STATUS-022, thinkcentre. 10 runs per quickjab leg, legs INTERLEAVED round-robin (not blocked) so machine drift hits all three equally; median. jab = 1 reference run. All 31 runs printed the same 7259 bytes.

| binary | first frame | user | sys | minflt | |------------------------------------------|-------------|------|------|--------| | jab (JSC, JIT) — reference, 1 run | 1.69 s | 1.58 | 0.55 | 61 k | | quickjab shipping, ~/bin (-O0) | 4.44 s | 3.39 | 1.54 | 1.053 M| | quickjab pristine, my Release -O3 | 4.19 s | 3.14 | 1.52 | 1.053 M| | quickjab rp, my Release -O3 + rpmalloc | 2.47 s | 2.55 | 0.37 | 18.5 k |

  • ROUND GATE (rp Release vs the shipping baseline ~/bin/quickjab): 2.47 vs 4.44 s = *-44.4%*, well over the >=10% gate. Against the pristine Release build (isolating the -O effect): 4.19 -> 2.47 = -41.1%.
  • -O buys almost nothing on this path: 4.44 (-O0) vs 4.19 (-O3) = -5.6%, confirming JAB-036 — the path is allocation-bound, not compute-bound.
  • minflt 1.053 M -> 18.5 k (57x): mallocng's mmap/munmap punting is gone. sys time 1.52 -> 0.37 s is the same fact seen from the kernel side. maxrss goes UP, 47 MB -> 70 MB — rpmalloc keeps its spans (see lifecycle above); that is the trade.
  • Spread was tight and non-overlapping: ship 4.38-4.64, pristine 4.09-4.29, rp 2.43-2.59.

Blockers and bummers

  • rpmalloc never returns memory to the OS in this wiring (no finalize) — maxrss +23 MB on the todo frame. Acceptable for a CLI; a long-lived quickjab daemon would want rpmalloc_finalize/trim, which nothing needs today.
  • The "5 known pre-existing engine-suite failures" from the STATUS-022 round do NOT appear in quickjab's own ctest: all 115 pass on the UNMODIFIED copy too, so they belong to some other suite. Parity is proven against the pristine copy, which is what the gate asks.
  • "rpmalloc 1.4.5" is unverifiable offline (no version string in the sources, no network) — carried over from JAB-036's note.
