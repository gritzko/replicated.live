JS-088: hand-rolled require-path resolution (libDir/_here) duplicated across 5 modules

Now
OPEN
Sev
MED

The be-relative require workaround (resolve a module's own dir so it can require siblings by absolute path under the resident loop, where argv[1] is loop.js not the module) is reinvented in five modules with subtly different fallbacks — "." vs argv[1] vs __dirname. Several sites do the require LAZILY in a function body, defeating the registry warm-cache and hiding the dependency graph. Method: Issues.

Input

Context

  • subs.js:44-46 libDir(){ return __dirname || "." } then subs.js:53 lazy require(libDir()+"/../core/discover.js") in classifyMount's body — a per-call require, not a top import.
  • classify.js:416-417 the SAME libDir(){ __dirname || "." }.
  • fold-decide.js:214-215 the SAME libDir(){ __dirname || "." }.
  • loop.js:14-15 a DIFFERENT idiom: _here = argv[1].slice(0, lastIndexOf("/")) — argv[1]-based, not __dirname.
  • refs.js:11 a THIRD idiom: require(__dirname+"/../../core/…") inline, no helper.

Goals

  • One shared/util/here.js exporting a base-dir + a sibling require helper; the 5 sites consume it (one resolution rule).
  • Hoist the lazy in-body requires (subs.js:53) to module top so the dependency graph is static + the warm-cache applies.

Constraints

  • Must work under the resident loop (argv[1]==loop.js) AND a one-shot entry; rely on __dirname (require.cpp injects it), drop the "."/argv[1] fallbacks once verified present.
  • No behavioural change to module resolution — same files loaded.

WIP

Design decisions

  • Standardise on __dirname-relative (the require.cpp contract); the "." fallback is dead under the real loader — assert + drop.
  • here.js stays dependency-free (no core/, no view/) so every layer may import it without a cycle.
