JS-070 MED: untrusted regex compiled/run per-line with no ReDoS guard

views/spot/match.js's regexMatcher compiles new RegExp(jsBody) from the user URI fragment, then runs re.exec per line over every candidate file behind the regex: VIEW. The only ceiling is a whole-file 16 MiB gate — no per-line length cap and no time/step budget — so (a+)+$ against a long line hangs the single-threaded runtime. Native used a Thompson NFA (linear), so this is also a parity divergence; matchFlat (the spot backtracker) likewise has no guard. Method: Issues.

Goals

  • A regex: (and spot:) search over a hostile file cannot wedge the runtime:

    a per-line length cap and/or a step/time budget bounds the work.

  • A repro test: regex:(a+)+$ (or spot analogue) over a long single-line

    file completes within a wall-clock budget instead of hanging.

Constraints

  • Pure JS, rides views/spot/search.js; keep the {,m}→{0,m} dialect

  • Stay a faithful subset of native (grep_match_span); don't regress the

WIP

Design decisions

  • Add a per-line byte cap (skip / truncate over-long lines) plus a step or

    wall-clock budget around re.exec; on overflow treat the line as no-match.

  • Minimum bar: reject nested unbounded quantifiers ((a+)+, (a*)*) at

    compile time so the worst exponentials never run.

  • Add a step-counter guard to matchFlat (bail → no-match on overflow);

    longer-term, port the bounded Thompson NFA for true linear parity.
