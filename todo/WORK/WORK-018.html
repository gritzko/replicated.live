WORK-018: gitlink pins via per-path descent — a shared utility, not a whole-tree walk

Now: OPEN

work.js nodePins answers "what sha does this tree pin its mounts at" by readTreeRecursive over the node's ENTIRE base tree — every tree object of the project inflated to find a handful of gitlink leaves whose paths are already known from .gitmodules. Make pin lookup a shared utility that descends each known path only.

Input

Context

Profiled jab work 2026-07-24: nodePins contributes a full-tree object walk per node that holds pins (the root + every mounted sub with children).

  • views/work/work.js nodePins: k.readTreeRecursive(tree, cb) collects kind === "s" leaves — O(all tree objects) getObject+inflate per node, per run.
  • The consumers only ever ask for pins at gitmodules.paths(dir) entries (treeRows mount ahbeh, resolveTrack pin-form tracks) — a known, short path list.
  • store.js reader already has the primitive: descendPath(rootTreeSha, segments) resolves one path in O(depth) tree reads.

Goals

A shared fn: (keeper, commitSha, paths[]) → { path: gitlinkSha }, descending each path; work.js nodePins becomes a thin memo over it.

  • Cost drops O(tree objects) → O(mounts × depth) per node; unpinned/missing paths simply absent from the map (current nodePins semantics).
  • A path whose leaf is not a gitlink (mode != 160000) is absent from the map — same as today's kind === "s" filter.
  • Utility lives in shared/ (gitmodules.js or a store.js reader method — implementer's pick), so status/subs stop hand-rolling the same lookup if they need it.

Constraints

  • Resolution stays on store.js descendPath — no new tree parser, no path string surgery beyond '/'-segment split.
  • Keeper opened by the caller (borrowed), the shared/ resource norm.
  • Behavior parity: work view renders byte-identical rows (the existing WORK tests are the harness).
