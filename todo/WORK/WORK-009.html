WORK-009: entered-worktree get click refuses — "NAVNONE: context //X is no worktree" for an existing wt

Now: OPEN Sev: HIGH

Input

Context

2026-07-19, live (gritzko): from the work view, entering //SUBFETCH-REPRO works (nav + view render fine), but a [get] click there dies: err: NAVNONE: context //SUBFETCH-REPRO is no worktree //:work. The tree EXISTS: work/SUBFETCH-REPRO/ is a be clone (main.js, core/, verbs/, jsrc/…) with a .be wtlog of five get ?#… rows (2026-07-14, alternating e7ae2927/9edfebcc re-pins).

  • Refusal site: core/loop.js:449 (the WORK-002 loud-refusal leg) — fires when contextRepo(opts2.context) returns null for a mutation verb.
  • contextRepo (loop.js:253-271): uri._parse → be.wtdir(navStr) (NAVESCAPE→null) → be.treeAt(dir) — any miss collapses to the same null, so the error cannot say WHICH step missed.
  • The asymmetry is the lead: the pager NAV path resolved //SUBFETCH-REPRO fine seconds earlier (the user was inside it); only the mutation-context path missed. Two resolution paths disagree about the same URI in the same session (resolve_hash is the mandated single path — check whether wtdir/contextRepo composition diverges from what nav used, incl. where the session was launched from and how //name composes off it).
  • The trailing //:work in the error line is the view's own address token riding the arg echo (same welding the WORK-002 [diff] defect showed) — possibly cosmetic, possibly the actual corrupted context string; must be established.

Goals

A [get]/[-N] click inside an entered worktree runs in that worktree; contextRepo resolves any URI the nav path resolves. When a context genuinely anchors nothing, the refusal names the failing step (parse / wtdir / treeAt), not a blanket "no worktree".

  • Red-first pty repro: work view → enter a wt row → click the get button; assert the get row lands in that wt's .be.
  • Establish whether the context string handed to _actSpell was already mangled (the //:work tail) or clean and mis-resolved.

Constraints

  • Rulings in force: all resolution through resolve_hash/discover (resolve_hash mandatory, no reimplementation); context changes only by navigation (BRO-024); //authority off arg0 only; verify through the real UI path (pty), not TLV probes.
  • Errors in plain words for the user-facing line (no bare NAVNONE).
  • Related: WORK-002 (context execution, landed 1075739f), JS-119 (cwd-pin ruling), JS-074 (error masking).

WIP

Design decisions

  • 2026-07-19 investigation (opus, pty fixture + instrumented /tmp copy): a HEALTHY existing wt does NOT reproduce — from project root, inside another wt, and inside the clone itself, the [-1] click resolves and the get runs. NAVNONE fires only on a genuine miss (wt dir or its .be removed post-paint), i.e. the WORK-002 refusal working as intended.
  • The nav (enter) and click paths are CODE-IDENTICAL: status //KEY operand → authorityRepo → be.wtdir/treeAt (loop.js:206-212) vs contextRepo → be.wtdir/treeAt (loop.js:259-261); be.projectRootDir caches once (resolve_hash.js:106), driveSpell never chdirs — one process cannot disagree with itself about //X.
  • //: work tail = COSMETIC status-line echo: pager.js:478 prepends message + " " + view-address. Refines the WORK-002 [diff] note — nothing is welded onto the spell/context; context at the throw is exactly //SUBFETCH-REPRO (parseOspell strips the invite slash, spell.js:154).
  • The step that missed: be.wtdir(navStr) → null (loop.js:259-260); treeAt never reached. Distinct causes collapse: no dir; .be gone → treeAt climbs to the MAIN tree and discover.js:295's prefix check rejects → null. The refusal cannot name which.
  • LIVE-failure hypotheses REFUTED by session facts (gritzko 2026-07-19): pager launched from the JOURNAL ROOT (tip code via the climb), session NEW, and a restart cleared the error. Not old-tree code, not long-lived cache drift — some per-process transient made be.wtdir null once for a URI the same process had just resolved. No known mechanism; unreproducible cold.
  • Deliverable therefore = the diagnosable refusal below: the next live occurrence must name its failing step and echo the cached projectRootDir/workRoot in the message, which pinpoints the transient.
