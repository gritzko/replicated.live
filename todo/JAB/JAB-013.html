JAB-013: ulog seekURI misses long-URI rows — 2048 pad NOROOM reads as "no match"; drain already has the raw slice

Now: OPEN Sev: MED

_ulog_seekURI (jab/ulog.hpp:172-195) reconstructs each row's URI via URIMake into a fixed u8 ub[2048]; on NOROOM JABCulogUriText returns 0 and the row silently never matches. Feed accepts raw URIs up to FILE_PATH_MAX_LEN=1024 whose escaped form (~3x) exceeds the pad — the same class JS-108 fixed on the read path (JABCulogUriStr, ulog.hpp:38, sized malloc). The reconstruction is also needless: ULOGu8sDrain sets rec.uri.data to the row's URI slice (dog/ULOG.c:119, ULOG.h:159); the ulog.hpp:25 comment claiming it stays empty is wrong. Found in the 2026-07-24 jab/ review.

Input

Context

  • A put/log on a deep path can write rows that seekURI then cannot find — reads as data loss to the caller.

Goals

  • seekURI matches every row it stored, regardless of URI length; compare against the raw rec.uri.data slice instead of reconstructing.

Constraints

  • Repro-first: append a row whose escaped URI > 2048 bytes, assert seekURI finds it.
  • Fix the ulog.hpp:25 comment while there.
