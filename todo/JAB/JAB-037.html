Found by the JAB-036 quickjab port (worker W5) while porting hunk.hpp: the field getters declare a 2-pointer u8s and hand it to a writer that fills 4 pointers, overwriting 16 bytes of the caller's stack on every invocation. gcc flags it -Wstringop-overflow; JSC builds happen to survive, so the suite stays green over live corruption.

Input

Context

  • jab/hunk.hpp:161 (and sibling getters): u8s buf = {} — two pointers — passed to JABChunkAt(hunk*, u8* buf[4], …).
  • JABChunkAt's JABCDataOf writes all 4 slots: 16 bytes past the u8s object, into adjacent locals/saved registers.
  • The quickjab twin (quickjab/hunk.c) declares u8 *buf[4] and reads buf[0] — byte-identical results, no smash; jab's own test/hunk.js passes on both, so the corruption is silent today.

Goals

  • Fix the jab getters to hand a real 4-slot array (or a typed record) to JABChunkAt; -Wstringop-overflow goes quiet.
  • Repro first per the workflow: an ASAN/-fstack-protector build of jab should trip on test/hunk.js before the fix and pass after.

Constraints

  • jab/ is edited only on gritzko's explicit order; this ticket records the finding, no code was touched.
