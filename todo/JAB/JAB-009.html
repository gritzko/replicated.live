JAB-009: mkd tok32 ends drift 1 byte per backslash-escape — MKDTonEscape shrinks the token, HUNKTokCB accumulates lengths

Now
OPEN
Sev
MED

Found via BRO-028 (gritzko's jab cat todo/ABC/ABC-011.mkd colour desync). Every markdown backslash-escape \X in prose sheds exactly 1 byte from every SUBSEQUENT tok32 end, so colour runs land mid-word with a shift that grows down the page. The desync is in the raw tok.parse(bytes,"mkd") binding output — JS painting and the C .color() sink faithfully paint the wrong spans they are given.

Input

Context

Proof (BRO-028 worker, read-only on ~/src/jab): for a \r b\n (7 bytes) the mkd tok32 stream ends at 1,2,3,4,5,6 — total 6 of 7 bytes, with a W tag sitting on the letter bytes; expected: the \r span ends at 4, last end 7.

  • dog/tok/MKDT.c:64-70 MKDTonEscape does u8csUsed(lit, 1) — drops the leading backslash from the callback token (an HTML-renderer convenience), so the emitted slice is 1 byte SHORTER than the source the grammar consumed (MKDT.c.rl:94-96).
  • dog/HUNK.c:1548-1556 HUNKTokCB packs tok32 ends by ACCUMULATING callback token lengths (end = c->off + $len(tok)) — assumes callback slices tile the source; any shrinking callback desyncs everything after it.
  • Em-dashes, ≥, quotes alone are clean — multibyte was a red herring; only \X escapes shed bytes.

Goals

tok32 ends tile the source for any mkd input; the BRO-028 xfail flips green.

  • Fix in ONE place: compute end from the slice pointer (tok[1] - sourceBase) in HUNKTokCB — immune to any shrinking callback; or stop shrinking in MKDTonEscape for the tok32 path (HTML path may still want the shrink).
  • The RED repro already exists: be-js-cat-color in the be/ tests (BRO-028, registered WILL_FAIL) — drop its WILL_FAIL entry when this lands, plus a jab-side unit if cheap.

Constraints

  • The HTML renderer path relies on the shrunk escape token — don't regress it; prefer the HUNKTokCB pointer-based end.
  • C side; ragel grammar untouched (the grammar consumes correctly — only the emit accounting lies).

WIP

Design decisions

Pointer-based end in HUNKTokCB: end = tok[1] - base, base added to HUNKTokCtx, the accumulator off field removed. Verified no lexer synthesizes tokens outside the source buffer ('U' nav tokens are packed by separate HUNK table code, never via this callback), so the pointer is always valid; fixes BOTH HUNKu32bTokenize consumers (tok.hpp binding + hunk.hpp) and leaves the HTML renderer's shrunk escape token untouched.
