The todo board renders slow: 2.6 s of a 3.0 s tty render is the per-wt status work behind the TODO-005 button frames (classifyMerge top 0.9 s + mounted subs 1.7 s over 88 wts + 81 subs; profile 2026-08-04). Ruling gritzko 2026-08-04 (r3, supersedes r2's rendered-line splice): in the PAGER, cache STRUCTURED per-row data — just the NUMBERS and head fields — and render the tok/TLV array EVERY time from it; native JS values only, never an io.buf/mmap handle. Each row block carries its OWN witness, so a post to the main tree (the upstream most wts track) refreshes only the COMMIT block's ahbeh numbers per wt while the expensive file counts and titles stay cached — never a full rerender. The STATUS-019 rev tree decides the drops: wt changed → file block, ticket changed → title/head, tips moved → commit block. A hit splices stored bytes and touches no classify, no graf, no keeper.

Input

Context

The render path is emitList → wtStat(t.wt) (todo.js:1031) → titleRow → fileFrame + commitFrame (todo.js:976): the frames are a FIXED-width region (1+16+1+10 cells), independent of the row's rails/key lead, so the rendered fragment is relocatable by construction.

  • span() records ABSOLUTE end offsets (todo.js:704); a cached fragment must store RELATIVE offsets and rebase on splice — the one mechanical prerequisite.
  • What the rendered frames depend on: files under the wt (counts), the wt's own wtlog (staged rows, cur tip), the TRACKED tip (ahbeh + the patch arg), the ticket page's title (the ci button's post 'KEY: title' spell), the theme truecolors, and the //<wt> ctx.
  • rev(wtDir) witnesses the files AND the wt's own wtlog (.be/ is re-admitted); rev(page's topic dir) witnesses the title; theme and ctx are per-process constants — the resident pager holds both.
  • The tracked tip is NOT witnessed: refs move below the track target's .be/ (unwatched, object churn) — the stale-ahbeh hole already flagged in STATUS-019's bummers.
  • STATUS-019 (in //STATUS-019/, unmerged) already memoizes the wtStat MODEL by rev; this ticket puts the RENDERED artifact on top and demotes that memo to the miss path.

Goals

One cached artifact per board row: the WHOLE LINE as emitted, dropped by revs, fingerprinted for what revs cannot see.

  • Memo in todo.js (consumers own values — the rev tree stores none): ticket file → { bytes(Uint8Array), toks(Uint32Array, relative), head, wtRev, pageRev, tips } surviving across render runs, pager-only, resident-only (no watcher → no memo, ruling 4).
  • FIRST a ONE-shot board check: rev(be.todoRoot()) — the ancestor rule makes any ticket edit anywhere bump the todo/ spot, so a standstill proves NO ticket changed: skip listTopics/listTopic/metaidx and every per-row page check, reuse the cached row set as-is, and only the per-wt revs + tips remain to check.
  • Row HIT = rev(wtDir) (wt rows only) AND rev(page's topic dir) both stand still AND the tips fingerprint (cur tip + resolved track tip, the status.js state precedent) matches → splice bytes, add the row's base offset to each tok, emit; zero wtStat/registry work, NO ticket-file read.
  • The entry stores the pageHead FIELDS the board logic needs (title, prio, closed, Sub, Rep, meta vals) so sorting, family nesting and the cols verdict run over cached heads without touching the file; wt-LESS rows cache too, with just the pageRev check.
  • A LINE is shape-dependent: rails (Sub: nesting), the arg line's vals brackets and the hunk's cols verdict are part of the stored entry — any of them differing from the fresh render run's is a MISS for that row (re-render, keep the head).
  • MISS = recompute through the existing wtStat (its STATUS-019 rev memo + foldSubs sub-gating stay as the cheap-miss layer), re-render the line ONCE via the existing titleRow — the cache captures its output, never a second renderer.
  • The pager's R/r already bumps the root — every line misses, no extra hook.
  • The tips fingerprint resolves per render via work.trackTip through the shared registry (~250 ms/board today for trackTip+ahbeh combined; tips alone are cheaper) — this is the price of never serving a stale ahbeh count; measure it and report.

Constraints

  • ONE row implementation: capture titleRow's output (parts/spans slice, offsets made relative); never fork a cached twin of the span emitters.
  • Native JS typed arrays for the stored bytes/toks — never a live io.buf/mmap handle (those are process resources, not values).
  • Builds ON the //STATUS-019/ worktree state of cache.js/todo.js — branch that wt or wait for its merge; do not re-implement the rev tree.
  • Tests repro-first: a pty leg proving a board re-render hits (object-read counter ~0 for unchanged wts, bytes identical) and that a write under ONE wt re-renders only that row; a tip moved with no fs event must recompute via the fingerprint. NO other tests edited without permission.
  • Verify through the real UI path: a pty click repro on a live board, not TLV probes.

WIP

Design decisions

  • The board memo keys by (board dir, arg line) — one pager loop reaches more than one project.
  • The topic DIR rev is the page witness: one ticket edit misses every row of that topic, other topics still hit.
  • Filter listings get the per-row memo but NOT the board short-circuit — their row set rides metaidx + the commit-time sort, which the todo/ spot does not witness.
  • The topic header row is not a ticket line — re-emitted each render (one spell); memos drop on any watcher live↔dead transition.
  • wtStat's STATUS-019 rev memo now carries the tips fingerprint too — a rev-only layer underneath would hand the line memo stale ahbeh counts on a fingerprint miss.
