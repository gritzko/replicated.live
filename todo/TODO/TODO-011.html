TODO-011 DONE: split the one-ticket page out of todo into its own view ticket

Now: DONE Sev: MED

RULING (gritzko, 2026-08-04): todo is the TABULAR side only — the open-ticket board, a topic's list, the meta-pair filters. The one-ticket page becomes its OWN view named ticket. Today one view multiplexes both by arg shape (views/todo/todo.js:1-6: bare → board, ABC → topic list, ABC-123 → ticket page) and has grown to 1601 lines; the page arm and the table arm share an arg grammar they don't actually share (filters mean nothing on a page, a page key means nothing to a table).

Input

Context

  • The routing is LEXICAL (the uc ucnum* "-" dgt+ key rule, todo.js:4-5) and stays lexical — no path resolution in arg classing.
  • The page arm renders a thin todo/GET/GET-001.mkd or a fat todo/GET/GET-001/README.mkd off be.todoRoot() (URI-016 climb, never an env var).
  • Click spells are the coupling to cut carefully (BE-054: context-less O spells, the pager stays arg-blind): 1. board/list ticket-key rows carry todo <KEY> spells today — a KEY row must now spell ticket <KEY>. 2. TODO-008 in-page ticket-valued meta links (See: BE-050) navigate to the ticket page — now ticket BE-050. 3. filter/topic spells (todo ABC Now:OPEN, argLineWith replacement, BRO-025) are table business and STAY todo spells, untouched.
  • Meta-pair machinery (TODO-003 metaidx, ONE find() per verb run; TODO-004 filters; the Now:/Sev: reading with the legacy header-mark fallback) is shared ground: the page shows a ticket's own pairs, the table filters on them. Share via requires, never duplicate.
  • Siblings: TODO-004 (arg grammar), TODO-008 (ticket-valued links), TODO-005 (board row growth, open).

Goals

ticket ABC-123 renders the one-ticket page exactly as todo ABC-123 does today (byte-parity is the RED/GREEN baseline); todo keeps board + topic list + filters only.

  • todo ABC-123 no longer serves the page: it refuses in plain words pointing at ticket ABC-123 (errors-in-plain-words rule; if a silent re-route is preferred that is gritzko's call — record the question in the Outcome, default to the refusal).
  • Every ticket-key click anywhere in the two views lands in ticket; every filter/topic click stays in todo.
  • ticket rejects non-key args in plain words (ticket ABC names the topic list it is not: point at todo ABC; filters likewise point at todo).

Constraints

  • Verbs resolve args, the pager stays arg-blind; spells stay context-less O spells (BE-054); arg classes stay LEXICAL.
  • Shared helpers (metaidx read, mkd page rendering, key lexing) move to a required module or stay required from one home — NO second implementation of any of them.
  • todo/done/ never lists — unchanged; the ticket view CAN render a closed ticket by key (a page is not a listing; same fail-open spirit as todo.js:45-48).
  • Minimal moving: extract, don't rewrite; views/ticket/ + edits in views/todo/; registry entry for the new view; no other verbs.
  • Status/board output for the table arms stays byte-identical; the page under ticket stays byte-identical to today's page under todo (modulo the in-page spell verb name).

WIP

Design decisions

  • *No registry entry exists to add.* core/registry.js build() resolves a bareword by FILE (views/<verb>/<verb>.js, then verbs/<verb>/) — dropping views/ticket/ticket.js in registers the view. Same for the test suite: test/CMakeLists.txt globs <verb>/<case>/run.sh, so test/ticket/page/ registers itself as be-js-ticket-page.
  • *ONE home for the shared ground, and it is views/todo/todo.js.* The page arm MOVED to ticket.js (refdefs, targetSpell, emitPage, pageLinks, the two tok helpers — 135 lines, cut verbatim); everything both views need stays in todo.js and is required from there: the key/topic LEXER (shape, ticketKey, keyTopic), the board root (boardDir), the page-file ladder (pageFile), the byte read (readBytes), EXTS, the arg-line grammar (parseArgs, argLineWith, spellWith) and the two click classifiers (navSpell, filterVal). Nothing is implemented twice; the edge is one-way (ticket.js → todo.js), so it needs no lazy require (unlike work.js ⇄ todo.js).
  • *parseArgs stays purely GRAMMATICAL and is shared.* It classes a token lexically (uc ucnum* "-" dgt+ unchanged) and never decides which view serves what. Its old "a ticket id takes no filters" check MOVED out to the two verbs, so each refusal can point at the other view and neither message is duplicated. unscheme grew a scheme parameter so the ONE DIS-060 parse serves todo:GET-1 and ticket:GET-1 alike.
  • *todo ABC-123 REFUSES (the ticket's stated default), it does not re-route.* The arg line IS the address bar (BRO-024/BRO-025), so a todo line answering with a page would lie about where the reader is. One refusal covers the filtered form too.
  • *Which spell is which:* a spell that lands on a PAGE is a ticket spell; a spell that lands on a LISTING is a todo spell. That is the whole rule, and navSpell() is its single point of truth for ticket-valued links. The in-page meta KEY/VALUE filter halves therefore stay todo spells minted through spellWith — a cross-view landing BY DESIGN, since a page carries no filters (a ticket-id arg line resolves to its TOPIC via argLineWith).
  • *views/work/work.js had to move too* (one literal): the [?] invite on a ticket-named worktree minted //: todo <KEY>, which the refusal would have turned into a dead button. It is //: ticket <KEY> now; the TOPIC-named branch is a listing and stays //: todo <TOPIC>.
  • *core/loop.js gains wrap.ticket = false.* An UNLISTED view type defaults to SOFT-wrap (pager.js wrapFor), so without the seed the split would have silently re-wrapped every ticket page. false preserves exactly what the page had under todo.
  • *The ticket miss is PLAIN WORDS, not the board's legacy TODONONE.* todo's own miss line is golden-pinned (BE-038) and is untouched; the new view starts clean under the errors-in-plain-words ruling.
